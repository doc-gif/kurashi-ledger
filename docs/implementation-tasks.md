## 全タスク共通の定義

各節を1つのIssue原稿として使用する。大きい場合は受入条件単位で子Issueに分け、親Issueだけを閉じて依存を解放しない。IDは恒久識別子。GitHub番号との対応は運用開始時に付ける。

**着手可能:** 実装再開済み、依存タスクの受入条件達成かつ成果物がmainに存在、対象契約版が確定、担当と作業範囲・予算が割当済み、競合資源が空いていること。単にIssueがclosedであるだけでは完了扱いしない。

**完了:** 受入条件の検証、対象SHAと実行結果、合成データによる証跡、公開差分の確認、別担当によるレビュー、マージとmain側の必要チェック成功。PR作成・CI成功だけではdoneにしない。コード以外の調査タスクも根拠とレビュー記録を残す。

ディレクトリは担当境界の提案。実行方式と技術構成はT00のADR（[docs/adr/](adr/README.md)）で決めた。データやHTTPの安全確認は、ADR-0007の共通の部品（G1〜G7）と操作ごとの適用表に従う。規則の本文はADR（ADR-0007の「定義」の場所）を正とする。本台帳は、タスクの範囲と検証の観点を書く。食い違う場合はADRに従い、気づいた作業で本台帳を直す。部品を変えるときは、適用表で影響する操作を確かめ、同じPRでADRと試験を直す。実装時にディレクトリの存在を確認し、ADRと食い違う場合は着手前に調整する。変更範囲を増やす場合は着手前に調整係へ引き継ぐ。各タスクは記載外の機能追加をしない。

## T07 — 永続化とmigrationの境界

- 依存: T06、T02。担当: 保存基盤。範囲: `src/infrastructure/storage/`、`migrations/`、Repository契約。共有資源: DBスキーマ、lockfile。

- データルート（ADR-0006）: 実体パスでの検査（Git作業ツリー、クラウド同期、ネットワークドライブ）、新規作成の手順（親ディレクトリが既にあることの確認、作業ディレクトリで組み立ててから1回の名前変更で置く、作成後の再検査、保守作業の状態ファイルや復元途中の退避物があれば作らない）、実データ／合成データの種別マーカー、固定の子（`db/`、`evidence/`、`snapshots/`、`tmp/`、`config/`、`logs/`、マーカー）がリンクでなくデータルートの配下にあることの検査、固定の子を空で作る共通の初期化（新規作成と復元の両方で使う。種別マーカーは操作ごとに決めた時点で書く。ADR-0006の1）、構造の版（種別マーカーに記録し、後のリリースで増えた固定の子だけを作るmigration）、権限（データルート・固定の子・作業ディレクトリを本人だけが使える権限で作って確かめる。新規作成・共通の初期化・復元・構造のmigrationで行い、起動時にデータルートと`tmp/`を確かめる。ADR-0006の1「権限」）、単一起動のlock（データルートの正規化した実体パスから決めた、データルートの外の`<データルート>.lock`に、OSのファイルロックで原子的に取る。強制終了ではOSが解放する。取れなければ奪わずに終了する。PIDファイルは表示用だけ。保守コマンドも同じlockを取り、入れ替えの前後を通して保持する）、migration前の退避と、DBとjournalの対を崩さないDBだけのrollback。rollbackは、中核の処理（DBディレクトリの入れ替えと、各段階からの再開・巻戻し。データルートとモードは引数で受け取る。ADR-0007の4）までをここで作り、一時の合成データのデータルートでその処理を直接呼んで試験する。利用者が使うコマンド（合成データ用の`rollback`と実データ用の`rollback:real`）は、起動モードの判別（G5）と実行物の確認（G6）を組み込むT09で公開する。
- 受入: 記録と改訂・参照を原子的に保存し、失敗時に半端な状態を残さない。古い版での上書きを拒否。DB版が新しすぎる場合に破損させない。
- 検証: 一時DBで再起動後の同一性、同時訂正、途中失敗、migration前後のデータ比較。各testは専用DBを使う。migration途中の強制終了でhot journalが残った状態からのrollback、rollbackの各段階での異常終了からの再開・巻戻し、保守作業の状態ファイル（`<データルート>.maintenance`。原子的かつ確実に書き、壊れた・読めない場合は起動しない）が残っている間は、アプリと新しい保守作業が起動せず、状態ファイルに対応する復旧操作（やり直し・入れ替えの完了・元に戻す・中止）だけが同じlockの下で実行できること（種類や対象が違う復旧操作は拒否されること）、欠けた`db/`を作り直さないこと、symlink・junctionによる検査回避。完全な新規環境での作成の成功、新規作成の各段階（初期スキーマ入りの空のDBの作成を含む）での異常終了のあと中途半端なデータルートが残らないこと、残った`<データルート>.create-*`（アプリが作ったものでないものを含む）を自動で削除せずに止まり、利用者が削除したあとでやり直せること、固定の子をリンクに差し替えたときに開かないこと、禁止先へのリンクを祖先に含むパスの拒否、状態ファイルや復元途中の退避物があるときに新規作成しないこと（lockを取ったあとの再確認を含む）、共通の初期化（新規作成の側）、構造の版（増えた子だけを作ること、前のリリースが新しい版のデータルートを開けて版を下げないこと）、復旧操作が欠けた子を作り直さずに段階を判別できること。復元の側の初期化の試験はT12で行う。lockについて、symlink・junction・大文字小文字の違う別名で同じデータルートを指定した2つのプロセスが同じlockで競合すること、2つ目の起動・保守コマンドが失敗すること、強制終了のあとに次の起動でlockを取れること、古いPIDファイルが判定に影響しないこと。lockファイルや状態ファイルをsymlink・junctionに差し替えたときに、開かずに終了し、リンク先を変更しないこと。lockファイルの名前に別のファイル（ほかの用途のSQLiteのDBを含む）があるときに、変更せずに終了すること。lockファイルを作る各段階で強制終了しても、次の起動でlockを取れること。ほかのユーザーが書き込める親ディレクトリ（共有フォルダ、`/tmp`の直下等）を拒否すること。試験の一時のデータルートも、本人専用の親（試験ごとに作る`0700`のディレクトリ等）の中に作る。新規作成・共通の初期化・構造のmigrationで作るものが本人だけの権限になること、データルートや`tmp/`の権限が広いときに開かずに終了すること。

- 受入: Amount Inputの値（Empty・Amount・Zero・Unknown）とT01の金額の状態の対応を決める。Emptyは保存しない編集中の状態で、独立の状態としても0としても保存しない。保存して再表示した状態が保存した状態と一致し、黙って変わらないことを試験する。保存するときのEmptyを、不明として保存して画面で示すか、エラーで止めるかを決め（項目ごとの規則はT09・T10）、`design/components.md`と`design/README.md`に記録する。

- ReactとViteをここで導入する（ADR-0004）。`npm run build`は、ビルドの前に依存の導入の記録がいまのlockfileと実行環境に一致することを確かめ、既存のmanifestを最初に削除し、`dist/`へ出力し終えてから最後にmanifest（commitのSHA・lockfileのハッシュ・Node.jsの版・各ファイルのハッシュ）を書く（ADR-0002）。既存の成果物がある状態からのビルド、途中で止めたビルド（manifestが残らないこと）、作業ツリーに変更がある状態でのビルド（manifestを書かないこと。ビルドの前からある変更と、ビルドの途中で加わって残った変更の両方）を試験する。ビルドの最中に変えて元に戻す意図的な改変は対象外（ADR-0002）。開発時は、ViteをmiddlewareモードでT26のサーバーに組み込み、ブラウザから見えるoriginを1つにする（ADR-0003の10）。開発UIからのトークン交換と状態を変える要求が成功し、Viteの単独の開発サーバーや別のポートからの直接の要求が拒否されること、HMRのWebSocketも同じ検査を通ることを試験する。CORSや認証を開発時だけ無効にしない。開発時のCSPは、応答ごとのnonceをViteの`html.cspNonce`と一致させて、inlineのstyle・scriptを許可する（ADR-0003の7）。実際のCSSとReactの変更がHMRで反映されること、nonceのない・値の合わないinlineのscript・styleが拒否されること、本番のCSPにnonceが含まれないことを試験する。開発時は、Viteが配信するHTMLの`<meta>`にも起動の識別子（ADR-0003の14）を入れ、開発UIからの交換・API要求が成功すること、識別子のない・違う要求が拒否されることを試験する。開発UIはDBを開かない段階から使える。開発時の起動をデータルートの検査に通すのはT09。UIのE2Eは、T05のブラウザ試験の基盤（ChromiumをMac/Windows/Linux、WebKitをMac）に追加する。Firefoxはbest effortとし、必須のE2E対象に含めない（2026-10-02の所有者決定）。

- 検証: 再送・二重クリック・ネットワーク応答喪失・訂正競合。外部取込の冪等キーは手入力の同額判定と分ける。`npm start`等の合成データモードが、指定なしでも既定のデータルートや`real`のデータルートを開かないこと。開発時の起動も、実データのデータルートを開かないこと。完全な新規環境で、`npm run start:real`の初回起動が確認のうえデータルートを作れること。リリースタグでない、または変更のある作業ツリーから`npm run start:real`を実行しても起動しないこと。作業branchで手元に作っただけのタグ（originにない、または`origin/main`から到達できないcommitを指すもの）や、originと指す先が違うタグでは起動しないこと。手元の`refs/remotes/origin/main`だけを動かしても、originの`main`から到達できないcommitでは起動しないこと。originの接続先が信頼するリポジトリでない（forkなど）cloneでは、mainとタグがそろっていても起動しないこと。オフラインで初めてのタグを使うと起動せず、照合済みのタグなら起動できること。`rollback:real`にも同じ条件が適用されること（開発branchや変更のある作業ツリー、手元に作っただけのタグ、originが信頼するリポジトリでないcloneから実データをrollbackできない）。データルートの検査に通る前に、トークンの一時ファイルがデータルートに書かれないこと。タグを切り替えたあとビルドしていない、ビルドに失敗・中断した（manifestがない）、manifestが欠けている、または配信物を書き換えた・追加した場合に、`npm run start:real`がDBを開く前に止まること。タグの切り替え後に依存の導入（`npm run setup`）を省略・中断した場合、`npm ci`を直接実行した場合、またはNode.jsの版を変えた場合にも止まること。Node.jsの版を変えて依存の導入だけをやり直し、ビルドし直していない場合（manifestのNode.jsの版が合わない）にも止まること。二重起動。

## T12 — CSV/JSON出力とバックアップ・復元

- 成果物: Issue/PR/CI、最新head/base、workerの明示的引継ぎ、レビュー記録から着手候補・修正待ち・判断待ちを判定。文書版のCodex定期確認は先行設定済みで、本タスクは製品CIとの統合と検証を追加する。PR #4のレビュー運用の台帳（`.review/invariants.json`）がmainにあれば、ADR-0007の部品（G1〜G7）ごとの不変条件を登録し、部品のファイルを変えたときに関係する確認の観点が引き出されるようにする。
- 受入: 無更新の時間だけで完了とせず、最新SHAのready-for-reviewを確認する。API不調は未確認とし、同じheadへの同じコメントを重複投稿しない。PR由来コードを高権限環境で実行しない。
- 検証: ページネーション、rate limit、古いready、レビュー中のpush/base更新、CI失敗、同時巡回、同一アカウントのCOMMENTレビュー、Copilot利用不可。
- 非対象: 実装AIの起動、実装修正、自動マージ、デプロイ。

## T24 — 外部AIの定期確認とレビュー指摘対応

- 依存: T23。担当: 実装側の運用。範囲: docs/external-worker.md、選択したAI環境の登録・停止・引継ぎ手順。
- 成果物: 所有者または調整係が割り当てた承認済みIssueを外部AIが定期確認し、作業中はDraft PR作成、指摘への修正を行い、レビュー依頼時はOpenへ切り替えて新head/baseを引き継ぐ。レビュー待ち・指摘なしなら新しい投稿をしない。
- 受入: 既存PRの修正を新規作業より優先。同じbranch/worktreeの多重起動を防ぎ、生存不明のworkerを勝手に置き換えない。仕様拡大は候補Issueへ分離。指摘は根拠を評価し、不要な変更は理由を残す。
- 検証: 起動重複・中断復帰・古い担当・停止中の製品実装・同じ指摘の繰返し・レビュー間の矛盾・2回の修正でも未解決・予算到達。CLAUDE.mdとAGENTS.mdの整合も確認。
- 子タスク: T24a 実行環境と担当割当、T24b PR引継ぎと修正ループ、T24c 停止・異常系の運用試験。
- 非対象: 自動マージ。CopilotのFix with Copilot等で第二の実装担当を無断起動しない。環境未設定なら指示書と手動引継ぎまで。

## T26 — ローカルHTTPサーバーと安全境界

- 依存: T02、T05。担当: 基盤・セキュリティ。範囲: `src/infrastructure/http/`、起動処理（`npm start`）、対応test。共有資源: `package.json`のscripts（T08より先に変更する）。Node.js標準の`node:http`を使い、依存を追加しない（追加が必要なら理由をPRに書き、lockfileを共有資源として扱う）。
- 成果物: ADR-0003の境界。開発時にViteのmiddlewareとHMRのWebSocketを同じ検査の後ろに組み込める口（組み込み自体はT08）。`127.0.0.1`へのbind、Hostの完全一致、起動ごとのトークンとcookieの交換、状態を変える要求の`Sec-Fetch-Site`・`Origin`・`Content-Type`の検査、CORSなし、CSP・`Cache-Control: no-store`等の応答ヘッダ、ログの制限。設定したディレクトリの静的ファイルの配信（試験は固定のfixtureで行い、ビルド済みUIはT08以降に配信する）、ADR-0002の起動と終了。
- 受入: ADR-0003の「別タスクで行う検証」の項目（開発時の構成と二重起動を除く）を自動試験し、T05のCIでMac/Windows/Linuxで通る。対応ブラウザでの試験（`file://`からのcookie交換等）はT05のブラウザ試験の基盤で行い、T26の完了時点でCIで実行できる。DBは開かない。データルートの検査とlockの組込みはT09、Viteを組み込む開発時の構成はT08で行う。
- 検証: 不正なHost、別Origin・別ポート、トークンなし・使用済み・別起動のcookie、`file://`から開いたときのcookieの交換（対応ブラウザ）、ポート使用中、トークン交換のエンドポイントだけがcookieなしで有効な1回限りのトークンを受け付け、ほかのAPIはcookieなしで拒否されること、ログ・サーバーへの要求のURL・交換後のURLにトークンが残らないこと、戻る操作でトークン付きのURLに戻らないこと、`Referer`にトークンが含まれないこと。トークンを入れる一時ファイルの権限が本人だけに限られ（macOSは`0600`、Windowsは本人だけのACL）、既存のファイルやsymlinkがあれば作成が失敗すること。T26は、外から渡された本人専用の一時ディレクトリだけを扱い、データルートには触れない。実行時にデータルートの`tmp/`を渡すつなぎ込みは、データルートの検査を組み込むT09で行う（検査の前にデータルートへ書き込まないため）。静的配信で、`..`・エンコードされた区切り文字・バックスラッシュ・配信ルート外を指すリンクによる範囲外のファイルの取得が拒否されること、静的ファイルの応答にも`Cache-Control: no-store`が付くこと（ADR-0003の13）。起動ごとの識別子を作り、配信するHTML（交換用のページを含む）の`<meta>`に入れること。識別子のないAPI要求、識別子が合わない要求（前の起動のものを含む）を拒否すること（ADR-0003の14。ヘッダの名前と形式、注入の方法をここで決める）。
- 非対象: 記録のAPI（T09）、画面（T10）、外部通信、LANへの公開。

## T27 — バックアップと出力の操作画面

- 依存: T08、T12、T26。担当: UI・application。範囲: `src/ui/features/backup/`、対応するAPIアダプタ。
- 成果物: バックアップ保存先の設定（パス入力と、T12によるサーバー側の検査結果の表示）、作成の操作と進行・結果、生成したパスフレーズの提示と保管の注意、検証済みバックアップの一覧、前回の作成からの経過による起動時の催促（期間の初期値をここで決める）、CSV/JSON出力の操作（平文であることの表示）。

- 非対象: 復元の画面化、クラウドへの直接送信、自動バックアップのスケジュール。
