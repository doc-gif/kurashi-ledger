## 全タスク共通の定義

各節を1つのIssue原稿として使用する。大きい場合は受入条件単位で子Issueに分け、親Issueだけを閉じて依存を解放しない。IDは恒久識別子。GitHub番号との対応は運用開始時に付ける。

**着手可能:** 実装再開済み、依存タスクの受入条件達成かつ成果物がmainに存在、対象契約版が確定、担当と作業範囲・予算が割当済み、競合資源が空いていること。単にIssueがclosedであるだけでは完了扱いしない。

**完了:** 受入条件の検証、対象SHAと実行結果、合成データによる証跡、公開差分の確認、別担当によるレビュー、マージとmain側の必要チェック成功。PR作成・CI成功だけではdoneにしない。コード以外の調査タスクも根拠とレビュー記録を残す。

ディレクトリは担当境界の提案。実行方式と技術構成はT00のADR（[docs/adr/](adr/README.md)）で決めた。データやHTTPの安全確認は、ADR-0007の共通の部品（G1〜G7）と操作ごとの適用表に従う。規則の本文はADR（ADR-0007の「定義」の場所）を正とする。本台帳は、タスクの範囲と検証の観点を書く。食い違う場合はADRに従い、気づいた作業で本台帳を直す。部品を変えるときは、適用表で影響する操作を確かめ、同じPRでADRと試験を直す。実装時にディレクトリの存在を確認し、ADRと食い違う場合は着手前に調整する。変更範囲を増やす場合は着手前に調整係へ引き継ぐ。各タスクは記載外の機能追加をしない。

## T07 — 永続化とmigrationの境界

- 依存: T06、T02。担当: 保存基盤。範囲: `src/infrastructure/storage/`、`migrations/`、Repository契約。共有資源: DBスキーマ、lockfile。
- 成果物: T00で決定したDB（ADR-0005の`node:sqlite`）、ユースケース単位のRepository、transaction、スキーマ版、楽観的競合検出。DBはrepo外。
- データルート（ADR-0006）: 実体パスでの検査（Git作業ツリー、クラウド同期、ネットワークドライブ）、新規作成の手順（親ディレクトリが既にあることの確認、作業ディレクトリで組み立ててから1回の名前変更で置く、作成後の再検査、保守作業の状態ファイルや復元途中の退避物があれば作らない）、実データ／合成データの種別マーカー、固定の子（`db/`、`evidence/`、`snapshots/`、`tmp/`、`config/`、`logs/`、マーカー）がリンクでなくデータルートの配下にあることの検査、固定の子を空で作る共通の初期化（新規作成と復元の両方で使う。種別マーカーは操作ごとに決めた時点で書く。ADR-0006の1）、構造の版（種別マーカーに記録し、後のリリースで増えた固定の子だけを作るmigration）、権限（データルート・固定の子・作業ディレクトリを本人だけが使える権限で作って確かめる。新規作成・共通の初期化・復元・構造のmigrationで行い、起動時にデータルートと`tmp/`を確かめる。ADR-0006の1「権限」）、単一起動のlock（データルートの正規化した実体パスから決めた、データルートの外の`<データルート>.lock`に、OSのファイルロックで原子的に取る。強制終了ではOSが解放する。取れなければ奪わずに終了する。PIDファイルは表示用だけ。保守コマンドも同じlockを取り、入れ替えの前後を通して保持する）、migration前の退避と、DBとjournalの対を崩さないDBだけのrollback。rollbackは、中核の処理（DBディレクトリの入れ替えと、各段階からの再開・巻戻し。データルートとモードは引数で受け取る。ADR-0007の4）までをここで作り、一時の合成データのデータルートでその処理を直接呼んで試験する。利用者が使うコマンド（合成データ用の`rollback`と実データ用の`rollback:real`）は、起動モードの判別（G5）と実行物の確認（G6）を組み込むT09で公開する。
- 受入: 記録と改訂・参照を原子的に保存し、失敗時に半端な状態を残さない。古い版での上書きを拒否。DB版が新しすぎる場合に破損させない。
- 検証: 一時DBで再起動後の同一性、同時訂正、途中失敗、migration前後のデータ比較。各testは専用DBを使う。migration途中の強制終了でhot journalが残った状態からのrollback、rollbackの各段階での異常終了からの再開・巻戻し、保守作業の状態ファイル（`<データルート>.maintenance`。原子的かつ確実に書き、壊れた・読めない場合は起動しない）が残っている間は、アプリと新しい保守作業が起動せず、状態ファイルに対応する復旧操作（やり直し・入れ替えの完了・元に戻す・中止）だけが同じlockの下で実行できること（種類や対象が違う復旧操作は拒否されること）、欠けた`db/`を作り直さないこと、symlink・junctionによる検査回避。完全な新規環境での作成の成功、新規作成の各段階（初期スキーマ入りの空のDBの作成を含む）での異常終了のあと中途半端なデータルートが残らないこと、残った`<データルート>.create-*`（アプリが作ったものでないものを含む）を自動で削除せずに止まり、利用者が削除したあとでやり直せること、固定の子をリンクに差し替えたときに開かないこと、禁止先へのリンクを祖先に含むパスの拒否、状態ファイルや復元途中の退避物があるときに新規作成しないこと（lockを取ったあとの再確認を含む）、共通の初期化（新規作成の側）、構造の版（増えた子だけを作ること、前のリリースが新しい版のデータルートを開けて版を下げないこと）、復旧操作が欠けた子を作り直さずに段階を判別できること。復元の側の初期化の試験はT12で行う。lockについて、symlink・junction・大文字小文字の違う別名で同じデータルートを指定した2つのプロセスが同じlockで競合すること、2つ目の起動・保守コマンドが失敗すること、強制終了のあとに次の起動でlockを取れること、古いPIDファイルが判定に影響しないこと。lockファイルや状態ファイルをsymlink・junctionに差し替えたときに、開かずに終了し、リンク先を変更しないこと。lockファイルの名前に別のファイル（ほかの用途のSQLiteのDBを含む）があるときに、変更せずに終了すること。lockファイルを作る各段階で強制終了しても、次の起動でlockを取れること。ほかのユーザーが書き込める親ディレクトリ（共有フォルダ、`/tmp`の直下等）を拒否すること。試験の一時のデータルートも、本人専用の親（試験ごとに作る`0700`のディレクトリ等）の中に作る。新規作成・共通の初期化・構造のmigrationで作るものが本人だけの権限になること、データルートや`tmp/`の権限が広いときに開かずに終了すること。

- ReactとViteをここで導入する（ADR-0004）。`npm run build`は、ビルドの前に依存の導入の記録がいまのlockfileと実行環境に一致することを確かめ、既存のmanifestを最初に削除し、`dist/`へ出力し終えてから最後にmanifest（commitのSHA・lockfileのハッシュ・Node.jsの版・各ファイルのハッシュ）を書く（ADR-0002）。既存の成果物がある状態からのビルド、途中で止めたビルド（manifestが残らないこと）、作業ツリーに変更がある状態でのビルド（manifestを書かないこと。ビルドの前からある変更と、ビルドの途中で加わって残った変更の両方）を試験する。ビルドの最中に変えて元に戻す意図的な改変は対象外（ADR-0002）。開発時は、ViteをmiddlewareモードでT26のサーバーに組み込み、ブラウザから見えるoriginを1つにする（ADR-0003の10）。開発UIからのトークン交換と状態を変える要求が成功し、Viteの単独の開発サーバーや別のポートからの直接の要求が拒否されること、HMRのWebSocketも同じ検査を通ることを試験する。CORSや認証を開発時だけ無効にしない。開発時のCSPは、応答ごとのnonceをViteの`html.cspNonce`と一致させて、inlineのstyle・scriptを許可する（ADR-0003の7）。実際のCSSとReactの変更がHMRで反映されること、nonceのない・値の合わないinlineのscript・styleが拒否されること、本番のCSPにnonceが含まれないことを試験する。開発時は、Viteが配信するHTMLの`<meta>`にも起動の識別子（ADR-0003の14）を入れ、開発UIからの交換・API要求が成功すること、識別子のない・違う要求が拒否されることを試験する。開発UIはDBを開かない段階から使える。開発時の起動をデータルートの検査に通すのはT09。UIのE2Eは、T05のブラウザ試験の基盤（ChromiumをMac/Windows/Linux、WebKitをMac）に追加する。Firefoxはbest effortとし、必須のE2E対象に含めない（2026-10-02の所有者決定）。

## T09 — 入力・訂正のユースケース

- 依存: T06、T07、T08、T26。担当: application。範囲: `src/application/records/`、そのAPIアダプタ（T26のサーバーに載せる）、起動処理へのデータルートの組込み。

- 起動処理: 起動モードを判別する。実利用モードは`npm run start:real`でだけ選べ、ADR-0006の「承認済みリリース」の条件（信頼するリポジトリであるorigin、originと一致する注釈付きタグ、`origin/main`から到達できるcommit、変更のない作業ツリー）を満たさなければ起動しない。originの接続先を識別する方法（URLの正規化、GitHubのリポジトリIDの照合等）をここで決める。それ以外は合成データモードで、合成データのデータルートの指定がなければ終了する（ADR-0006）。T26の起動処理に、T07のデータルートの検査・種別マーカー・lockを組み込み、検査に通るまでDBを開かない。検査に通ったデータルートの`tmp/`を、トークンを入れる一時ファイルの作成先としてT26に渡す（`tmp/`がリンクでなく、データルートの配下にあることを確かめてから。ADR-0006の固定の子の検査）。開発時の起動（Viteのmiddleware）も、同じデータルートの検査・種別マーカー・lock・起動モードの判別（ADR-0007のG1〜G5）に通す。二重起動を防ぐ。`npm run start:real`は、DBを開く前に、依存の導入の記録がいまのlockfileと実行環境に一致すること、配信物のmanifestがHEADと`package-lock.json`といまのNode.jsの版に一致しファイルのハッシュが合い余分なファイルがないことを確かめ、確かめた内容をメモリに読み込んで配信する（ADR-0002）。
- 診断ログ（ADR-0010の1の9・10）: データルートの`logs/`へのつなぎ込みは、T09とT29のうち後からmainに入るほうが行う。判定は、マージの前に最新のmainを取り込んだ時点のbaseで行う。そのbaseにT29があれば、T09が、データルートの検査（G1〜G5）に通ったあとでT29のファイルの出力先を`logs/`へつなぐ（検査に通る前はターミナルだけに出す）。T29がなければ、T09はつながず、T29の受入でつなぐ。
- 成果物: ソース別の下書き→検証→確定、訂正、検索、勤務先別月表示。Clock/ID/Repositoryを注入。
- 受入: 銀行入金だけでも登録可能。保存再試行は重複しない一方、同額同日の別件は保存可能。同時編集は衝突を知らせる。曖昧な重複は候補表示に留める。
- 検証: 再送・二重クリック・ネットワーク応答喪失・訂正競合。外部取込の冪等キーは手入力の同額判定と分ける。`npm start`等の合成データモードが、指定なしでも既定のデータルートや`real`のデータルートを開かないこと。開発時の起動も、実データのデータルートを開かないこと。完全な新規環境で、`npm run start:real`の初回起動が確認のうえデータルートを作れること。リリースタグでない、または変更のある作業ツリーから`npm run start:real`を実行しても起動しないこと。作業branchで手元に作っただけのタグ（originにない、または`origin/main`から到達できないcommitを指すもの）や、originと指す先が違うタグでは起動しないこと。手元の`refs/remotes/origin/main`だけを動かしても、originの`main`から到達できないcommitでは起動しないこと。originの接続先が信頼するリポジトリでない（forkなど）cloneでは、mainとタグがそろっていても起動しないこと。オフラインで初めてのタグを使うと起動せず、照合済みのタグなら起動できること。`rollback:real`にも同じ条件が適用されること（開発branchや変更のある作業ツリー、手元に作っただけのタグ、originが信頼するリポジトリでないcloneから実データをrollbackできない）。データルートの検査に通る前に、トークンの一時ファイルがデータルートに書かれないこと。タグを切り替えたあとビルドしていない、ビルドに失敗・中断した（manifestがない）、manifestが欠けている、または配信物を書き換えた・追加した場合に、`npm run start:real`がDBを開く前に止まること。タグの切り替え後に依存の導入（`npm run setup`）を省略・中断した場合、`npm ci`を直接実行した場合、またはNode.jsの版を変えた場合にも止まること。Node.jsの版を変えて依存の導入だけをやり直し、ビルドし直していない場合（manifestのNode.jsの版が合わない）にも止まること。二重起動。T09がつなぐ場合（上の「診断ログ」）、データルートの検査に通る前に`logs/`へ書かず、通ったあとに書くこと。

- 設計の正本: [ADR-0010](adr/0010-diagnostics-and-maintainability.md)の4.4。
- 成果物: Biomeのlinter（推奨の`suspicious`・`correctness`の規則と、`noConsole`・`noFloatingPromises`）。Gitの対象外の生成物（`dist/`、`test-results/`等）を対象から外し（`vcs.useIgnoreFile`）、`noConsole`は`src/`の製品のファイルだけに適用する（`scripts/`・試験のファイル・`e2e/`・診断の出力先と起動処理は対象外。ADR-0010の4.4）。書式の統一（formatter）は入れない。
- 受入: lintの失敗でCIが失敗する。規則を外すときは、ファイル・行ごとの理由を残す（一律の無効化をしない）。Biomeの導入後に、3つのOSで`npm run setup`・`check:install`が通る（このOSで入らないoptionalな依存の扱いを含む。ADR-0008）。インストールスクリプトがなく、`resolved`が`https://registry.npmjs.org/`だけ。
- 検証: 意図的な違反（待たれないPromise、`src/`の製品のファイルの`console.log`）でCIが失敗すること、`dist/`の生成物や`scripts/`・試験のファイルの`console`の出力で失敗しないこと、3つのOSのCI、依存のライセンスとサポートの確認。
- 非対象: 書式の統一（T32の完了後に、進行中のPRが少ない時期を所有者と決める）、ESLint・typescript-eslint（TypeScript 7.1でAPIが安定したら再評価）。
