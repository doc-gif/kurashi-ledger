# 給与の所得の年への帰属

[制度の規則の入口](README.md)／規則: `jp-salary-income-year`（版`1`、状態`draft`）／制度データ: `rules/salary-income-year/v1.json`／使う担当: T11（照合の帰属）、T16・T18（所得の年の集計を使う試算）

[照合の規則](../contracts/reconciliation.md)の8が「T14が承認した規則」としている、給与明細の所得の年への帰属の規則。一次資料の根拠を確かめたが、契約版1.0の明細では当てはめてよい給与を見分けられないので、版1は**自動では当てはめない**（下の「規則（版1）」）。年間資料か利用者の指定がない明細の帰属は`undetermined`のまま。

## 根拠

給与所得の収入金額の収入すべき時期は、次のとおり（国税庁 タックスアンサーNo.2509。根拠法令等: 所得税法第36条、所得税基本通達36-9）。

| 給与の種類 | 収入すべき時期 |
| --- | --- |
| 一般の給与で、契約・慣習・株主総会の決議等により支給日が定められているもの | その支給日 |
| 一般の給与で、支給日が定められていないもの | その支給を受けた日 |
| 給与規程の改訂が既往にさかのぼって実施されたための新旧給与の差額 | 支給日が定められていればその支給日、定められていなければ改訂の効力が生じた日 |
| 役員賞与のうち、利益を基礎として支給金額が定められるもの | 決議等があった日（各人の金額が定まらなければ、定まった日） |
| いわゆる認定賞与 | 定められた支給日、定めがなければ現実に支給を受けた日 |

勤務した期間（「12月分」等）や、入金された日ではなく、支給日で決まる。年末の支給日の給与が翌年に入金されても、所得の年は支給日の年。通勤手当の非課税限度額の改正の適用（令和7年11月）でも、「支払われるべき」日を同じ区分で判定している（通勤手当の非課税限度額の引上げに関するQ&AのQ3〜Q9。未払いのまま後日支給した分は、本来の支給日による）。

## 規則（版1）: 自動では当てはめない

- **自動の帰属は未対応（`autoApply`が`false`）。** この規則は、規則の根拠で所得の年を決めない（契約の照合の規則の8の「規則」の根拠を作らない）。帰属は、契約どおり、年間資料（`annual-coverage`）と利用者の指定（`tax-year-assertion`）だけで決まり、どちらもなければ`undetermined`。
- **理由:** 上の表のとおり、支給日の定めがない給与、支給日の定めがない遡及差額、利益を基礎とする役員賞与、認定賞与は、支給日と別の時期の収入になる。契約版1.0の給与明細には、これらを見分ける項目も、規則の対象外と記録する手段もない。支払予定日の年を規則の年にすると、利用者の指定がない明細では、誤った年が黙って使われる（指定があっても`conflict`になるだけで、指定がなければ防げない）。
- **表示の候補:** 明細の`scheduledPayDate`が`known`なら、その暦年を、利用者が所得の年を指定するときの候補として**表示するだけ**にする（通常の給与＝契約・慣習等で支給日が定められた給与の場合の年）。表示の候補は、帰属の根拠にも、集計の範囲の絞り込みにも使わない。範囲外の給与（決議の日等による給与）がありうることを併せて示す。
- **使わないもの:** 入金日、勤務期間、行の期間、明細の対象の表示、記録日時から年を決めない（契約の「単独では根拠にしないもの」と同じ）。帰属の候補の年は、契約の表のとおり。

### 例（`rules/salary-income-year/v1.json`の`examples`）

| 例 | 明細と事実 | 帰属 | 候補の年 | 表示の候補 |

| SIY-1（年をまたぐ範囲外の給与、指定なし） | 利益を基礎とする役員賞与。決議は2025-12-20（明細からは分からない）、明細の支払予定日2026-01-09、勤務期間の記載なし。年間資料・利用者の指定なし | `undetermined`（所得の年は`unknown`） | すべての年（勤務期間が`not-stated`） | 2026（表示だけ。正しい年は2025年で、2026年に決めない） |

### 契約の帰属の候補の年の表との関係

規則は帰属の根拠を作らないので、契約の表に次元を足さない。ただし、範囲外の給与の本当の時期（決議の日・改訂の効力が生じた日・支給を受けた日）は表の次元にないので、勤務期間等が分かっている明細では、候補の年に本当の年が入らないことがある（契約への候補の2）。

### 行ごとの帰属

契約版1.0は、帰属を明細全体で1つとし、行ごとの帰属が必要かをT14に委ねている（[合成例](../contracts/examples.md)のEX-04(b)）。支給日が定められた遡及差額は、その明細の支給日で帰属する（上の表の3行目）ので、明細全体で1つの年で足りる。支給日の定めがない遡及差額は、明細の支給日と別の時期になりうるが、この版は自動で年を決めないので、利用者の指定で扱う。

## 契約への候補（所有者の判断待ち）

このPRでは契約を変えない。次は所有者の判断待ちで、決まるまで自動の帰属は未対応のまま。

1. 給与明細に「支給日の定めの種類」（契約・慣習等で定められた支給日か、ほかの時期か）を記録する項目を足し、定められた支給日の給与だけにこの規則を自動で当てはめる。
2. 範囲外の給与の本当の時期（決議の日・改訂の効力が生じた日・支給を受けた日）を、帰属の候補の年の表の次元に足す。
3. 規則と利用者の指定が食い違うときに、利用者の指定を優先する手段（いまは`conflict`）。

## 制度のケース

帰属は照合（T11）の判定で、計算runの結果ではないので、`regime-cases.json`のケースにしない（例は制度データの`examples`。検査が、規則の根拠で年を決める例がないことを確かめる）。T03の台帳の場面（`tests/fixtures/ledger/cases/EX-05.json`）は、合成例の説明のための例示の規則（`EX-05-scheduled-pay-date-year`）を使っている。この版は自動で当てはめないので、例示の規則の代わりにはならない（EX-05の「規則が承認された場合（例示）」は、契約への候補の1が決まった後の版で確かめる）。
