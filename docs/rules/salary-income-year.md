# 給与の所得の年への帰属

[制度の規則の入口](README.md)／規則: `jp-salary-income-year`（版`1`、状態`draft`）／制度データ: `rules/salary-income-year/v1.json`／使う担当: T11（照合の帰属）、T16・T18（所得の年の集計を使う試算）

[照合の規則](../contracts/reconciliation.md)の8が「T14が承認した規則」としている、給与明細の所得の年への帰属の規則。T14の承認までは、この規則を使わない（年間資料か利用者の指定がない明細の帰属は`undetermined`のまま）。

## 根拠

給与所得の収入金額の収入すべき時期は、次のとおり（国税庁 タックスアンサーNo.2509。根拠法令等: 所得税法第36条、所得税基本通達36-9）。

| 給与の種類 | 収入すべき時期 |
| --- | --- |
| 一般の給与で、契約・慣習・株主総会の決議等により支給日が定められているもの | その支給日 |
| 一般の給与で、支給日が定められていないもの | その支給を受けた日 |
| 給与規程の改訂が既往にさかのぼって実施されたための新旧給与の差額 | 支給日が定められていればその支給日、定められていなければ改訂の効力が生じた日 |
| 役員賞与のうち、利益を基礎として支給金額が定められるもの | 決議等があった日（各人の金額が定まらなければ、定まった日） |
| いわゆる認定賞与 | 定められた支給日、定めがなければ現実に支給を受けた日 |

勤務した期間（「12月分」等）や、入金された日ではなく、支給日で決まる。年末の支給日の給与が翌年に入金されても、所得の年は支給日の年。通勤手当の非課税限度額の改正の適用（令和7年11月）でも、「支払われるべき」日を同じ区分で判定している（通勤手当の非課税限度額の引上げに関するQ&AのQ3〜Q9。未払いのまま後日支給した分は、本来の支給日による）。

## 規則（版1）

- **入力:** 給与明細の`scheduledPayDate`（支払予定日。明細に書かれた支給日）だけ。
- **仮定:** 明細に書かれた支給日を、契約・慣習等で定められた支給日とみなす。
- **結果:** `scheduledPayDate`が`known`なら、その日の暦年を所得の年とする（契約の帰属の根拠の「規則」。規則の識別子`jp-salary-income-year`と版`1`を根拠として残す）。
- **当てはめないもの:** `scheduledPayDate`が`unknown`・`not-stated`の明細（規則の根拠にならず、ほかの根拠がなければ`undetermined`。候補の年は契約の表どおり、すべての年）。適用の年（`applies`の2025年・2026年）以外の暦年になる明細。
- **使わないもの:** 入金日、勤務期間、行の期間、明細の対象の表示、記録日時（契約の「単独では根拠にしないもの」と同じ。この規則はこれらを入力にしない）。

### 契約の帰属の候補の年の表との関係

規則の入力は、表の次元「支払予定日」だけなので、契約の表に次元を足さない（[照合の規則](../contracts/reconciliation.md)の8の「規則が新しい次元を使う場合は、この表を同じ変更で直す」に当たらない）。

### 行ごとの帰属は要らない

契約版1.0は、帰属を明細全体で1つとし、行ごとの帰属が必要かをT14に委ねている（[合成例](../contracts/examples.md)のEX-04(b)）。遡及差額の行も、支給日が定められていれば、その明細の支給日で帰属する（上の表の3行目）ので、明細全体で1つの年で足りる。支給日の定めがない遡及差額（改訂の効力が生じた日による）は、この規則の範囲外（下の「範囲外」）。

## 範囲外

次の給与は、この規則の範囲外。契約版1.0の明細には、これらを見分ける項目がない。

- 支給日の定めがない給与（支給を受けた日による）
- 遡及差額のうち支給日の定めがないもの（改訂の効力が生じた日による）
- 利益を基礎とする役員賞与（決議等の日による）、認定賞与、経済的利益（現物給与）

これらの明細にも規則は支給日の年を導くので、実際の時期と違う場合は、利用者が指定（`tax-year-assertion`）すると、規則の年と食い違って帰属が`conflict`になる（黙って違う年に数えない。照合の規則の8の順3）。

## 契約への候補（所有者・調整係の判断待ち）

- 上の範囲外の明細で、利用者の指定を規則より優先する、または明細ごとに規則の対象外と記録する手段は、契約版1.0にない（いまは`conflict`のまま残る）。必要なら、照合の判断（`tax-year-assertion`）の意味を変えるか、明細に「支給日の定めの種類」を足す契約の変更（メジャー）になる。このPRでは契約を変えない。

## 制度のケース

帰属は照合（T11）の判定で、計算runの結果ではないので、`regime-cases.json`のケースにしない。T03の台帳の場面（`tests/fixtures/ledger/cases/EX-05.json`）は、合成例の説明のための例示の規則（`EX-05-scheduled-pay-date-year`）を使っている。この規則の承認後、その場面で、例示の規則の代わりにこの規則を使えるかをT11が確かめる。例示の規則と同じく支払予定日の年を使うが、版1の適用の年は2025年・2026年だけなので、支払予定日が2027年の明細（EX-05の`pay_503`）には当てはめず、`undetermined`のまま残る（EX-05の「規則が承認された場合（例示）」の2027年の期待値とは違う）。2027年以後は、その年の法令で確かめた新しい版で扱う。
