# 共通の型

[契約の入口](README.md)／次: [記録の型](records.md)

すべての記録で使う型と規則を定める。ID、版、金額・通貨・単位、金額の状態、日付と期間、3つの時間軸（適用期間・把握日・記録日時）、記録の区分、改訂、冪等キー、集計値の形。

## 1. 表記

型の表は「項目・型・意味と制約」の3列で書く。

| 表記 | 意味 |
| --- | --- |
| `Yen` | 日本円の整数（4を参照） |
| `Fact<T>` | 状態付きの値。`T`の値と、4つの状態のどれか（5を参照） |
| `List<T>` | `T`の並び。並びの順序に意味がある場合は項目の説明に書く。空の並びの意味は12の「並びの空の意味」による |
| `Id<T>`、`LineId`、`Ref<T>` | 記録のID、記録の中の行のID、記録への参照（2を参照） |
| `LocalDate`、`YearMonth`、`CalendarYear`、`FiscalYear`、`Instant`、`Period` | 日付と期間（6を参照） |
| `Text` | 文字列。資料の記載や利用者のメモ。意味を解釈せず、そのまま持つ |
| `Decimal` | 10進の数を表す文字列（4を参照） |
| `Minutes`、`Days`、`Count` | 分・日数・件数の0以上の整数（4を参照） |
| `a`・`b`・`c` | 列挙。並べた値のどれか1つ |
| `boolean`、整数 | 真偽値（`true`・`false`）、整数（範囲は項目ごとに書く） |

**型の識別子（1つの規則）:** 1つの項目が2つ以上の型のどれかを持つ場合（「`A`または`B`」、種類ごとの型、複数の種類の記録を指す参照）は、どの型かを、値がない状態（`unknown`・`not-applicable`等）でも決められる識別子で示す。値の形から型を推し量らない。契約の項目は、次のどれかで識別する。

| 項目 | 識別子 |
| --- | --- |
| `Fact<T>` | `state`（4つの状態。5） |
| 複数の種類の記録を指す`Ref`（証憑の紐付けの`target`、照合配分の`from`等）、`MissingInput`・`missing`の`ref` | 参照先の`id`の接頭辞（2。記録の種類ごとに固定） |
| 照合の判断の`value` | `decisionType`（[照合の規則](reconciliation.md)の4） |
| 計算runの`ResultItem`の`value`、`Assumption`の`value` | `valueType`（[計算結果](calculation-results.md)の1） |
| 集計値の`AxisValue` | `axis`（11） |
| 集計値の`measure`（`AggregateKey`） | `kind`（11の「集計のキー」） |
| 集計値の`missing`と`MissingInput`の`field`（`FieldKey`） | `kind`（11の「不足の項目」） |
| `subjectYear`・`Target.year`の年・年度 | `kind`（`calendar`・`fiscal`） |

新しく2つ以上の型を持つ項目を足すときは、識別子を決めてこの表に加える。

**`other`と自由な値をキーにしない（1つの規則）:** 列挙の`other`（「その他」）と、利用者・資料の自由な値（`Text`。表示名、表題、`issuerLabel`、`payerLabel`等）は、次のキーに使わない。`other`は「列挙のどれでもない」ことしか表さず、`other`どうしが同じ種類である保証がないため。自由な値は表記が揺れ、同じものが別の値に、別のものが同じ値になりうるため。

- **足してよいかを決めるキー:** 意味の違う金額を分けて集計する種類のキー（正式通知の`noticeType`、通知の金額の`category`）。`other`の記録・行は、その種類の集計に足さない（[照合の規則](reconciliation.md)の2）。
- **採用の候補を決めるキー:** 年間資料の`documentType`が`other`の資料は、項目の意味が決まらないので、年間の値の採用の候補にしない（同5）。
- **同一性を決めるキー:** 同じ記録・同じ相手かどうかは、IDと、契約で決めた識別の次元で決め、自由な値では決めない（雇用先・発行者は登録したマスタのIDで参照する）。識別の次元に列挙の項目があり、両方が`other`なら4×4の表では一致になるが、ほかの次元（支払者・日付・発行者・年度）と合わせて使い、`other`だけで同じとはしない。

- **契約が決めるキー:** 集計のキーは`AggregateKey`（11）。不足の`field`（集計値の`missing`、計算runの`MissingInput`）は`FieldKey`（11）で、記録の項目は記録の型の表にある項目名、規則で導く不足は派生キーの表の値、計算器の入力は計算器の版ごとの一覧の値だけを使う。比較の`field`（`comparisons`・`explainedComparisons`）は、年間資料の金額の項目名（`AggregateKey`の`annual-value`の`item`と同じ列挙）だけを使う。計算runの`ResultItem`・`Assumption`の`key`は、計算器の版ごとに決めた一覧の値だけを使う（一覧はT15以降で計算器と一緒に定める）。表・一覧にない名前は保存しない。表示の並びの重複を避けるための比較（`unconfirmedItems`の同じ文）はキーではないので、この規則の対象外。

上位の量の内訳として、意味が同じ金額に含まれる`other`（給与明細の`otherEarnings`の分類`other`の行も、総支給額の一部）は、上位の量の中で数える（その分類だけの集計は作らない）。表示と照合の候補の提示には、`other`も自由な値も使ってよい。新しく種類を分けて集計する必要が出たら、列挙に値を足す（READMEの「契約の変更」。`other`を細かく分けるキーを自由な値で作らない）。

**項目の省略:** 表に書いた項目は省略しない。`Fact<T>`の項目に入力がなければ、状態を`unknown`（不明）として持つ。`Fact`でない項目は、必ず値を持つ。「〜の場合だけ」と書いた`Fact`の項目は、その場合でなければ`not-applicable`（対象外）を持つ。`Fact`の項目が許す状態は、12で1か所にまとめる。既定は`known`・`unknown`・`not-stated`の3つで、`not-applicable`は12の「`not-applicable`を許す項目」の表に挙げた項目だけで使える。`known`が必要な場合や、既定より狭い場合は、12の「`known`が必要な項目」の表に書く（各ファイルの説明の「`known`が必要」は、この表と同じ内容）。表の条件を満たさない保存は拒否する。

## 2. IDと参照

### `Id<T>`（記録のID）

- アプリが記録の作成時に割り当てる。生成はdomainに注入するID生成器で行う（T06・T09。試験では決まった値を返す生成器を渡せる）。
- 形式は`<接頭辞>_<本体>`。接頭辞は記録の種類ごとに固定（下の表）。本体は英数字とハイフン（`0-9`、`A-Z`、`a-z`、`-`）の1〜40文字（ULIDやハイフン付きのUUIDv7が入る長さ）。比較は完全一致で、大文字と小文字を区別する。本体の生成方式（ULID、UUIDv7等）はT06で決める。
- 記録の種類をまたいで一意。一度使ったIDは、取消のあとも再利用しない。
- **内容から作らない。** 勤務先・月・日付・金額からIDを作らない。内容を訂正しても、IDは変わらない。
- 合成例では、読みやすいように本体を通し番号にする（`pay_101`等）。番号に意味はない。

| 接頭辞 | 記録 | 接頭辞 | 記録 |
| --- | --- | --- | --- |
| `emp` | 雇用先 | `ntc` | 正式通知 |
| `term` | 雇用条件 | `evf` | 証憑ファイル |
| `acct` | 口座 | `evl` | 証憑の紐付け |
| `pay` | 給与明細 | `alc` | 照合配分 |
| `dep` | 銀行入金 | `dcs` | 照合の判断 |
| `ann` | 年間資料 | `run` | 計算run |
| `fc` | 予測 | `iss` | 発行者 |

### 一意キーにしないもの

次の組は、記録を識別するキーにしない。同じ組の記録が複数あってよい（同じ月の給与と賞与、遡及差額、分割入金、同じ日の同額の別件）。これらは重複候補の提示にだけ使う（[照合の規則](reconciliation.md)の7）。

- 勤務先＋月、勤務先＋支払予定日、勤務先＋明細の種類＋月
- 口座＋入金日＋金額
- 勤務先の表示名（同じ表示名の別の勤務先がありうる。同じ勤務先への再就職は、同じ雇用先と期間ごとの雇用条件で表す）

### `LineId`（行のID）

給与明細のその他の行、予測の行、正式通知の行など、記録の中の要素を指す。形式は英数字の1〜40文字。記録の中で一意。改訂の間で、同じ行には同じ行IDを使う。改訂で消した行の行IDは、その記録の中で再利用しない。

### `Ref<T>`（参照）

| 項目 | 型 | 意味と制約 |
| --- | --- | --- |
| `id` | `Id<T>` | 参照先の記録 |
| `revision` | 1以上の整数、または`current` | `current`は、その参照を読む見方で選ばれた参照先の版を指す。現在の見方では最新の版、時点を指定した見方ではその時点で選ばれる版（7）なので、過去の時点を再現しても、その時点に存在しなかった版には結び付かない。整数は、その版に固定する |
| `line` | `LineId`、または`whole` | `whole`は記録全体。行を指す場合は行ID。どの項目で行を指せるかは、下の「参照先の種類・粒度・次元」の表の`line`の列で決まる（記録全体についての関係は`whole`だけ） |

**`current`と整数の使い分け（1つの規則）:**

- **記録どうしの関係**（照合配分の`from`・`to`、照合の判断の`targets`、証憑の紐付けの`target`、`supersedes`、`duplicateOf`）は、`revision`に`current`だけを使う。関係が確定した時点の版は、関係そのものに整数で固定せず、専用の項目（照合配分の`confirmedAgainst`、`mismatch-explanation`の`explainedComparisons`）で持つ。関係と確定の時点を2か所で持って食い違うことを防ぐため。
- **固定した写し**（計算runの中のすべての参照。[計算結果](calculation-results.md)の1）は、`revision`に整数だけを使う。
- **集計の結果**（集計値の`missing`の`ref`。11）は、`revision`に整数だけを使う。その整数は、集計を計算した見方（7。現在の見方なら最新の版）で選ばれた参照先の版とする。後から改訂されても、出力した結果の参照が別の版に変わらないようにするため。
- **参照先の種類・粒度・次元（1つの規則）:** `Ref`の項目は、下の表の「参照先」に書いた種類の記録だけを指し、`line`には表の「`line`」の列に書いたものだけを使う。違う種類を指す保存と、許さない`line`（記録全体についての関係で行を指す等）の保存は拒否する。記録全体についての関係（差し替え・取消・判断・証憑・採用・入力の写し）は`whole`だけを使い、行を指せるのは表で行を許した項目だけとする。行を指す場合、その行は参照先の版（整数ならその版、`current`なら保存のときの現在の版）になければならない。`current`の参照で、後の改訂で行が消えた場合の扱いは、その項目を使う規則に従う（照合配分は[照合の規則](reconciliation.md)の9）。表に一致が必要な識別の次元を書いた項目は、その次元を13の4×4の表で比べ、結果の扱いを13の「各判定での結果の使い方」の表に従って決める。不一致と未確定で何を拒否するか（保存か、照合配分の確定か）と、拒否しない未確定をどう扱うかは、項目ごとにその表の1行だけで決め、表に行がない項目では、不一致も未確定も保存を拒否する。保存・確定の条件をこの1か所で決めるので、ほかの規則が同じ参照に別の条件を足すことはない（記録の型の10や照合の規則の3は、その行の内容を詳しく書いたもの）。保存のあとの改訂で満たさなくなった参照は、その項目を使う規則（照合配分の使われ方、判断の前提、差し替えの系列等）に従って要確認・要判断になる。
- 契約の`Ref`の項目は、すべて上の3つのどれかに当たり、その項目の説明にどちらを使うかを書く。新しく`Ref`の項目を足すときも、どれに当たるかを決めて説明に書く。

| `Ref`の項目 | 区分 | `revision` | `line` | 参照先（種類と、一致が必要な次元） |
| --- | --- | --- | --- | --- |
| 照合配分の`from`・`to`（[照合の規則](reconciliation.md)の3） | 記録どうしの関係 | `current` | 種類ごとの表（同3）の`from`・`to`の列に書いたもの（予測の行と、`forecast-realization`の`from`の`otherEarnings`の行だけが行） | 種類ごとの表（同3）の`from`・`to`の種類。次元は同3の「識別の次元」 |
| 照合の判断の`targets`（同4） | 記録どうしの関係 | `current` | `whole`だけ | 判断の種類ごとの表（同4）の種類と件数。`annual-adoption`の年間資料は同4の保存の検証 |
| 証憑の紐付けの`target`（[記録の型](records.md)の9） | 記録どうしの関係 | `current` | `whole`だけ（ファイルの中の位置は`locator`で持つ） | 改訂を持つ記録（証憑の紐付けそのものを除く） |
| 給与明細・年間資料・正式通知の`supersedes`（同4・6・8） | 記録どうしの関係 | `current` | `whole`だけ | 同じ種類の記録。次元は同10の「差し替えの識別の次元」 |
| 改訂の共通の形の`duplicateOf`（9） | 記録どうしの関係 | `current` | `whole`だけ | 取り消す記録と同じ種類の記録 |
| 計算runの`inputs.records` | 固定した写し | 整数 | `whole`だけ | 改訂を持つ記録 |
| 計算runの`inputs.allocations`・`inputs.decisions`の要素の`ref` | 固定した写し | 整数 | `whole`だけ | それぞれ照合配分・照合の判断 |
| `AdoptionSnapshot`の`adoptedRef` | 固定した写し | 整数 | `whole`だけ | 年間資料で、`targetYear`がスナップショットの`year`と同じ、範囲が確定していてスナップショットの`payers`と同じ集合（範囲の一部だけにしない）、取消・差し替えされていない（その版で）もの。[照合の規則](reconciliation.md)の5で選ばれた資料と同じ |
| `Assumption`の`ref` | 固定した写し | 整数 | `source`が`forecast`なら予測の行だけ。ほかは`whole`だけ | `source`が`forecast`なら予測。ほかは改訂を持つ記録 |
| `MissingInput`の`ref`、`ResultItem`の`explanationRefs` | 固定した写し | 整数 | `whole`か、参照先のその版にある行 | 改訂を持つ記録 |
| 集計値の`missing`の`ref`（11） | 集計の結果 | 整数（集計を計算した見方で選ばれた版） | `whole`か、参照先のその版にある行（不足が行にある場合。正式通知の`category`が分からない行等） | 改訂を持つ記録 |

参照先が存在しない参照は保存できない（T06・T07で検証する）。

**`current`の解決（すべての見方で1つの規則）:**

- 見方（7の「時点を指定した見方」。現在の見方を含む）で参照先の改訂が1つも選ばれない場合、`current`は**解決できない**。たとえば、把握時点の再現で参照先の改訂の把握日がすべて`unknown`か`D`より後の場合。記録時点の再現では、参照先は参照する改訂より前に保存されている（参照先が存在しない参照は保存できない）ので、解決できない参照は生じない。解決できない参照を、ほかの版（最新の版等）に読み替えない。
- **関係の記録**（照合配分・照合の判断・証憑の紐付け）で、参照のどれかを解決できないものは、その見方では「参照先がこの見方にない」として要確認に出す。照合の残高・予測の残り・帰属・比較・確定の条件の計算には使わない。
- その関係を使うはずだった値は、その見方では決められないものとして扱う（解決できない照合配分は、[照合の規則](reconciliation.md)の9の「使えない関係」の1つで、その規則に従う）。
  - 照合の残高と予測の行の残りは`unknown`にし、集計では`missing`に状態`unknown`で挙げる。
  - 帰属の根拠に使うはずだった明細は、その見方では帰属を`undetermined`とする（候補の年は、5の「分からない値で絞り込まない」によりすべての年）。
  - 比較（年間資料と明細）は`incomplete`とする。
  - 正しい関係を黙って落とした値にはしない。
- **記録の中の参照の項目**（`supersedes`・`duplicateOf`）を解決できない場合も、「関係がない」とはみなさない（5の「分からない値で絞り込まない」。関係がないとみなすと、差し替えの系列が切れて、古い記録と新しい記録を両方数えるおそれがあるため）。
  - `supersedes`: 解決できない参照を含む系列は、その見方では整っていない系列（「未確認の系列」）とし、その系列の見える記録をすべて集計・採用・照合から除き、`conflict`で挙げる。どこまでを1つの系列とするかと、まだ把握していない新しい記録（鎖の最新の側）だけが見えない場合（解決できない参照は生じない）の扱いは、[記録の型](records.md)の10の「時点を指定した見方」に従う。
  - `duplicateOf`: 取り消した記録は、取消のまま集計から除く。その記録を指す`same`の`duplicate-review`の判断は、前提を確かめられないので要確認とする（[照合の規則](reconciliation.md)の4）。
- 現在の見方では、参照先は保存のときに存在し、改訂の記録は削除しない（9）ので、`current`は必ず解決できる（取消された参照先も解決でき、取消の扱いは9による）。

## 4. 金額・通貨・単位

### `Yen`

- 日本円の1円単位の整数。小数を持たない。
- 契約版1では、通貨は日本円だけ。項目ごとに通貨を持たない。外貨や外貨建ての記録は受け付けない（必要になったら契約版を上げる）。出力（T12）では通貨（`JPY`）を明示する。
- 値の範囲は安全な整数（−(2^53−1)〜2^53−1）。集計の途中や結果がこの範囲を超える場合は誤りとして止め、丸めたり浮動小数にしたりしない（ADR-0005、T06）。

### 符号

- 各金額の項目に、「0以上」「正」「符号あり」のどれかを定める（[記録の型](records.md)の表）。
- 控除（税・保険料等）は、控除の項目に0以上の金額として持つ。負の数で表さない。
- **訂正は改訂で表す。** 入力の誤りを、負の金額の記録を足して打ち消さない。
- 「符号あり」の項目は、資料に負の支払・回収・調整が記載されている場合に使う（年末調整の過不足、過払いの回収等）。これは現実の取引であり、入力の誤りの訂正ではない。

### ほかの単位

| 型 | 単位 | 用途 |
| --- | --- | --- |
| `Minutes` | 分（0以上の整数） | 所定労働時間等。時間を小数で持たない |
| `Days` | 日数（0以上の整数） | 出勤日数等 |
| `Count` | 件数（0以上の整数） | ファイルの大きさ（バイト数）、件数 |
| `Decimal` | 10進の文字列（`^-?[0-9]+(\.[0-9]+)?$`、例`"0.1021"`） | 率、丸めの前の値。2進の浮動小数で持たない |

## 5. 金額の状態（`Fact<T>`）

金額をはじめ、分からないことがある項目は`Fact<T>`で持つ。4つの状態を区別する。

| 状態 | 日本語 | 意味 | 例 | 集計での扱い |
| --- | --- | --- | --- | --- |
| `known` | 値あり | 値が分かっている。**0も値**（`known(0)`） | 明細に「住民税 0」と書いてある | 値を使う |
| `unknown` | 不明 | 値がある、またはありうるが、分からない。確かめていない。未入力 | 明細を紛失した。読めない。まだ入力していない | 不足として数える。0として足さない |
| `not-stated` | 記載なし | 資料を確かめたが、その資料に項目の記載がない | 明細に雇用保険の欄がない | 不足として数える（別の資料が要る） |
| `not-applicable` | 対象外 | その項目が当てはまらないと分かっている | 勤務先に通勤手当の制度がない | 集計から除く。不足に数えない |

- 未入力は`unknown`。UIは空欄を0にしない。0を保存するのは、利用者が0を入力・確認した場合だけ。
- `not-stated`は、確かめた資料がある場合にだけ使う。資料がなく、記憶から入力する場合の不明は`unknown`。
- `not-applicable`は、利用者が根拠を持って判断した場合に使う。根拠はメモ（`note`）に書ける。使える項目は12の「`not-applicable`を許す項目」の表に挙げたものだけ（既定では使えない）。
- `known`の値は、項目の型の制約（0以上等）を満たす。
- 状態は金額以外にも使う（`Fact<LocalDate>`、`Fact<Period>`、列挙、参照等）。意味は上の表と同じ。
- **分からない値で絞り込まない（1つの規則）:** 集合を絞り込む判定では、使う値が`unknown`・`not-stated`なら、その値で対象を除外しない。対象は候補・不足・要確認のまま残し、黙って除外しない。また、分からない値を一致の根拠にしない（分からない値どうしを一致とみなさない）。真偽の`Fact`（`Fact<boolean>`。照合配分の`settlesForecastLine`等）の`unknown`・`not-stated`も、`true`としても`false`としても扱わない（`true`の条件に当たらないからといって`false`の扱いにしない）。この規則を使う判定は次のとおりで、どれも規則を言い換えずにここを参照する。
  - 集計の範囲・期間への振り分け（11、[照合の規則](reconciliation.md)の2の「日付不明」）
  - 帰属の候補の年（同8）
  - 正式通知の決定額の採用（同2）
  - 重複の候補（同7）
  - 照合配分の識別の次元（同3。推定の項目である入金の`payerHint`は識別の値ではないので、同3の表の扱いに従う）
  - 期間の重なり（6の「端が分からない期間の扱い」は、この規則を期間の端に当てはめたもの）
- **見込み・推計は状態ではない。** 予測の記録の`known`は「見込みとして入力した値が分かっている」という意味で、実績ではない。実績・見込み・正式通知・推計の区別は、記録の区分（8）で表す。

**標準の表記:** 合成例と、出力（T12）が状態を表すときの基準。

```json
{"state": "known", "value": 0}
{"state": "unknown"}
{"state": "not-stated"}
{"state": "not-applicable", "note": "勤務先に通勤手当の制度がない"}
```

`note`はどの状態にも付けられる（任意）。CSV/JSONの具体的な形はT12で決めるが、状態を値と別に持ち、空の値を0や`known`と解釈しない形にする。出力して取り込み直しても4つの状態と0が区別されたまま保たれること（round trip）を、T12で試験する。

## 6. 日付と期間

| 型 | 形式 | 意味と制約 |
| --- | --- | --- |
| `LocalDate` | `YYYY-MM-DD` | 日本の暦日（Asia/Tokyo）。時刻とタイムゾーンを持たない。資料・通帳に書かれた日付をそのまま持つ |
| `YearMonth` | `YYYY-MM` | 月。予定の月や表示に使う。日を補って`LocalDate`にしない |
| `CalendarYear` | `YYYY` | 暦年（1月1日〜12月31日）。所得の年等 |
| `FiscalYear` | `YYYY` | 年度（`YYYY-04-01`〜翌年の`03-31`）。文中では`FY2027`のように書く。`CalendarYear`と同じ型として扱わない |
| `Instant` | RFC 3339、UTC、ミリ秒まで（`2026-11-02T01:30:00.000Z`） | 時点。記録日時・取込日時・計算日時に使う。表示はAsia/Tokyo。資料の日付には使わない |
| `Period` | `{ start: Fact<LocalDate>, end: Fact<LocalDate> }` | 期間。両端の日を含む。両端が`known`なら`start` ≤ `end` |

- 年に種類があるところ（正式通知の対象年等）は、`{ kind: calendar・fiscal, year: YYYY }`の形で種類を明示する。
- `Period`の`end`が`not-applicable`のときは「終わりの定めがない（継続中）」、`unknown`のときは「終わりがある、または継続中かどうかが分からない」。
- **端が分からない期間の扱い（1つの規則）:** 期間が重なるかどうか、どの年と重なるかを判定するすべての計算（雇用条件の重なり、帰属の候補の年等）では、`start`が`known`でなければ過去へ、`end`が`known`でなければ（`not-applicable`の継続中を含む）未来へ、限りなく開いた期間として扱う。端を推測で埋めず、狭く解釈しない。この規則を使う場所は、規則を言い換えずにここを参照する。期間そのもの（`Fact<Period>`）が`unknown`・`not-stated`の場合は、「期間がない」とはみなさない。5の「分からない値で絞り込まない」に従い、両端とも分からない期間（過去にも未来にも限りなく開いた期間）として扱う。`not-applicable`（期間という概念が当てはまらない）の場合だけ、期間がないとして扱う。
- 和暦は表示だけに使い、データは西暦で持つ（「令和8年分」は`2026`）。
- **日付を推測で補わない。** 明細の「10月分」という記載から、10月1日〜31日の期間を作らない（支給月の表示である場合もある）。記載は文字列としてそのまま持ち、期間は`unknown`または`not-stated`にする。

## 7. 3つの時間軸（適用期間・把握日・記録日時）

改訂を持つ記録は、次の3つを区別して持つ。証憑ファイルと計算runは改訂を持たず、記録日時に当たるもの（取込日時`importedAt`、実行日時`createdAt`）だけを持つ。記録日時は時計の値で、順序には使わない。保存の順序は、すべての保存が持つ保存の連番（`recordedSeq`。下の「保存の順序」）で決める。

| 時間軸 | 型 | 意味 | 決める人 | 変更 |
| --- | --- | --- | --- | --- |
| 適用期間 | 記録の種類ごと（下の表） | 記録の内容が現実に当てはまる期間 | 資料の記載、利用者 | 改訂で変えられる |
| 把握日（`knownOn`） | `Fact<LocalDate>` | 利用者が、その改訂の内容の情報源（資料・通知・説明）を得た日 | 利用者 | 改訂ごとに持つ |
| 記録日時（`recordedAt`） | `Instant` | アプリがその改訂を保存した時点の時計の値。表示と、時刻から保存の連番を求めるためだけに使う | アプリ（注入した時計） | 変えない |

記録の種類ごとの適用期間:

| 記録 | 適用期間として使う項目 |
| --- | --- |
| 雇用条件 | `applicablePeriod` |
| 給与明細 | `workPeriod`（勤務期間） |
| 銀行入金 | なし（`depositDate`の1日の出来事） |
| 年間資料 | `targetYear`（暦年） |
| 予測 | 各行の`workPeriod`と`expectedMonth` |
| 正式通知 | `applicablePeriod`と`subjectYear` |
| 雇用先、口座、証憑、照合配分、照合の判断 | なし（参照先の記録に従う） |
| 計算run | `target` |

給与明細の支払予定日・銀行入金の入金日・税務上の帰属は、適用期間とも別に持つ（[記録の型](records.md)の11）。

### 把握日の決め方

| 改訂の理由（9を参照） | 把握日 |
| --- | --- |
| `create`（新規） | 情報源を得た日（明細を受け取った日、通知を受け取った日、入金を確認した日等）。UIは当日を提案してよいが、利用者が確かめずに保存した場合は`unknown` |
| `correct-input-error`（入力誤りの訂正） | 訂正した改訂の把握日を引き継ぐ（情報源は前から手元にあり、写し誤りを直すだけのため）。ただし、誤っていたのが把握日そのもの（日付の写し誤り）なら、正しい把握日に直してよい。その場合は`changeNote`に書く |
| `new-information`（新しい情報の反映） | 新しい情報源を得た日 |
| `void`（取消）、`unvoid`（取消の取り消し） | 直前の改訂の把握日を引き継ぐ |

- 利用者が新しく入力する把握日（`create`・`new-information`、または把握日の写し誤りを直す`correct-input-error`）は、保存のときの時計の日付（Asia/Tokyo）より後にできない（未来の日付を防ぐ保存の検査）。前の改訂から引き継いだ把握日は、この検査をしない（入力したときに検査済みのため）。
- 記録日時（`recordedAt`）は時計の値で、狂うことがあるので、把握日との大小を不変条件にしない（保存の順序は7の`recordedSeq`で決める）。
- 発行者が資料を作り直した場合（明細の再発行、変更通知）は、改訂ではなく新しい記録にする（[記録の型](records.md)の「資料の差し替え」）。

### 時点を指定した見方

| 見方 | 選ぶ改訂 | 用途 |
| --- | --- | --- |
| 現在 | 各記録の最新の改訂 | 通常の表示・集計・照合 |
| 記録時点の再現（連番`S`） | `recordedSeq` ≤ `S`の改訂のうち、版が最大のもの | 監査、当時の画面の再現 |
| 記録時点の再現（時点`T`） | 下の「時点から連番への対応」で`T`を連番`S(T)`にし、連番`S(T)`の見方と同じにする | 同上（利用者が時刻で指定する場合） |
| 把握時点の再現（日`D`） | `knownOn`が`known`で`D`以下の改訂のうち、版が最大のもの。把握日が`unknown`の改訂は選ばず、該当する記録を「把握日不明」として一覧に出す | 「その日までに分かっていたこと」の確認（後着の通知、資格の判断等） |

**保存の順序:** すべての保存（記録の改訂、証憑ファイル、計算run）は、保存のときにデータベース全体で1つの連番`recordedSeq`（1から始まり、保存がcommitされた順に1ずつ増える整数）を持つ。番号はcommitのときに割り当て、失敗した保存は番号を使わない（抜けがない）。同じ番号は2回使わない。同じ記録の改訂では、版の番号が大きいほど`recordedSeq`も大きい。順序は`recordedSeq`だけで決まり、時計の値（`recordedAt`等）が巻き戻っても、同じ値が並んでも、順序は変わらない。

**時点から連番への対応:** 時点`T`の連番`S(T)`は、`recordedSeq`が1から`s`までのすべての保存の記録日時が`T`以下であるような、最大の`s`とする（そのような保存がなければ0）。時計が巻き戻って記録日時の順が連番の順と食い違っても、`T`より後の時刻を持つ保存が現れた番号より後は含めない。そのため、連番の順は崩れない（ある保存を含めるなら、それより前の保存もすべて含める）。ただし、時点からの対応は記録日時に頼るので、時計が狂っていた保存は、その記録日時のとおりに扱われる。同じ時刻の保存が複数ある場合や、時計が狂っていた場合も、連番で指定すれば、どの状態も一意に再現できる（例はEX-04(a)）。

照合配分・照合の判断・証憑の紐付けも、同じ見方で改訂を選び、参照は2の「`current`の解決」に従って解決する（その時点で把握・記録されていなかった配分や判断は使わない）。入力誤りの訂正は把握日を引き継ぐので、把握時点の再現では訂正後の値が使われる（誤りは利用者の入力のもので、現実の情報ではないため）。計算runは入力の版を固定するので、これらの見方に影響されない（[計算結果](calculation-results.md)）。

## 8. 記録の区分

| 区分 | 記録 | 意味 |
| --- | --- | --- |
| 実績 | 給与明細、銀行入金、年間資料 | 起きた支給・入金と、その資料 |
| 見込み | 予測 | 利用者の見込み・仮定 |
| 正式通知 | 正式通知 | 行政・保険者・勤務先等による決定・通知 |
| 推計 | 計算run | アプリの計算 |
| 補助 | 雇用先、雇用条件、口座、発行者、証憑、照合配分、照合の判断 | 金額の集計の採用元にならない |

- 区分は記録の種類で決まり、利用者が変えない。
- 見込みを実績に書き換えない。実績が届いたら、実績の記録を作り、照合配分で予測と結ぶ（[照合の規則](reconciliation.md)の6）。
- 推計を正式通知として保存しない。正式通知の値を計算runの結果として保存しない。比べるだけ。

## 9. 記録と改訂の共通の形

証憑ファイルと計算runを除く記録は、改訂の並びとして持つ。改訂は記録全体の内容を持つ（差分ではない）。

| 項目 | 型 | 意味と制約 |
| --- | --- | --- |
| `id` | `Id<T>` | 記録のID。改訂の間で変わらない |
| `recordType` | 列挙（下の表） | 記録の種類。改訂の間で変わらない |
| `revision` | 1以上の整数 | 記録の版。1から始まり、改訂ごとに1増える |
| `status` | `active`・`voided` | 有効・取消 |
| `reason` | `create`・`correct-input-error`・`new-information`・`void`・`unvoid` | 改訂の理由 |
| `recordedAt` | `Instant` | 記録日時（時計の値。順序には使わない） |
| `recordedSeq` | 1以上の整数 | 保存の連番。データベース全体で一意で、commitの順に1ずつ増える（7の「保存の順序」） |
| `knownOn` | `Fact<LocalDate>` | 把握日（7を参照） |
| `changeNote` | `Fact<Text>` | 改訂の理由のメモ |
| `duplicateOf` | `Fact<Ref<T>>` | `void`の改訂で、二重登録として取り消した場合だけ、残す方の記録（その場合は`known`が必要）。ほかの改訂では`not-applicable`（下の改訂のモデルの表）。`revision`は`current`、`line`は`whole`だけ（記録どうしの関係。2の「参照先の種類・粒度・次元」）。指せるのは、自分以外の、保存のときに有効な記録（下の「検査の対象は有効な記録だけ」）だけ（取消した記録どうしで指し合い、どちらも残らない状態を作らないため）。保存のあとで残す方が取消された場合は、どちらの記録も集計に戻さず、この取消を「残す方がない二重登録」として要確認に出す |
| `entryChannel` | `manual`・`import` | 手入力か取込か |
| `writeRequestId` | `Text` | 保存の要求の冪等キー（10を参照） |
| `importKey` | `Fact<{ source: Text, key: Text }>` | 取込の冪等キー。取込の場合だけ（10を参照）。`source`は取込元の識別子、`key`はその取込元の中での取引のキー |
| `body` | 記録の種類ごとの内容 | [記録の型](records.md)、[照合の規則](reconciliation.md) |

`recordType`の値: `employer`、`employment-term`、`account`、`issuer`、`payslip`、`bank-deposit`、`annual-document`、`forecast`、`official-notice`、`evidence-link`、`allocation`、`decision`。

**改訂のモデル:** 記録の状態は、最新の改訂の`status`・`duplicateOf`・`body`で決まる。改訂の理由ごとに、使える直前の状態と、改訂後の状態・項目を次の表のとおり定める。表にない組合せの保存は拒否する。

| 理由 | 意味 | 直前の`status` | 改訂後の`status` | `duplicateOf` | `body` |
| --- | --- | --- | --- | --- | --- |
| `create` | 新規（版1だけ） | （なし） | `active` | `not-applicable` | 新しく書く |
| `correct-input-error` | 入力誤りの訂正。同じ情報源からの写し誤り・入力漏れ（`unknown`だった項目を同じ資料から埋める場合を含む）を直す | `active` | `active` | `not-applicable` | 変えてよい |
| `new-information` | 新しい情報源による内容の変更（予測の見直し、問い合わせの回答で分かった値等） | `active` | `active` | `not-applicable` | 変えてよい |
| `void` | 取消。記録そのものが誤り（二重登録、自分の口座でない取引の取込等、存在しない取引・資料の記録） | `active` | `voided` | 二重登録なら残す方の記録（`known`）、それ以外は`not-applicable` | 直前の改訂と同じ（変えない） |
| `unvoid` | 取消の取り消し | `voided` | `active` | `not-applicable` | 直前の改訂と同じ（取消の前の内容のまま） |

- **取消と取消の取り消しは、`status`と`duplicateOf`だけを表のとおりに変える。** `body`（金額、参照、`supersedes`等）は直前の改訂と同じ値にし、違えば保存を拒否する。`duplicateOf`は記録の内容ではなく、取消の理由を表す改訂の項目なので、取消で設定し、取消の取り消しで`not-applicable`に戻す。内容（`body`）を変えるのは`correct-input-error`と`new-information`だけで、把握日の規則（7）もそれに従う。
- 改訂ごとに持つ付帯の項目（`recordedAt`・`recordedSeq`・`knownOn`・`changeNote`・`writeRequestId`）は、どの理由の改訂でも、その改訂の値を持つ（`knownOn`は7の規則に従う）。
- 取消した記録に続けられる改訂は`unvoid`だけ。取消した記録の内容を直すには、先に取消を取り消す。
- **保存の検査:** どの改訂の保存（新規・訂正・新しい情報・取消・取消の取り消し）も、記録の種類ごとに定めた保存の検査（差し替えの系列、照合配分の確定の条件、雇用条件の期間の重なり、照合の判断の検証、12の`known`が必要な項目等）を、保存したあとの状態に対して行い、満たさなければ拒否する。
- **保存の検査をすり抜けたデータ（1つの規則）:** 古いデータの復元・取込・移行等で、保存の検査（確定の条件、12の`known`が必要な項目、並びの一意のキー、参照先の種類・粒度・次元、差し替えの系列、マスタの不変条件、計算runの形・閉包・履歴等）を通らずに保存されている記録・関係・runがありうる。導く判定（集計・照合・採用・帰属・比較・runの読み方）のたびに、保存の検査と同じ条件で確かめ、満たさないものを黙って有効として使わない。
  - 照合配分は「要確認（古いデータ）」で、使えない関係にする（[照合の規則](reconciliation.md)の9）。照合の判断は、前提が崩れたものとして扱う（同4）。差し替えの系列は整っていない系列にする（[記録の型](records.md)の10の5）。
  - そのほかの記録は、その記録を使う集計を`incomplete`にし、`missing`に状態`conflict`で挙げる（黙って数えない・黙って落とさない）。有効なマスタに解決できない参照（マスタの不変条件を満たさない参照）は、その参照の値を`unknown`として扱う（5の「分からない値で絞り込まない」）。
  - 計算runは、結果を使わず「要確認（古いデータ）」として表示する（runは不変なので直さず、新しいrunを作る）。
  - 分からない値を`false`・0・対象外として扱って、条件を満たしたことにしない。
- **検査の対象は有効な記録だけ（1つの規則）:** 一意性・重なり・食い違い・上限を調べる検査と判定（雇用条件の期間の重なり、照合配分の確定の条件、重複の候補、正式通知の重複、年間資料の採用の候補等）は、**有効な記録**だけを対象にする。有効な記録とは、最新の改訂が`active`で、差し替えの系列の現在の記録であるもの（[記録の型](records.md)の10。差し替えを持たない種類では、最新の改訂が`active`であるもの）。差し替えの系列と現在の記録は、取消していない記録（最新の改訂が`active`）だけから作る（記録の型の10の1〜4）ので、この定義は循環しない。取消した記録や差し替え済みの記録は、存在しない取引・古い資料として扱い、検査を妨げない。取消・取消の取り消しも保存なので、この検査をやり直す。取消の取り消しで、有効な記録どうしの重なりや上限の超過が生じる場合は、その取消の取り消しを拒否する。各検査は、この規則を言い換えずにここを参照する。
- **マスタの取消と二重登録（1つの規則）:** 雇用先（`employer`）・口座（`account`）・発行者（`issuer`）を**マスタ**と呼ぶ。マスタは、ほかの記録から`Ref`ではなく`Id`で参照される（雇用条件・給与明細の`employerId`、年間資料の`payerEmployerId`と他の支払者の行の`payerEmployerId`、銀行入金の`accountId`・`payerHint`、予測の`employerId`・`accountId`、正式通知の`issuerId`、照合の判断の`scope.payers`）。取消できるマスタのすべてに、次の1つの規則を当てはめる。
  - **正規のID:** マスタのIDは、そのマスタから二重登録の取消の`duplicateOf`をたどり、最初に着いた有効なマスタのIDに解決する（取消していないマスタは、それ自身が正規のID）。`duplicateOf`は自分以外の、保存のときに有効な記録だけを指し（上の`duplicateOf`の行）、1つの記録は最新の改訂の`duplicateOf`を1つだけ持つので、たどり方は1通りで、循環も分岐もない。
  - **不変条件:** 有効な記録のマスタへの参照（`known`の値）は、つねに有効なマスタに解決できる。これを壊す保存は拒否する。
    - 二重登録でない取消（`duplicateOf`が`not-applicable`）は、そのマスタに解決される参照（直接の参照と、二重登録の取消をたどってそのマスタに着く参照）を持つ有効な記録が1件でもあれば拒否する。先に参照している記録を直す（`correct-input-error`で別のマスタに付け替える、または記録そのものを取り消す）。
    - 二重登録の取消（`duplicateOf`が`known`）は、参照があっても許す。参照は`duplicateOf`の先の正規のIDに解決される。
    - 記録の保存（新規・改訂・取消の取り消し）で、マスタへの参照が有効なマスタに解決できなくなるもの（二重登録でない取消をしたマスタを指す等）は拒否する。二重登録として取消したマスタのIDを指す保存は許し、正規のIDに解決する（UIは正規のIDを提案する）。
  - **比べる・まとめるときは正規のIDで:** 集計の`scope`、照合配分と差し替えの識別の次元、重複の候補、年間資料の範囲と採用、照合の判断の`scope`等で、マスタのIDを比べる・まとめるときは、すべて正規のIDに解決してから行う（13の4×4の表も、解決したIDで比べる）。記録の`Id`の値は書き換えない（参照を自動で付け替えない）。
  - **取消の取り消し:** 二重登録として取消したマスタの取消を取り消すと、そのマスタは有効に戻り、それを指す参照はそれ自身に解決する（二重登録ではなかったと分かった場合）。
  - **正規のIDが変わる保存:** マスタの二重登録の取消（`duplicateOf`を付ける。二重登録の鎖を延ばす場合を含む）と、その取消の取り消し（`duplicateOf`を外す）は、そのマスタと、それに解決されていたマスタの正規のIDを変える。二重登録でない取消と、その取消の取り消しは、参照がある間は上の不変条件で拒否・制限されるので、有効な記録の参照の解決を変えない。正規のIDが変わっても、参照している記録の版は変わらないので、下流の確定済みの関係（照合配分・照合の判断・差し替えの系列）は、使った正規のIDを保存の時点と現在とで比べて確かめ直す（[照合の規則](reconciliation.md)の9の「確かめ直しの条件」）。正規のIDが変わる保存そのものは拒否しない。
  - **見方:** 二重登録は利用者の入力の誤りなので、現在の見方と把握時点の再現では、各マスタの最新の改訂で解決する（7の、入力誤りの訂正を把握時点の再現でも使うのと同じ考え方）。記録時点の再現（連番`S`）では、連番`S`までの改訂で解決する。
  - 計算runは固定した写しなので、この規則で書き換えない（`AdoptionSnapshot`の`payers`等は、実行したときのIDのまま）。
  - 例はEX-03の「雇用先の二重登録」。

`correct-input-error`と`void`の境界: 取引・資料は存在し、勤務先・口座・金額・日付などの写し方だけを誤った場合は、`correct-input-error`で直す（勤務先や口座の取り違えを含む）。記録に当たる取引・資料が存在しない場合は`void`にする。

規則:

- **改訂の順序:** 同じ記録の改訂の順序は版の番号（`revision`）で決まり、記録をまたぐ保存の順序は`recordedSeq`で決まる（7の「保存の順序」）。どちらも時刻では決めない。`recordedAt`は時計の値をそのまま持ち、巻き戻っても直さない。
- **改訂は追記だけ。** 前の改訂を変更・削除しない。記録を物理的に削除する操作は、契約版1では定めない。
- **古い版での上書きを拒否する。** 改訂の保存は、基にした版を指定する。現在の版と違えば保存せず、競合を知らせる（T07・T09）。
- 取消した記録（最新の改訂が`voided`）は、集計・照合・重複候補から除く。履歴には残す。
- 取消した記録を参照する照合配分・照合の判断は、無効として「要確認」に出す。ただし、二重登録として取り消した記録を指す`same`の`duplicate-review`の判断は有効のまま（[照合の規則](reconciliation.md)の7・9）。
- 改訂で変えられないもの: `id`、`recordType`、`entryChannel`、`importKey`。

**証憑ファイルと計算run**は、一度だけ書き、改訂を持たない（[記録の型](records.md)の証憑、[計算結果](calculation-results.md)）。

## 10. 冪等キー（再送・再取込）

保存の再送と、同じ内容の別件を分けて扱う。

| キー | 作る人 | 意味 | 同じキーが来たとき |
| --- | --- | --- | --- |
| `writeRequestId` | 画面・APIが、保存の操作ごとに作る | 1回の保存の操作 | 新しい記録・改訂を作らず、最初の結果を返す |
| `importKey` | 取込処理が、取込元ごとに作る | 取込元（`source`）の中の1件の取引（`key`） | 同じ記録の種類で、`source`と`key`の組が同じ記録があれば作らない |

- `writeRequestId`は内容から作らない。同じ内容でも、別の操作なら別の記録として保存できる（同じ日・同じ金額の別件）。
- 同じ`writeRequestId`で内容が違う要求が来た場合は、誤りとして拒否する（最初の結果を返さず、新しい記録・改訂も作らない）。
- `importKey`は、取込元の識別子（`source`）と、取込元の中での取引のキー（`key`）の組として保存する。一意性は`recordType`・`source`・`key`の組で判定し、別の取込元で同じ`key`が使われても、別の取引として扱う。`key`は、取込元が持つ取引の識別子から作る。`source`の決め方（口座ごとの明細の形式等）はT09で決める。取込元が識別子を持たない場合の作り方はT09で決める。その場合も、同じ日・同じ金額の別の取引を1件にまとめない方式にする。
- 金額と日付が同じかどうか（同額判定）は冪等キーと別に扱い、重複候補の提示にだけ使う（[照合の規則](reconciliation.md)の7）。

## 11. 集計値の形

集計（合計）は、次の形で返す。集計の種類ごとの採用元と日付の軸は、[照合の規則](reconciliation.md)の2で定める。

| 項目 | 型 | 意味 |
| --- | --- | --- |
| `measure` | `AggregateKey` | 何の集計か（下の「集計のキー」）。自由な文字列にしない |
| `axis` | `deposit-date`・`scheduled-pay-date`・`expected-month`・`income-year`・`subject-year` | 集計に使った日付の軸（`subject-year`は正式通知の対象の年・年度） |
| `scope` | `{ employerIds: List<Id<Employer>>, accountIds: List<Id<Account>>, from: AxisValue, to: AxisValue }` | 対象の勤務先・口座（空なら限定しない）と、軸の上の範囲。`from`・`to`の型は軸で決まり（下の表）、両端を含み、`from` ≤ `to` |
| `state` | `complete`・`incomplete`・`not-applicable`・`no-records` | 集計の状態（下の表） |
| `knownSum` | `Yen` | 値ありの項目の合計 |
| `missing` | `List<{ ref: Ref, field: FieldKey, state: MissingState }>` | 不足の一覧。`ref`の`revision`は整数で、集計を計算した見方で選ばれた版（2の「`current`と整数の使い分け」）。`undetermined`は所得の年の帰属が決まらない明細（[照合の規則](reconciliation.md)の8）、`conflict`は根拠や記録が食い違って決められないもの（帰属の根拠の食い違い、重複の疑いのある正式通知、整っていない差し替えの系列。同2、[記録の型](records.md)の10）、`adoption-needed`は年間の値の採用が要判断の支払者、`partial-scope`は`scope`が採用した年間資料の範囲の一部だけを含む場合のその資料（同5） |
| `excludedCount` | `Count` | 対象外・取消・差し替え済みで除いた件数 |
| `coverage` | `Fact<annual-document・entered-records-only>` | 所得の年の軸（`income-year`）の年間の値で、`knownSum`の元が採用した年間資料の値か、入力済みの記録の合計か（下の「coverageの決め方」）。ほかの軸の集計と、範囲のどの支払者の値も足せない場合（すべて要判断等）は`not-applicable` |

**集計のキー（`AggregateKey`）:** `kind`で型が決まる、判別できる和の型。修飾子はすべて必須で、値は表に書いた列挙だけ（自由な文字列にしない。1の「`other`と自由な値をキーにしない」）。`kind`ごとに、採用元（[照合の規則](reconciliation.md)の2）、日付の軸、`scope`で使ってよい次元が決まる。

| `kind` | 修飾子 | 採用元 | `axis` | 許す`scope`の次元 |
| --- | --- | --- | --- | --- |
| `deposit-amount` | なし | 銀行入金の`amount` | `deposit-date` | `accountIds` |
| `payslip-item` | `item`: 給与明細の金額の項目名（`grossPay`・`taxablePay`・`nonTaxablePay`・`commutingAllowance`・`incomeTax`・`residentTax`・`healthInsurance`・`nursingCareInsurance`・`pensionInsurance`・`employmentInsurance`・`yearEndAdjustment`・`totalDeductions`・`netPay`・`bankTransferAmount`） | 給与明細の該当項目 | `scheduled-pay-date` | `employerIds` |
| `payslip-by-income-year` | `item`: 上と同じ給与明細の金額の項目名 | 帰属の年が決まった給与明細の該当項目 | `income-year` | `employerIds` |
| `annual-value` | `item`: 年間資料の金額の項目名（`paymentAmount`・`incomeAfterEmploymentDeduction`・`totalIncomeDeductions`・`withholdingTax`・`socialInsurancePremiums`） | 採用した年間資料、または明細から示す値（同5） | `income-year` | `employerIds` |
| `forecast-remaining` | `forecastMeasure`: `gross-pay`・`net-pay`・`bank-transfer`・`deposit-amount` | 予測の行の残り（同6） | `expected-month` | `gross-pay`・`net-pay`・`bank-transfer`は`employerIds`。`deposit-amount`は`employerIds`と`accountIds` |
| `notice-determination` | `noticeType`: 正式通知の`noticeType`の列挙（`other`の扱いは同2）。`category`: `annual-total`だけ | 正式通知の決定額 | `subject-year` | なし（期間だけ） |

- 表にない`kind`・修飾子の値、`kind`と合わない`axis`の集計の要求は拒否する。
- **許さない`scope`の次元:** 許す次元以外の次元に空でない値を指定した要求は、黙って無視せず拒否する（例: `deposit-amount`に`employerIds`を指定する要求。入金の支払者は推定の`payerHint`しかなく、それで絞り込まないため）。許す次元が空の並びなら「限定しない」。
- `kind`と修飾子がすべて同じなら同じ集計とする。ファイルの文字列の表記（CSV/JSON）はT12が決めるが、この構造と1対1にする。
- 新しい集計を足すときは、この表に行を足す（READMEの「契約の変更」。列挙に値を足すのでメジャーを上げる）。

`AxisValue`（軸の上の値）は軸ごとに次の型を使う。`from`と`to`は同じ型で、両端を含む。順序は暦の順で、`subject-year`では`from`と`to`の`kind`が同じでなければならない（暦年と年度を1つの範囲にしない）。

| 軸 | `AxisValue`の型 | 例（2026年9月の1か月） |
| --- | --- | --- |
| `deposit-date`・`scheduled-pay-date` | `LocalDate` | `from` 2026-09-01、`to` 2026-09-30 |
| `expected-month` | `YearMonth` | `from` 2026-09、`to` 2026-09 |
| `income-year` | `CalendarYear` | （年単位）`from` 2026、`to` 2026 |
| `subject-year` | `{ kind: calendar・fiscal, year: YYYY }` | （年度単位）`from` FY2026、`to` FY2026 |

**coverageの決め方（1つの規則）:** 所得の年の軸の年間の値では、範囲の各支払者を、選択（[照合の規則](reconciliation.md)の5）によって次の3つに分ける。1つの集計値は1つの`coverage`だけを持ち、`coverage`は`knownSum`の元で決まる。

| 支払者の分け方 | 当てはまる支払者 | 集計値での扱い |
| --- | --- | --- |
| 年間資料 | 選択が年間資料で、その資料の範囲全体が集計の`scope`に入る | `coverage` `annual-document`の集計値の`knownSum`に、これらの支払者が選んだ年間資料を資料のIDで重複を除いた集合にして、各資料の値を1回だけ足す（範囲がA・Cの資料は、AとCの両方に選ばれても1回。[照合の規則](reconciliation.md)の5、下の「1回だけ数える」） |
| 入力済みの記録 | 選択が`entered-payslips`・年間資料なし | `coverage` `entered-records-only`の集計値の`knownSum`に、帰属した明細の値を足す |
| 値を足せない | 選択が要判断（`adoption-needed`）、選択が年間資料でも範囲の一部だけが`scope`に入る（`partial-scope`）、または選択が入力済みの記録で、その項目の比較の対応表がまだない（`rule-pending`） | どの`coverage`にも入れず、`knownSum`に足さない。`missing`に`adoption-needed`・`partial-scope`・`rule-pending`で挙げる |

- 年間資料と入力済みの記録の支払者が混ざる場合は、`coverage`ごとに分けた集計値の並びを返し、全体の合計は返さない（年間資料の値と、入力済みの明細の合計を、同じものとして足さないため）。どちらか一方だけなら、集計値は1つ。
- 値を足せない支払者があれば、その`missing`の行を、返すすべての集計値に挙げる（どの`coverage`に入るはずだったかが分からないため）。そのため、返すすべての集計値は`incomplete`になり、分かっている分（`knownSum`）とその元（`coverage`）は保たれる。
- 範囲のすべての支払者が値を足せない場合は、`coverage` `not-applicable`の集計値を1つ返す（`knownSum`は0で、`incomplete`。0円とは表示しない）。
- 例はEX-06(b)の「他の支払者の分を確かめていない場合」（勤務先Cの年間資料の値だけが分かり、勤務先Aが要判断）。

`MissingState`（不足の状態）は次の7つだけ。どの文書で「要確認」「要判断」として集計から外すものも、このどれかで`missing`に挙げ、黙って少なく数えない。計算runの`MissingInput.state`も同じ6つを使う（[計算結果](calculation-results.md)）。

| 状態 | 使う場面 |
| --- | --- |
| `unknown` | 項目が不明。日付の軸に使う日付が不明（「日付不明」。[照合の規則](reconciliation.md)の2）。正式通知の具体的な種類が分からない（`noticeType`が`other`。同2） |
| `not-stated` | 項目が資料に記載なし。日付の軸に使う日付が記載なし |
| `undetermined` | 所得の年の帰属の根拠がない明細（同8） |
| `conflict` | 根拠や記録が食い違って決められないもの: 帰属の根拠の食い違い（同8）、重複の疑いのある正式通知（同2）、整っていない差し替えの系列（[記録の型](records.md)の10） |
| `adoption-needed` | 年間の値の採用が要判断の支払者（[照合の規則](reconciliation.md)の5） |
| `partial-scope` | `scope`が、採用した年間資料の範囲の一部だけを含む場合のその資料（同5） |
| `rule-pending` | 値を導く規則がまだない（T14が承認する前の、比較の対応表がない年間資料の項目を、明細から示す場合等。同5） |

**不足の項目（`FieldKey`）:** 集計値の`missing`と計算runの`MissingInput`の`field`は、`kind`で判別する次の型にする（自由な文字列にしない）。

| `kind` | 値 | 使う場面 |
| --- | --- | --- |
| `record-item` | `name`: 参照先の記録の型の表にある項目名（並びの行の項目は`並び名.項目名`。例 `scheduledPayDate`、`amounts.category`） | 記録の項目そのものが不足（`unknown`・`not-stated`等） |
| `derived` | `key`: 下の派生キーの表の値 | 記録の項目ではなく、規則で導く値が決まらない |
| `calculator-input` | `key`: 計算器の版ごとに決めた入力の一覧の値（計算runの`MissingInput`だけ） | 計算器が必要とする入力がない・決まらない |

派生キー（`derived`の`key`。この表だけで決める）:

| `key` | 決まらない値 | `ref`が指すもの | 状態（`MissingState`） | 定める場所 |
| --- | --- | --- | --- | --- |
| `income-year` | 給与明細の所得の年の帰属 | 給与明細 | `undetermined`・`conflict` | [照合の規則](reconciliation.md)の8 |
| `annual-adoption` | 支払者の年間の値の採用 | 雇用先 | `adoption-needed` | 同5 |
| `annual-scope` | 年間資料の範囲の一部だけが集計の`scope`に入る | 年間資料 | `partial-scope` | 同5 |
| `annual-mapping` | 明細から示す年間の値（比較の対応表がまだない項目） | 雇用先（支払者） | `rule-pending` | 同5 |
| `notice-duplicate` | 同じ種類・同じ年度の正式通知が2件以上ある | 正式通知 | `conflict` | 同2 |
| `supersede-series` | 整っていない差し替えの系列 | 系列の記録 | `conflict` | [記録の型](records.md)の10 |
| `forecast-remaining` | 予測の行の残り（使えない関係・予測の金額の不明） | 予測（行を指す） | `unknown` | 照合の規則の6・9 |
| `unreconciled-amount` | 照合の残高（使えない関係） | 銀行入金・給与明細 | `unknown` | 同3・9 |
| `save-check` | 保存の検査をすり抜けたデータで、使えない記録 | その記録 | `conflict` | 9の「保存の検査をすり抜けたデータ」 |

- 派生キーは、どれも`ref`を必要とする。`ref`のない不足は、計算runの`MissingInput`の`calculator-input`だけで表す（`MissingInput.ref`を`not-applicable`にできるのは、`field`の`kind`が`calculator-input`の場合だけ）。集計値の`missing`の`ref`は必ずある。
- 新しく導く不足を足すときは、この表に行を足す（READMEの「契約の変更」）。表にない`key`は保存しない。

`missing`の1行は（`ref`, `field`）の組ごとに1つで、同じ組に2つ以上の原因が当てはまる場合は、次の優先順で1つの状態にする: `conflict` > `adoption-needed` > `partial-scope` > `rule-pending` > `undetermined` > `not-stated` > `unknown`（13の「状態の決め方」）。

集計の状態は、次の表を**上から順に**調べ、最初に当てはまったものに決める（すべての場合にちょうど1つに決まる。13の「状態の決め方」）。「対象の記録」は、集計の採用元として範囲・期間に入る有効な記録（9）で、`missing`に挙げたもの（帰属未判定の明細、日付不明の記録等）は含まない。

| 順 | 状態 | 条件 | 表示の例 |
| --- | --- | --- | --- |
| 1 | `incomplete` | `missing`が1件以上ある（対象の記録が0件でも） | 「入力済み1,500円（不明1件）」。`known`が1件もなければ「不明（記載なし2件）」のように不足だけを示す。`knownSum`を合計として表示しない |
| 2 | `no-records` | `missing`がなく、対象の記録が0件 | 「記録なし」。0円と表示しない |
| 3 | `not-applicable` | `missing`がなく、対象の記録が1件以上あり、その項目がすべて`not-applicable` | 「対象外」 |
| 4 | `complete` | `missing`がなく、対象の記録が1件以上あり、`known`の項目が1件以上ある | 「230,000円」 |

- `coverage`が`entered-records-only`の合計は、その期間の全体の合計とは限らない（入力していない明細がありうる）。年間の合計として扱えるのは、採用した年間資料の値だけ（[照合の規則](reconciliation.md)の5）。
- 計算runの結果（推計）は、この形で返さない。runごとの結果をそのまま示し、runどうしを足さない（[照合の規則](reconciliation.md)の2）。
- 集計と照合の結果は、記録の入力順・保存順に依存しない。並べる順序が必要な場合は、日付の軸の値、次にIDの文字列の順で決める。
- **除くと0を分ける（1つの規則）:** 集計で「除く」（対象にしない）と「0として数える」（対象にあって値が0）を分ける。除くのは、存在しない・使わない記録（取消した記録、差し替え済みの記録、使えない関係で決まらない値は`missing`へ）と、別の集計の記録。0として数えるのは、対象にあって値が`known`の0の記録（記載どおりの0円、消し込んだ予測の行の残り、取り下げた予測の行の残り）。対象の記録がすべて除かれれば`no-records`（不足があれば`incomplete`）で、0円と表示しない。0として数えた記録があれば、合計は`complete`の0円になりうる。例はEX-07(b)の「取り下げた場合」。
- **1回だけ数える（1つの規則）:** 集計は、採用元の記録ごとに1回だけ足す（所得の年の年間の値では、採用した年間資料ごとに1回）。多対多・多対一の関係で同じ記録に複数の道筋で着いても、重ねて足さない。範囲の複数の支払者が同じ年間資料を選ぶ場合（範囲がA・Cの資料をAとCが選ぶ）、照合配分で複数の相手と結ばれた記録（分割入金・合算入金、複数の予測の行を実績化した明細）、`scope`の複数のIDが同じ正規のIDに解決される場合（9の「マスタの取消と二重登録」）が当たる。

## 12. `known`が必要な項目

**既定（すべての`Fact`の項目）:** 許す状態は`known`・`unknown`・`not-stated`の3つ。`not-applicable`は、下の「`not-applicable`を許す項目」の表に挙げた項目と条件だけで使える（挙げていない項目に`not-applicable`を保存しない）。既定より狭くする場合（`known`だけ、`known`と`unknown`だけ等）は、次の「`known`が必要な項目」の表に書く。2つの表と既定で、契約のすべての`Fact`の項目の許す状態が決まる。

**`known`が必要な項目（既定より狭い項目）:** 記録の種類と状態ごとに、`known`が必要な項目と許す状態を1か所にまとめたもの。各ファイルの説明に書いた「`known`が必要」は、この表と同じ内容を指す（食い違えばこの表を正とし、気づいた作業で直す）。保存のときに満たさなければ拒否する（9の保存の検査）。

| 記録・項目 | 条件 | 許す状態 |
| --- | --- | --- |
| 改訂の共通の形の`duplicateOf` | `void`の改訂で、二重登録として取り消す | `known` |
| 同 | それ以外の改訂 | `not-applicable` |
| 改訂の共通の形の`importKey` | `entryChannel`が`import` | `known` |
| 同 | `entryChannel`が`manual` | `not-applicable` |
| 給与明細・年間資料・正式通知の`supersedes` | いつでも | `known`（発行者が作り直した資料で、前の記録を指す）か`not-applicable`（作り直しでない、または前の資料を記録していない）。`unknown`は使わない。作り直しだと分かっていて前の記録が分からなければ、前の記録を確かめてから保存する |
| 給与明細の`scheduledPayDate` | いつでも | `known`・`unknown`・`not-stated`（集計の軸に使う日付なので`not-applicable`は使わない。分からない場合は11の`MissingState`で不足として挙げられる） |
| 銀行入金の`depositDate`・`amount` | いつでも | `known`・`unknown`・`not-stated`（`not-applicable`は使わない） |
| 正式通知の`subjectYear` | 下の「`not-applicable`を許す項目」の表の条件に当たらない場合（`amounts`が`unknown`の場合を含む） | `known`・`unknown`・`not-stated`（決定額の集計の軸に使うので`not-applicable`は使わない） |
| 給与明細の`otherEarnings`・`otherDeductions`、正式通知の`amounts`・`installments`・`statusDates` | いつでも | `known`か`unknown`だけ（下の「並びの空の意味」。資料から写す並び） |
| 年間資料の`includedOtherPayers` | いつでも | `known`か`unknown`（`unknown`の資料は範囲が確定しない。[照合の規則](reconciliation.md)の5） |
| 照合配分の`amount` | `transfer-to-deposit`・`forecast-realization`を`confirmed`にする（消し込む場合も） | `known`（正） |
| 同 | `annual-coverage` | `not-applicable` |
| 確定の不変条件の上限に使う実績の金額: `forecast-realization`の「実績の該当の金額」（[照合の規則](reconciliation.md)の3。`grossPay`・`netPay`・`bankTransferAmount`・入金の`amount`）と、実績の行を指す場合はその行の`amount` | その実績から`forecast-realization`を`confirmed`にする | `known`（`known`でなければ確定しない。先に実績の記録を訂正するか、予測の行を取り下げる） |
| 銀行入金の`amount` | その入金への`transfer-to-deposit`、またはその入金からの`forecast-realization`を`confirmed`にする | `known`（入金の側の上限に使う） |
| 給与明細の`bankTransferAmount` | `transfer-to-deposit`を`confirmed`にする | `known`、`unknown`、`not-stated`を許す。`known`なら明細の側の上限に使う。`unknown`・`not-stated`なら明細の側の上限はなく、入金の側の上限（入金の`amount`は確定のときに`known`）だけで過剰配分を防ぐ。配分の合計を振込額として扱わない。`not-applicable`（振込がない明細。現金払い等）なら確定しない |
| 照合配分の`settlesForecastLine` | `forecast-realization`を`confirmed`にする | `known` |
| 照合配分の`confirmedAgainst` | `allocationStatus`が`confirmed` | `known`（保存の時点の両方の現在の版） |
| 照合配分の識別の次元の項目（[照合の規則](reconciliation.md)の3の表） | 確定するとき | 同3の表の条件のとおり |
| 計算runの`target.jurisdiction` | いつでも | `known`か`unknown`だけ（`not-stated`・`not-applicable`は使わない。`known`でなければ結果の状態は`unsupported`。[計算結果](calculation-results.md)の2） |
| 改訂の共通の形の`knownOn` | いつでも | `known`か`unknown`だけ（`not-stated`・`not-applicable`は使わない。7の時点を指定した見方は、この2つで改訂を選ぶ） |
| 照合の判断の`scope` | `annual-adoption`・`mismatch-explanation` | `known` |
| 照合の判断の`explainedComparisons` | `mismatch-explanation` | `known`（1件以上） |
| 計算runの`ruleSet`・`failure`・`previousRunId` | 結果の状態ごと | 下の「計算runの項目の状態」の表 |
| `AdoptionSnapshot`の`adoptedRef`と`coverage` | `selection`が`annual-document` | `adoptedRef`は`known`（版を固定）、`coverage`は`known`の`annual-document` |
| 同 | `selection`が`entered-payslips`・`no-annual-document` | `adoptedRef`は`not-applicable`、`coverage`は`known`の`entered-records-only` |
| 同 | `selection`が`adoption-needed` | どちらも`not-applicable` |
| `Assumption`の`ref` | `source`が`forecast` | `known`（予測の行。版を固定） |

**`not-applicable`を許す項目:** この表にない`Fact`の項目は`not-applicable`を使わない。

| 項目 | `not-applicable`の意味・条件 |
| --- | --- |
| メモ・根拠の文の項目: 改訂の共通の形の`changeNote`、雇用先・口座・発行者・照合配分の`note`、雇用条件の`payScheduleNote`、予測の`basisNote`、計算runの`scopeNote`、`RoundingStep`の`ruleRef` | 書くことがない |
| 「〜の場合だけ」と書いた項目（`duplicateOf`、`importKey`、照合配分の`settlesForecastLine`・`confirmedAgainst`、照合の判断の`scope`・`explainedComparisons`、予測の`accountId`、計算runの`failure`等） | その場合でない（1の規則） |
| `Period`の`end` | 終わりの定めがない（継続中。6） |
| 雇用条件の`scheduledWeeklyMinutes` | 所定労働時間の定めがない |
| 給与明細の`workPeriod`、予測の行の`workPeriod`、正式通知の`applicablePeriod` | 期間という概念が当てはまらない（6） |
| 給与明細の`commutingAllowance`・`commutingAllowanceTaxTreatment`・`incomeTax`・`residentTax`・`healthInsurance`・`nursingCareInsurance`・`pensionInsurance`・`employmentInsurance`・`yearEndAdjustment` | その支給・控除がその人に当てはまらない（制度・雇用条件による。利用者の根拠をメモに書ける） |
| 給与明細の`bankTransferAmount` | 振込がない（現金払い等）。入金と結べない（[照合の規則](reconciliation.md)の3） |
| 給与明細・年間資料・正式通知の`supersedes` | 作り直しでない、または前の資料を記録していない（上の表） |
| 予測の`employerId` | 入金の予測で勤務先に結び付けない |
| 正式通知の`subjectYear` | `amounts`が`known`（確かめた）で、その中に`category`が`annual-total`の行も、`category`が`known`でない行もない場合だけ。`amounts`が`unknown`（読んでいない）なら、決定額の行がないとは確かめられないので許さない（5の「分からない値で絞り込まない」） |
| 正式通知の`incomeYear` | 所得に基づかない通知（資格の通知等） |
| 証憑の紐付けの`locator` | ファイル全体を指す |
| 計算runの`ruleSet`・`previousRunId` | 下の「計算runの項目の状態」の表のとおり |
| `AdoptionSnapshot`の`adoptedRef`・`coverage`、集計値の`coverage` | 上の表と11のとおり |
| `Assumption`・`MissingInput`の`ref` | 参照する記録がない（`MissingInput`は、`field`の`kind`が`calculator-input`の場合だけ。11の「不足の項目」） |
| `ResultItem`の`value` | [計算結果](calculation-results.md)の2の表で許す状態のとき（その結果の項目が当てはまらない） |

金額の合計や比較に使う項目（給与明細の`grossPay`・`taxablePay`・`nonTaxablePay`・`totalDeductions`・`netPay`、行の`amount`、年間資料の金額、正式通知の行の`category`と`amount`、入金の`amount`等）は、この表にないので`not-applicable`を使わない。`not-applicable`は集計から除かれ、不足にも数えないので、これらに使うと値を黙って落とすことになるため。

**並びの空の意味（1つの規則）:** 並びは、空の並びが何を意味するかで、次の2つに分ける。契約のすべての並びは、下の表のどちらかに当たる。

- **資料から写す並び:** 利用者が資料の行を写す並び。空の並びが「確かめて行がない」とも「まだ読んでいない・写していない」とも読めるので、`Fact<List<…>>`にし、`known`（空なら確かめて行がない）か`unknown`（写していない。既定）だけを許す。`unknown`の並びは、5の「分からない値で絞り込まない」に従って扱う（その並びを使う集計は不足に挙げ、候補の年等を狭めない）。
- **作った時点で完全な並び:** アプリ・計算器・利用者の操作が作る並び。空は「該当なし」の意味で一通りに決まる（または空を許さない）ので、`List<…>`のままにする。

並びの要素は、下の表の「要素の一意のキー」で一意とする（同じキーの要素が2つある並びは保存しない。計算runの中の並びなら、そのrunを保存しない）。キーが`known`でない要素（支払者が分からない行等）は、互いに区別できないので重なりとはみなさないが、そのような要素があることは、その並びを使う規則に従って不足・要確認として扱う。

| 並び | 区分 | 空の並び | 要素の一意のキー |
| --- | --- | --- | --- |
| 給与明細の`otherEarnings`・`otherDeductions`（[記録の型](records.md)の4） | 資料から写す | `known`の空は行がない。`unknown`は写していない | `lineId` |
| 年間資料の`includedOtherPayers`（同6） | 資料から写す | `known`の空は他の支払者の分がない。`unknown`は確かめていない（範囲が確定しない） | `payerEmployerId`（`known`のもの） |
| 正式通知の`amounts`・`installments`・`statusDates`（同8） | 資料から写す | `known`の空は行がない。`unknown`は読んでいない | `lineId` |
| 予測の`lines`（同7） | 利用者の操作が作る | 空を許さない（1行以上） | `lineId` |
| 照合の判断の`targets`（[照合の規則](reconciliation.md)の4） | 利用者の操作が作る | 判断の種類ごとの件数（同4の表）。`entered-payslips`の`targets`だけが空 | 参照先の`id` |
| 照合の判断の`scope.payers`（同4） | 利用者の操作が作る | 空を許さない | 支払者の`id` |
| 照合の判断の`explainedComparisons`（同4） | 利用者の操作が作る | 空を許さない（1件以上） | `field` |
| `explainedComparisons`の各要素の`coveredPayslips`（同4） | 利用者の操作が作る（判断したときの写し） | 空を許す（結んだ明細がなかった） | 明細の`id` |
| 集計値の`scope`の`employerIds`・`accountIds`（11） | 利用者の操作が作る | 空は「限定しない」 | `id` |
| 集計値の`missing`（11） | アプリが作る | 空は不足がない | `ref`と`field`の組 |
| 計算runの`results`・`roundingSteps`・`missingInputs`・`unconfirmedItems`・`assumptions`・`adoptions`・`inputs`の各並び（[計算結果](calculation-results.md)の1） | 計算器が作る | 空は該当なし | [計算結果](calculation-results.md)の1の「run内の並びの規則」の表 |
| `ResultItem`の`explanationRefs`（同1） | 計算器が作る | 空は該当なし | 参照先の`id`と`line`の組 |
| `AdoptionSnapshot`の`payers`（同1） | 計算器が作る | 空を許さない | 支払者の`id` |
| `AdoptionSnapshot`の`comparisons`（同1） | 計算器が作る | 空は比較する項目がない | `field` |

**計算runの項目の状態（結果の状態ごと）:** 計算runの`Fact`の項目のうち、結果の状態で決まるものを、5つの状態すべてについてこの1つの表で定める。結果の状態は、[計算結果](calculation-results.md)の2の順序（`failed` > `unsupported` > `incomplete` > `provisional` > `computed`）で1つに決まる。結果の値（`results`の`value`）の状態も、同じ2の表による。

| 項目 | `computed` | `provisional` | `incomplete` | `unsupported` | `failed` |
| --- | --- | --- | --- | --- | --- |

| `failure` | `not-applicable` | `not-applicable` | `not-applicable` | `not-applicable` | `known` |
| `previousRunId` | `known`か`not-applicable`（どちらになるかと保存の条件は[計算結果](calculation-results.md)の3の「runの履歴」） | 同左 | 同左 | 同左 | 同左 |

どの状態でも、`ruleSet`は制度データを読み込んだかどうかだけで決まり（読み込んだら`known`、読み込まなかったら`not-applicable`）、`unknown`は使わない。

## 13. 状態の決め方と、値どうしの比較

**状態の決め方（すべての状態の判定に共通）:** 契約で列挙した状態を導く判定は、どれも優先順を付けた表で書く。上から順に調べ、最初に当てはまったものに決める。空の集合（対象の記録・根拠・配分・候補が0件）の場合も、表のどれかに当たるように書く。どの判定も、すべての場合にちょうど1つの状態に決まる。

**規則がまだないとき（1つの規則）:** 有効なキー・入力（`AggregateKey`、比較の項目、帰属等）でも、値を導く規則（T14が承認する比較の対応表・帰属の規則、T15以降の計算器の規則）がまだない場合は、要求を拒否せず、記録なし（`no-records`）や0にもしない。値を決めない状態にする: 集計は`incomplete`で`missing`に`rule-pending`（派生キーは11の表）、比較は`rule-pending`（[照合の規則](reconciliation.md)の5）、帰属は`undetermined`（同8）、計算runは`unsupported`（[計算結果](calculation-results.md)の2）。

**判定の順序（1つの規則）:** 優先順の表は、次の順に条件を置く。

1. 関係の有無や、関係を使えるかどうかにかかわらず結果が決まる条件（取り下げた予測の行の残りは0、対応表がない比較は`rule-pending`等）。
2. 関係を解決できない・使えない条件（[照合の規則](reconciliation.md)の9の「使えない関係」）。
3. 関係がない場合の条件（結んだ明細が0件、根拠が0件等）と、値による条件。

前の手順は、後の手順へ進む道を塞がないようにする。前の手順で止まる状態（使えない関係、要確認、要判断）には、利用者が抜け出す操作（確かめ直し、却下、取消、結び直し、判断の改訂）がなければならない。抜け出す操作がない状態（取り下げた行への配分は、`withdrawn`のままでは確かめ直せない等）で結果が決まるなら、その条件を手順1に置く。

| 判定 | 定義の場所 | 空の集合の場合 |
| --- | --- | --- |
| 集計の状態 | 11 | 不足がなく対象の記録が0件なら`no-records` |
| 不足の1行の状態 | 11（優先順） | 行は原因が1つ以上あるときだけ作る |
| 年間の値の採用（支払者ごとの選択） | [照合の規則](reconciliation.md)の5 | 候補が0件で、範囲が確定しない資料・整っていない系列の資料（同5の手順2）もなければ年間資料なし |
| 比較の状態（年間資料と明細） | 同5 | 使えない関係（同9）がなく、結んだ明細が0件なら`no-coverage`（使えない関係があれば`incomplete`） |
| 予測の行の残り | 同6 | 取り下げた行は0。それ以外で確定済みの配分が0件なら予測の金額（`known`でなければ`unknown`） |
| 所得の年への帰属 | 同8 | 根拠が0件なら`undetermined` |
| 照合配分の使われ方 | 同9 | （配分ごとの判定） |
| 差し替えの系列 | [記録の型](records.md)の10 | 関係が0件の記録は、それ自身が現在の記録 |
| 計算runの結果の状態 | [計算結果](calculation-results.md)の2 | （runごとの判定） |

**値どうしの比較（4×4の表）:** 2つの値が「同じかどうか」を比べる判定は、次の1つの表で結果を決める。対象は、差し替えの識別の次元、照合配分の識別の次元、重複の候補、`Ref`の参照先の次元（下の「各判定での結果の使い方」の表の4行）。結果は「一致」「不一致」「未確定」の3つ。

| 左＼右 | `known`（値b） | `unknown` | `not-stated` | `not-applicable` |
| --- | --- | --- | --- | --- |
| `known`（値a） | aとbが同じなら一致、違えば不一致 | 未確定 | 未確定 | 不一致 |
| `unknown` | 未確定 | 未確定 | 未確定 | 未確定 |
| `not-stated` | 未確定 | 未確定 | 未確定 | 未確定 |
| `not-applicable` | 不一致 | 未確定 | 未確定 | 一致 |

- 未確定は、5の「分からない値で絞り込まない」を当てはめた結果で、一致として扱わず（確定の根拠にしない）、不一致として除外もしない。
- **表への当てはめ方（1つの規則）:** 比べる2つの値は、どちらも次のとおりに表の行・列の1つへ当てはめ、表のちょうど1つの欄で結果を決める。
  - `Fact`の値は、その状態の行・列に当てはめる。
  - `Fact`でない値（`Id`、`CalendarYear`、列挙等。記録の`employerId`・`accountId`、年間資料の`targetYear`等）は、その値を持つ`known`として当てはめる。`Fact`でない値どうしは左上の欄になり、同じなら一致、違えば不一致。`Fact`と`Fact`でない値（予測の`employerId`と明細の`employerId`、予測の`accountId`と入金の`accountId`等）は、`Fact`の側の状態で行または列が決まる。
  - 値が組（`subjectYear`の`{ kind, year }`等）なら、すべての要素が同じときだけ「同じ」とする。
  - マスタ（雇用先・口座・発行者）のIDは、9の「マスタの取消と二重登録」で正規のIDに解決してから当てはめる。
- **集合に含まれるか:** 値が集合に含まれるか（年間資料の範囲に支払者が含まれるか等）は、集合の要素ごとに上の表で比べる。どれかが一致なら一致。集合が確定していて（並びが`known`で、要素がすべて`known`）、すべて不一致なら不一致。それ以外は未確定。たとえば範囲が確定しない年間資料では、発行者と同じ支払者の明細だけが一致になり、ほかは未確定になる（[照合の規則](reconciliation.md)の3・5）。
- 推定の項目（入金の`payerHint`）は識別の値ではないので、この表を使わない。[照合の規則](reconciliation.md)の3の表の扱い（両方が`known`のときだけ比べる）に従う。

各判定での結果の使い方:

| 判定 | 一致 | 不一致 | 未確定 |
| --- | --- | --- | --- |
| 差し替えの識別の次元（[記録の型](records.md)の10） | その次元を満たす | 保存を拒否する | 保存は許し、未確認の差し替えとする（その系列を未確認の系列として集計・採用・照合から除き、`conflict`で挙げる） |
| 照合配分の識別の次元（[照合の規則](reconciliation.md)の3） | その次元を満たす | 確定を拒否する（候補としては保存できる） | 確定しない（候補としては保存できる。値を確かめてから確定する） |
| 重複の候補（同7） | 候補にする | 候補にしない | 候補にする（外さない） |
| `Ref`の参照先の次元（2の「参照先の種類・粒度・次元」。差し替え・照合配分の2行以外の項目。たとえば`AdoptionSnapshot`の`adoptedRef`、`annual-adoption`の判断の年間資料） | 指せる | 保存を拒否する | 保存を拒否する |
