# 合成例

[契約の入口](README.md)／前: [計算結果](calculation-results.md)

契約の規則を当てはめた結果を、合成データで示す。第三者が読んで、記録の持ち方と集計の結果を一通りに決められることを目的とする。T03は、これらの例を基にケースID・入力・期待する記録と集計・理由を台帳にする（例のIDを引き継いでよい）。

## 読み方

- **すべて架空のデータ。** 勤務先・口座・摘要・金額は、実在の人・会社・給与と関係がない。税額・保険料の値は、制度による計算の結果ではなく、例のために置いた数。
- 各例は独立している。記録のID（`pay_101`等）はその例の中だけで使う。下の「共通の設定」の雇用先・雇用条件・口座だけを共有する。
- 表に挙げない記録の項目は、その例の期待する結果に影響しない（実際の記録では、入力がなければ`unknown`になる）。ただし、資料から写す並び（給与明細の`otherEarnings`・`otherDeductions`、正式通知の`amounts`・`installments`・`statusDates`）は、表に挙げなければ「確かめて行がない」（`known`の空の並び）とする（[共通の型](common-types.md)の12の「並びの空の意味」）。
- 金額の状態は「値あり 230,000」「不明」「記載なし」「対象外」と書く（[共通の型](common-types.md)の5）。金額は円。
- 集計は「集計の種類（範囲、軸）」で書く。集計の種類は、[共通の型](common-types.md)の11の`AggregateKey`に対応する（入金額＝`deposit-amount`、支給額＝`payslip-item`の`grossPay`、見込み＝`forecast-remaining`、正式通知の決定額＝`notice-determination`、年間の支払金額＝`annual-value`の`paymentAmount`等）。軸は、入金日・支払予定日・予定月・所得の年のどれか（[照合の規則](reconciliation.md)の2）。期間は短く「入金日 2026-09」のように書く。これは`scope`の`from` 2026-09-01・`to` 2026-09-30（両端を含む。[共通の型](common-types.md)の11の`AxisValue`）を表す。
- 「しないこと」は、この契約のもとで誤りになる解釈。

## EX-03 同じ日・同じ金額の別件

勤務先Bから、2026-10-30に口座2へ30,000の入金が2件あった。1件は9月勤務分の給与、もう1件は立て替えた経費の精算。

| ID | 種類 | 内容 |
| --- | --- | --- |
| `dep_301` | 銀行入金 | 口座2、2026-10-30、30,000、摘要「フリコミ ビーシヤ（架空）」、`purpose` 給与の振込。`writeRequestId` `w-301` |
| `dep_302` | 銀行入金 | 口座2、2026-10-30、30,000、摘要「フリコミ ビーシヤ（架空）」、`purpose` 経費の精算。`writeRequestId` `w-302` |
| `pay_301` | 給与明細 | 勤務先B、給与、勤務期間 2026-09-01〜2026-09-30、支払予定日 2026-10-30、総支給額 33,000、所得税 3,000、振込額 30,000 |
| `dcs_301` | 照合の判断 | `duplicate-review`、対象 `dep_301`・`dep_302`、`distinct`、理由「給与と経費の精算の別の振込（勤務先に確認）」 |
| `alc_301` | 照合配分 | `pay_301` → `dep_301`、30,000、確定 |

手順と結果:

1. `dep_301`の保存の要求が、通信の再送で2回届いた（同じ`w-301`）。記録は`dep_301`の1件だけ。2回目の要求には、1回目と同じ結果を返す。
2. `dep_302`は別の操作（`w-302`）なので、口座・日付・金額が同じでも別の記録として保存する。`dep_301`との組が重複の候補として表示される（保存は止めない）。
3. 利用者が`dcs_301`（別件）を記録する。この組は候補に出なくなる。
4. `alc_301`で給与の明細と`dep_301`を結ぶ。

| 集計 | 結果 |
| --- | --- |
| 入金額（口座2、入金日 2026-10） | `complete` 60,000 |
| 支給額（勤務先B、支払予定日 2026-10） | `complete` 33,000（`pay_301`だけ） |
| 未照合の入金 | `dep_301`: 0、`dep_302`: 30,000（経費の精算。給与ではないので未照合のまま残る） |

二重登録の場合: 後日、利用者が同じ入金を手入力でもう一度保存した（別の操作`w-303`で`dep_303`、口座2、2026-10-30、30,000）。

| 時点 | 入金額（口座2、入金日 2026-10） | 表示 |
| --- | --- | --- |
| `dep_303`の保存直後 | `complete` 90,000 | 重複の候補2組（`dep_301`と`dep_303`、`dep_302`と`dep_303`） |
| `dcs_302`（`duplicate-review`、対象 `dep_301`・`dep_303`、`same`）を記録し、`dep_303`を取消（版2、`void`、`duplicateOf` `dep_301`）した後 | `complete` 60,000 | `dep_303`は履歴に残る。`dcs_302`は有効のまま（取消した`dep_303`の`duplicateOf`が判断のもう一方`dep_301`を指すため。[照合の規則](reconciliation.md)の7） |

**取消と取消の取り消し（改訂のモデル。[共通の型](common-types.md)の9）:**

| 操作 | 結果 |
| --- | --- |
| `dep_303`の取消（版2）で、同時に金額を29,000に変えて保存しようとした | 拒否。`void`は`status`と`duplicateOf`だけを変え、`body`は直前の改訂と同じでなければならない。金額を直すなら、取消の前に別の改訂（`correct-input-error`）にする |
| 上の表のとおり、`dep_303`を取消（版2、`void`、`body`は版1と同じ、`duplicateOf` `dep_301`）した | 入金額（口座2、2026-10）は`complete` 60,000。`dcs_302`（`same`）は前提を満たす |
| 取消した`dep_303`を、取消の取り消しをせずに`correct-input-error`で直そうとした | 拒否。取消した記録に続けられる改訂は`unvoid`だけ |
| 後日、`dep_303`は実は別の3件目の振込（経費の精算）だったと分かり、`dep_303`の取消を取り消した（版3、`unvoid`、`body`は版2と同じ、`duplicateOf`は対象外） | `dep_303`は有効に戻り、入金額（口座2、2026-10）は`complete` 90,000。`dcs_302`（`same`）は両方が有効になったので前提が崩れ、「要確認」と表示される。利用者が`dcs_302`を`distinct`に改訂（`new-information`）すると、`dep_301`と`dep_303`の組は候補に出なくなる。`dep_302`と`dep_303`の組は、判断するまで重複の候補として残る |

**雇用先の二重登録（マスタの取消。[共通の型](common-types.md)の9の「マスタの取消と二重登録」）:** 利用者が勤務先Bを誤ってもう一度登録し（`emp_9`、表示名「勤務先B（重複）」）、10月勤務分の明細`pay_304`（勤務期間 2026-10-01〜10-31、支払予定日 2026-11-30、総支給額 33,000、振込額 30,000）の`employerId`を`emp_9`にして保存した。

| 操作 | 結果 |

| --- | --- | --- | --- |
| `fc_702`の`l1` | 60,000 | 25,000（消し込まない） | 35,000 |
| `fc_701`の`l3` | 50,000 | 50,000（消込） | 0（見込みとの差 0） |

| 集計 | 結果 |
| --- | --- |
| 実績と見込みの表示（勤務先B、2027-01） | 実績 75,000（`pay_702`）＋ 見込み 35,000（`fc_702`の`l1`の残り）＝ 110,000（「見込みを含む」） |

後日（把握日 2027-03-10）、勤務先Bから残りは支払わないと連絡があった。利用者が`alc_702`を改訂（`new-information`）して消し込む（true）と、`fc_702`の`l1`の残りは0、見込みとの差は −35,000になる。

**取り下げた場合（判定の順序。[照合の規則](reconciliation.md)の6）:** 消し込む代わりに、利用者が`fc_702`の行`l1`を取り下げた（`lineStatus` `withdrawn`、`new-information`）とする。

| 項目 | 結果 |
| --- | --- |
| `alc_702`の使われ方 | 要再確認（確定に使う項目の予測の行の状態が変わった）。`withdrawn`のままでは確かめ直せない。記録は消さず、「要再確認」として表示し続ける（関係がないとはみなさない） |
| `fc_702`の`l1`の残り | `known`の0（手順1。使えない関係の手順2より先に調べるので、`unknown`のまま止まらない） |
| 見込み（勤務先B、予定月 2027-01） | `complete` 0。取り下げた行`l1`を対象に残し、0として数える（`no-records`にしない。行があって取り下げたことを、記録がないことと区別する。[共通の型](common-types.md)の11の「除くと0を分ける」） |
| 実績と見込みの表示（勤務先B、2027-01） | 実績 75,000（`pay_702`）＋ 見込み 0 ＝ 75,000。実績化した25,000を、見込みとしても数えない |

しないこと: `pay_702`の総支給額75,000と、`fc_701`の`l3`の50,000を両方足さない（`l3`の実績化を忘れると、この二重計上が起きる）。`fc_702`の`l1`を60,000のまま見込みに残さない。

### (c) 識別の次元の比較（`Fact`と`Fact`でない値）

`forecast-realization`の識別の次元では、予測の側が`Fact`、実績の側が`Fact`でない値を比べる（[照合の規則](reconciliation.md)の3）。比べ方は[共通の型](common-types.md)の13の「表への当てはめ方」で、`Fact`でない値は`known`として4×4の表に当てはめる。4×4の表は左右対称なので、予測の側を左に置いても、実績の側を左に置いても（両方向）、同じ欄に当たり、同じ結果になる。

勤務先（給与の予測。予測の`employerId`は`Fact<Id<Employer>>`、明細の`employerId`は`Id<Employer>`）。明細は`pay_701`（勤務先B）とする。

| 予測の`employerId` | 明細の`employerId` | 予測→明細の欄 | 明細→予測の欄 | 結果 |
| --- | --- | --- | --- | --- |
| `known` 勤務先B | 勤務先B（`known`として当てはめる） | `known`×`known`（同じ） | `known`×`known`（同じ） | 一致。確定できる（`alc_701`） |
| `known` 勤務先A | 勤務先B | `known`×`known`（違う） | `known`×`known`（違う） | 不一致。確定を拒否する（候補としては保存できる） |
| `unknown` | 勤務先B | `unknown`×`known` | `known`×`unknown` | 未確定。確定しない（一致とみなさない。先に予測を改訂して`known`にする） |
| `not-stated` | 勤務先B | `not-stated`×`known` | `known`×`not-stated` | 未確定。確定しない |
| `not-applicable` | 勤務先B | `not-applicable`×`known` | `known`×`not-applicable` | 不一致。確定を拒否する（給与の予測では`not-applicable`は使えないので、予測の保存のときにも拒否される） |

口座（入金の予測。予測の`accountId`は`Fact<Id<Account>>`、入金の`accountId`は`Id<Account>`）。仮の入金の予測`fc_703`（`subject` 入金、`measure` 入金額）と、口座2への入金を比べる。

| `fc_703`の`accountId` | 入金の`accountId` | 両方向の欄 | 結果 |
| --- | --- | --- | --- |
| `known` 口座2 | 口座2 | `known`×`known`（同じ） | 一致。確定できる |
| `known` 口座1 | 口座2 | `known`×`known`（違う） | 不一致。確定を拒否する |
| `unknown` | 口座2 | `unknown`×`known`／`known`×`unknown` | 未確定。確定しない（実績化の確定には予測の`accountId`の`known`が必要。[記録の型](records.md)の7） |
| `not-stated` | 口座2 | `not-stated`×`known`／`known`×`not-stated` | 未確定。確定しない |
| `not-applicable` | 口座2 | `not-applicable`×`known`／`known`×`not-applicable` | 不一致。確定を拒否する（入金の予測では`not-applicable`は使えないので、予測の保存のときにも拒否される） |

入金の予測の`employerId`と入金の`payerHint`は、推定の項目なので4×4の表を使わず、両方が`known`のときだけ比べる（[照合の規則](reconciliation.md)の3の表）。`payerHint`が`unknown`でも、それだけで確定を止めない。

## EX-09 雇用条件の期間（不明な境界）

雇用条件の期間の重なりの判定（[記録の型](records.md)の2）。境界が`known`でない場合は推測せず、最も広く解釈する。

| 操作 | 結果 |
| --- | --- |
| 勤務先Aの`term_1`（2026-04-01〜、`end`は対象外＝継続中）があるときに、勤務先Aの新しい雇用条件`term_901`（2027-04-01〜、継続中）を保存しようとした | 拒否。`term_1`は継続中で、後ろへ無限に広がるので、重ならないことを確かめられない |
| `term_1`を改訂（`new-information`。契約の更新で条件が変わると分かった）して`end`を2027-03-31にしてから、`term_901`を保存した | 保存できる。2026-04-01〜2027-03-31と2027-04-01〜は重ならない |
| 勤務先Cの以前の雇用条件`term_902`（`start`は不明、`end` 2024-03-31）を保存した | 保存できる。`start`は前へ無限に広げて解釈するが、`end`が`term_3`の`start`（2025-04-01）より前なので、重ならない |
| 勤務先Cの雇用条件`term_903`（`start`は不明、`end`は不明）を保存しようとした | 拒否。前後どちらにも無限に広がるので、`term_3`・`term_902`と重ならないことを確かめられない |

`end`の「対象外（継続中）」と「不明」は、重なりの判定ではどちらも後ろへ無限に広げる。ただし意味は違う。`term_1`は「継続中」と表示し、`end`が`unknown`の雇用条件は「終了日不明」と表示する。古いデータの復元などで、重ならないことを確かめられない雇用条件がすでに2件あった場合は、どちらも「要確認」とし、確かめるまで期間に基づく判定（T14・T17）に使わない。

しないこと: 不明な`start`を、知っている最初の給与明細の日付などで埋めない。継続中の`end`を「不明」として記録しない（逆も同じ）。
