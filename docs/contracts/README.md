# 記録・照合・計算結果の契約

T01「記録・照合・計算結果の契約」の成果物。関連Issue: [#8](https://github.com/doc-gif/kurashi-ledger/issues/8)（契約版1.0）、[#32](https://github.com/doc-gif/kurashi-ledger/issues/32)（契約版2.0の見直し）。

- 契約版: `2.0`（変更の内容は下の「変更の履歴」）
- 状態: Proposed（変更したPRがmainに統合された時点で、後続タスクの前提にできる）

## この契約の役割

記録の種類ごとに、項目・型・意味を定める。合成データと期待結果（T03）、記録ドメイン（T06）、永続化（T07）、入力（T09・T10）、照合（T11）、出力（T12）、制度と計算（T14・T15〜T22）は、この契約の意味に従う。

- **定めること:** 記録の種類と項目、ID・版・単位・日付・通貨・金額の状態、3つの時間軸（適用期間・把握日・記録日時）、改訂と差し替え、照合配分と判断、集計の採用元、所得の年への帰属の根拠の持ち方、計算runの形。
- **定めないこと:** DBのテーブル（T07）、TypeScriptの型の書き方（T06）、CSV/JSONのファイル形式とデータ辞書（T12）、画面（T10）、税・保険の制度の規則（どの日付で年に帰属させるか、どの支給が課税か、年間資料のどの項目を明細のどの項目と比べるか。T14）。ただし、実装や出力は、この契約の区別（金額の4つの状態、日付の種類、改訂の履歴）を失ってはならない。

## 読む順序

1. [共通の型](common-types.md) — ID、版、金額・通貨・単位、金額の状態、日付と期間、時間軸、記録の区分、改訂、冪等キー、集計値の形
2. [記録の型](records.md) — 雇用先、雇用条件、口座、給与明細、銀行入金、年間資料、予測、正式通知（と発行者）、証憑、資料の差し替え、4つの日付
3. [照合・採用・集計の規則](reconciliation.md) — 集計の採用元、照合配分、照合の判断、年間資料と月次資料、予測の実績化、重複と同額別件、所得の年への帰属、改訂の影響
4. [計算結果](calculation-results.md) — 計算run、結果の状態、不変と再計算
5. [合成例](examples.md) — EX-01〜EX-09

## AGENTS.mdの不変条件との対応

| 不変条件 | 契約での扱い |
| --- | --- |
| 未知値は0ではない | 金額は4つの状態（値あり・不明・記載なし・対象外）を持つ。0は「値あり」の0だけ。集計は不足を数え、不足があれば合計として表示しない（[共通の型](common-types.md)の5・11） |
| 銀行入金は総支給額でも課税給与でもない | 入金は入金の集計にだけ使う。照合配分は金額を移さない（[照合の規則](reconciliation.md)の2・3） |
| 年間資料と月次明細を足して二重計上しない | 1つの集計に採用元は1つ。年間の値は、範囲の重ならない年間資料を採用する（[照合の規則](reconciliation.md)の5・10） |
| 実績・見込み・正式通知を分ける | 記録の区分を記録の種類で固定する。見込みは照合配分で実績化し、書き換えない（[共通の型](common-types.md)の8、[照合の規則](reconciliation.md)の6） |
| 適用期間・把握日・記録日・改訂履歴を保持する | 3つの時間軸と、追記だけの改訂（[共通の型](common-types.md)の7・9） |
| 過去の計算runを黙って書き換えない | 計算runは一度だけ書き、入力の版を固定する（[計算結果](calculation-results.md)の3） |
| 税・保険は対象年・地域・適用範囲・原典・丸めと、独立して確認した期待値が必要 | 計算runは、対象（年・年度・地域・手続・基準の時点）と制度データの版を持ち、制度の規則による丸めの手順は、その版と照合できる原典の箇所を必須にする（[計算結果](calculation-results.md)の1の「手続と基準の時点」「丸めの根拠」）。規則と期待値はT14・T03が一次資料から決め、実装の出力を正解にしない |
| 合成データのみ | 合成例はすべて架空（[合成例](examples.md)） |

## 契約の変更

- 契約定義（`docs/contracts/`）は共有資源。同時に変更するのは1担当だけにし、着手前に調整係へ申告する。
- 後続タスクの作業でこの契約の変更が要る場合（T14が帰属の候補の年の表に次元を足す、T17が数値以外の結果の型を足す等。上の「後続タスクへの引継ぎ」の表）は、そのタスクの範囲に`docs/contracts/`がなくても、契約定義を共有資源として申告し、この節の手順で変える。台帳のそのタスクの節に共有資源として書かれていなければ、着手のときに調整係が台帳に加える（T17は記載済み）。範囲の外の編集として黙って行わない。
- 版は`メジャー.マイナー`。意味・状態の区別・値が必要かどうかを変える変更は、メジャーを上げる。省略時に`unknown`と解釈できる`Fact`の項目を足すだけなら、マイナーを上げる。列挙に値を足す変更は、既存の処理が知らない値を受け取るので、メジャーを上げる。
- 例外として、**拡張できる列挙**（[共通の型](common-types.md)の1。いまは給与明細の帰属の区分`incomeTimingKind`だけ）に値を足す変更は、マイナーを上げる。既存の処理は、知らない値をその項目の`unknown`と同じに扱う（規則を選ばない、候補・範囲を狭めない）ことが契約で決まっているため。その値に意味を与える項目（省略時に`unknown`と解釈できる`Fact`）・表の行（[照合の規則](reconciliation.md)の8の「帰属の区分と規則」と帰属の候補の年の表）・規則の差し込み口は、同じ変更で足す。既存の値の意味を変える、知らない値の扱いを変える変更はメジャー。
- 変更するPRは、影響するタスクの成果物（T03のケース、T06の不変条件、T07のmigration、T12のデータ辞書）を本文に挙げ、必要な追従を同じPRか後続のIssueで扱う。
- ADR（[docs/adr/](../adr/README.md)）と食い違う場合は、ADRを正とし、気づいた作業で契約を直す。

### 2.0の変更

所有者の決定（2026-10-03）: 役員賞与と昇給の遡及差額は、いまは製品の対象外とする。あとで機能として足せるように拡張点を用意する。T14（PR #29）の契約への候補と、T03の台帳の未決事項をまとめて見直す。

- **拡張できる列挙**（[共通の型](common-types.md)の1）: 後の機能で値を足す列挙。読む処理が知らない値は`unknown`と同じに扱う。値を足す変更はマイナー（上の「契約の変更」）。
- **給与明細の帰属の区分**（[記録の型](records.md)の4の`incomeTimingKind`、拡張できる列挙）: いまは`ordinary`（通常の給与等。役員賞与と遡及差額は条件によらず含まない）だけ。`known`か`unknown`だけ。`ordinary`の明細に遡及差額の行を持たせない保存の検査。
- **帰属の区分と規則**（[照合の規則](reconciliation.md)の8）: 区分ごとに規則を選ぶ差し込み口。区分が`unknown`・知らない値の明細は、規則を当てはめず、帰属の候補の年をすべての年にする（黙って帰属させない）。区分を足す手順（役員賞与・遡及差額）。
- **利用者の指定の優先**（同8）: 有効な`tax-year-assertion`は規則の根拠に優先する。年間資料の根拠とは、食い違えば1.0と同じく`conflict`。指定の前提に帰属の区分を含める（同4）。
- **比較の状態`not-compared`**（同5）: 比較の対応表が、明細の合計では比べないと定めた項目。`rule-pending`（対応表がまだない）と分ける。明細から示す年間の値では、派生キー`annual-no-counterpart`（状態`unknown`）で不足に挙げる（[共通の型](common-types.md)の11）。
- **行IDの予約語`whole`**（[共通の型](common-types.md)の2の`LineId`）: 所有者の決定（2026-10-03。PR #28のレビューPR28-R009への回答）。行IDに`whole`を使わず、`Ref`の`line`の`whole`をつねに記録全体の意味にする（`Ref`の形は変えない）。行IDとして許す値を狭めるので、この版のメジャーの変更に含める。復元等で入った`whole`の行IDは名前を変えず、保存の検査をすり抜けたデータとして扱う。
- **帰属の規則の版の写し**（[計算結果](calculation-results.md)の1の`inputs.attributionRules`）: runの中の帰属は、runを作ったときの規則の版で導く。
- **T03の台帳の未決事項の明確化**（[台帳](../test-oracles/README.md)の「未決事項」の1〜9。10・11は契約の範囲外）: 集計値の`excludedCount`の数え方と`payslip-by-income-year`の`coverage`（[共通の型](common-types.md)の11）、未照合の振込額の状態（[照合の規則](reconciliation.md)の3）、`mismatch-explanation`の判断全体の前提と項目ごとの前提（同4）、`same`の判断と重複の候補・差し替え済みの通知と決定額の不足（同7）、要求の範囲のマスタを閉包の根に入れること（[計算結果](calculation-results.md)の1）、把握時点の再現の「把握日不明」の一覧（[共通の型](common-types.md)の7）、拒否された保存のID（同2）。

**1.0の記録との互換:** 1.0で保存した給与明細は帰属の区分を持たないが、省略した`Fact`の項目は`unknown`として持つ（[共通の型](common-types.md)の1の「項目の省略」）ので、記録を書き換えずにそのまま有効。帰属は、区分を確かめるまで規則を当てはめず（1.0でも規則は承認されておらず、規則の根拠はなかった）、年間資料か利用者の指定がなければ`undetermined`のまま。ただし帰属の候補の年は、区分が分からないので、1.0の表の次元から決めた年よりも広く、すべての年になる（[照合の規則](reconciliation.md)の8。分からない値で絞り込まない）。利用者が区分を確かめて`ordinary`にすれば、1.0と同じ候補の年に戻る。計算runは固定した写しで、この変更で書き換えない（契約版1.0のもとで保存したrunはない。T15は未実装）。

**影響するタスクの成果物（追従）:** T03の台帳（このPRで、契約版の表記、契約の型の写し、省略した項目の既定、引用、新しい規則の場面を直した。追加の検査は後続）、T06の不変条件（記録の型の写しに帰属の区分。PR #28）、T07のmigration（帰属の区分の列）、T11（帰属・比較・`excludedCount`）、T12のデータ辞書（拡張できる列挙のround trip）、T14の規則（区分`ordinary`の規則の版、比較の対応表の「比べない」項目。PR #29の後続）、T15（帰属の規則の版の写し）。
