# ADR-0006: データ保管先・バックアップ・暗号化・同期の扱い

- 状態: Proposed（このPRがmainに統合された時点でAcceptedとみなす）
- 日付: 2026-10-02
- 関連: T00（Issue #1）、ADR-0002、ADR-0003、ADR-0005、ADR-0007（共通の安全確認と操作ごとの適用表。この本文はG1〜G5の定義の場所）。実装はT07・T09・T12・T27、検証はT13・T25。

## 背景

実データ（給与明細、銀行入金、通知書、証憑のPDF・画像）はこのpublic repoのcheckoutに置けない。`.gitignore`は追加の防御にすぎない（[SECURITY.md](../../SECURITY.md)、[architecture.md](../architecture.md)）。さらに、開発用のworktreeとAIも所有者と同じPCで動くため、開発・試験の実行が実データのDBを開かないようにする必要がある（[AGENTS.md](../../AGENTS.md)、[worktree運用](../local-worktrees.md)）。T00では保管先、バックアップ、暗号化と鍵、Mac/Windowsの二台間同期について、扱う範囲と扱わない範囲を決める。

## 決定

### 1. データルート

アプリの全データを1つの「データルート」に置く。

| OS | 実データの既定のデータルート |
| --- | --- |
| macOS | `~/Library/Application Support/KurashiLedger/` |
| Windows | `%LOCALAPPDATA%\KurashiLedger\`（ローミングしない、そのPC専用の領域） |

- パスは決め打ちせず、OSのホームディレクトリや`%LOCALAPPDATA%`から求める。
- この2つは、OneDriveの既知フォルダー移動（デスクトップ、ドキュメント、ピクチャ等）とiCloudの「デスクトップと書類」の同期対象外。macOSでファイルアクセスの許可を求められる場所（書類、デスクトップ、ダウンロード、iCloud Drive等）にも当たらない。
- 環境変数`KURASHI_LEDGER_HOME`（または起動時の引数）で別の場所を指定できる。指定先も同じ規則で検査する。

**実データと合成データの分離:**

- データルートは作成時に種別（`real`または`synthetic`）を記録したマーカーファイルを持つ。
- **起動モード**を明示的に分ける。どちらのモードかを、データルートの指定の有無から推測しない。このモードの区別は、アプリの起動だけでなく、データルートを開くすべてのコマンド（バックアップの作成、復元、rollback、CSV/JSON出力等の保守コマンド）に同じように適用する。アプリの画面から行う操作（バックアップの作成、CSV/JSON出力）は、起動時に確かめたモードと実行物の確認（承認済みリリース、依存の導入の記録、配信物のmanifest）を引き継ぎ、操作ごとに確かめ直さない。コマンドで行う場合は、`:real`の有無でモードが決まる。
  - **実利用モード:** 専用のコマンド（起動は`npm run start:real`、保守コマンドも`restore:real`のように`:real`の付いた専用のもの）でだけ選べる。既定のデータルート、または`KURASHI_LEDGER_HOME`で指定した`real`のデータルートを開く。次の「承認済みリリース」の条件をすべてGitで確認できなければ、起動しない。開発用のworktreeやAIの作業branchから実行しても、実データを開かないようにするため。
    - HEADが、リリースの名前の規則（`vX.Y.Z`、試験用は`vX.Y.Z-rc.N`）に合う注釈付きタグのcommitと一致し、作業ツリーに変更がない。
    - そのcommitが`origin/main`から到達できる（レビューとマージを経てmainに入っている）。到達の判定は、照合の時点でoriginから取得した`main`の先端で行い、手元のremote-tracking ref（`refs/remotes/origin/main`）だけでは判定しない（手元で動かせるため）。
    - 同じ名前のタグがoriginにあり、指す先が手元のタグと同じ。起動時に`git ls-remote`でoriginと照合する。照合できたタグの名前とobject IDは、そのcommitがそのときのoriginの`main`から到達できたことと合わせて、データルートに記録し、オフラインのときは記録済みのタグだけを認める。初めてのタグをオフラインで使おうとした場合は起動しない。記録を読めない場合（データルートがない新しい環境への復元、入れ替えの途中の復旧、`config/`を含まないバックアップから復元した直後）も、オンラインでの照合を必須とする。記録は、データルートの検査とlockのあと（新規作成では、置いたあと）に書く。
    - 作業branchで手元に作っただけのタグ（originにない、または`origin/main`から到達できないcommitを指すもの）は認めない。
    - originの接続先が、信頼するリポジトリ（`github.com/doc-gif/kurashi-ledger`）であること。forkなど別のリポジトリをoriginにしたcloneでは、そのリポジトリのmainとタグがそろっていても起動しない。接続先の識別方法（URLの正規化、GitHubのリポジトリIDの照合等）はT09で決める。
    - 署名付きタグの検証は、T25でリリース手順を正式にするときに採否を決める。
  - **合成データモード:** それ以外の起動と保守コマンドはすべてこのモード（`npm start`、`:real`の付かない保守コマンド、開発サーバー、試験、E2E、AIの作業）。`KURASHI_LEDGER_HOME`等で明示した`synthetic`のデータルート（試験ごとの一時ディレクトリを含む）だけを開く。指定がなければ、既定のデータルートへ切り替えずに終了する（fail closed）。既定のデータルートと`real`のデータルートは開かない。
- データルートの新規作成は、そのモードの初回起動で、確認を求めてから行う。合成データモードでは、試験のために、作成を明示する引数で確認に代えてよい（方式はT09）。手順は下の「新規作成の手順」に従う。既存のデータルートの一部（`db/`や種別マーカー等、記録した構造の版に含まれるもの）が欠けていても、空のものを作り直さない（3の復元・rollbackが途中で止まった状態を壊さないため）。この規則は置いたあとのデータルートに適用し、新規作成と復元の作業ディレクトリの中での初期化（下の「共通の初期化」）には適用しない。3の復旧操作も、欠けた子を作り直さない。後のリリースで増えた子の扱いは、下の「構造の版」に従う。
- 実利用は、開発用のworktreeとは別の利用専用のcloneから行う（ADR-0002）。

**起動時の検査:** 次のどれかに当たれば、DBを開かずに理由を表示して終了する。判定は既知のパスやOSの情報による発見的なものなので、`.gitignore`と同じく追加の防御として扱う。

- データルートがGitの作業ツリー内（上位にリポジトリのメタデータがある）またはアプリのcheckout内にある。
- データルートがクラウド同期フォルダ内（iCloud Drive、OneDrive、Dropbox、Google Drive等）にある。
- データルートがネットワークドライブ上にある（WindowsのUNCパスと割り当てたネットワークドライブ、macOSのネットワークボリューム。判定できる範囲で）。
- 種別のマーカーが起動方法と合わない（上の分離の規則）。
- 復元やrollbackの作業中を示す状態ファイル（3の「保守作業の状態ファイル」）が残っている。

検査は、指定されたパスの字面ではなく、symlinkやWindowsのjunction等（reparse point）を解決した実体のパスと、その祖先すべてに対して行う。字面だけで判定すると、checkoutや同期フォルダを指すリンクを別の名前で指定して回避できてしまうため。既存のデータルートの実体パスを解決できない場合は、開かずに終了する（fail closed）。まだ存在しないデータルートは、次の「新規作成の手順」で扱う。

**新規作成の手順:** 指定（または既定）のデータルートのパスが存在しない場合だけ、新規作成として扱う。

1. データルートの親ディレクトリが既にあることを確かめ、実体パスに解決する。親がない、または解決できなければ終了する（アプリは親ディレクトリを作らない。下の「単一起動のlock」を参照）。
2. 解決した親と作成予定のパスについて、上の起動時の検査（Git作業ツリー・checkout内、クラウド同期フォルダ、ネットワークドライブ、デスクトップ・書類は確認つき）を行う。
3. 同じ親ディレクトリに、このデータルートの保守作業の状態ファイル（`<データルート>.maintenance`。3を参照）か、復元・rollbackの途中の退避物（`<データルート>.before-restore-*`、`<データルート>.restore-*`）があれば、新規作成として扱わずに止める。復元コマンドでの再開か巻戻しを案内する。前の新規作成の作業ディレクトリ（`<データルート>.create-*`）が残っている場合も止める（6）。
4. 利用者の確認を得て、lockを取る。lockを取ったあとで3の確認をもう一度行い（確認を待つ間に別の作業が始まった場合に備えるため）、データルートと同じ親ディレクトリに作業ディレクトリ`<データルート>.create-<日時>`を作る。作ったパスを実体パスに解決し直して、2の検査をもう一度行う。作成と検査の間にリンクへ差し替えられた場合も、ここで止まる。
5. 作業ディレクトリの中に、固定の子ディレクトリ（下の「共通の初期化」）、種別マーカー（種別と構造の版）、初期スキーマまで入れた空のDB（migrationを済ませ、正常に閉じたもの）を作り終えてから、作業ディレクトリをデータルートの名前へ1回の名前変更で置く。置いたあと、実体パスでもう一度検査する。名前変更のあとにDBの作成や初期化はしない。利用者のデータの書込みは、そのあとに行う。
6. 途中で失敗・中断した場合、データルートの名前のディレクトリはできていない（中途半端なデータルートは残らない）。残った`<データルート>.create-*`は、アプリが自動では削除しない。名前だけでは、アプリが作ったものか、利用者が同じ名前で置いたものかを区別できないため（`KURASHI_LEDGER_HOME`で親を選べる）。次の新規作成は3で止まり、パスを表示して、利用者が中身を確かめて削除してからやり直すよう案内する。

データルートが存在するのに種別マーカーがない、または中身が欠けている場合は、新規作成として扱わずに止める。

**保存先と出力先:** バックアップの保存先とCSV/JSONの出力先も、データルートと同じ方法（実体パスとその祖先）で検査する。拒否する場所は対象ごとに決める。どちらも、repo内とデータルート内を拒否する。バックアップは暗号化済みなので、外付けドライブもクラウドフォルダも可。CSV/JSONは平文なので、暗号化されないことを画面で示す（3）。アプリはこれらのディレクトリを作らない。存在しなければ拒否するので、利用者がOSで作ってから指定する。出力するファイル（アーカイブ、CSV/JSON）は、まず同じ保存先の一時名（完成品と区別できる名前）に、既存のファイルやリンクがあれば失敗する排他的な作成で書く。平文のCSV/JSONは、一時ファイルも最終的なファイルも、本人だけが読める権限（macOSは`0600`、Windowsは本人だけに許可するACL）で作り、確かめる。権限を設定・確認できない場所（FAT・exFATのドライブ等）には出力しない。必要なら、利用者が出力したあとで自分で複製する。書き終えてディスクへの反映を済ませ、バックアップは検証（3の「作成」）も済ませてから、変更先に既存のものがあれば失敗する方法で最終的な名前にする。既存のものを上書きしたり、リンクをたどってほかの場所へ書いたりしない。途中で止まった場合は一時名のまま残り、完成品として扱われない（方法と、各段階での中断の試験はT12）。

デスクトップ・書類（ドキュメント）配下は、OSの設定次第でクラウドへ同期される。利用者が明示的に確認しない限り使わない。

**構成（案。T07・T12で確定）:** `db/`（SQLiteのDBファイルとそのjournal類だけを置く。3のrollbackを参照）、`evidence/`（証憑の複製）、`snapshots/`（migration前の自動退避）、`tmp/`（スナップショットやアーカイブの作業用）、`config/`、`logs/`、種別のマーカー。単一起動用のlockファイルは、下のとおりデータルートの外に置く。

**固定の子の検査:** データルートの中の固定の子ディレクトリ（`db/`、`evidence/`、`snapshots/`、`tmp/`、`config/`、`logs/`）と種別マーカーは、symlinkやjunction等のリンクであってはならない。開く・書くたびに、リンクでないこと（`lstat`等で確かめる）と、実体パスがデータルートの実体パスの配下にあることを確かめる。外れていれば開かずに終了する。たとえば`tmp/`がcheckoutを指していると、起動トークンやスナップショットが公開領域へ書かれてしまうため。確かめ方の詳細と試験はT07で決め、T09（トークンの一時ファイル）とT12（スナップショット・アーカイブの作業）でも同じ確認を使う。

**権限:** データルート、固定の子、新規作成と復元の作業ディレクトリは、本人だけが使える権限で作る（macOSはディレクトリ`0700`、Windowsは本人だけに許可するACL。判定の詳細はT07で決め、ADR-0003の一時ファイルと同じ基準にする）。中のファイルは、本人だけが使えるディレクトリの中にあることで守られる。作る処理（新規作成、共通の初期化、復元、構造のmigration）は、作ったものに権限を設定してから確かめる。復元では、アーカイブの中に記録された権限を使わない。起動時の検査では、データルートと`tmp/`の権限も確かめ、広すぎれば開かずに理由と直し方を表示して終了する。

**共通の初期化:** 固定の子を空で作る処理は1つにし、新規作成と復元の両方で使う。渡された作業ディレクトリに、いまの構造の版の固定の子のうち欠けているものを空で作るだけで、DB、種別マーカー、状態ファイル、lockは扱わない。それらは、呼び出す操作が決めた時点で扱う。

- 新規作成: 共通の初期化のあと、種別マーカーを書き、初期スキーマ入りの空のDBを作ってから置く（上の「新規作成の手順」の5）。
- 復元: アーカイブを展開したあと、共通の初期化で欠けている子（`snapshots/`・`tmp/`・`logs/`・`config/`、空の`evidence/`等）を作る。DBはアーカイブのものを使う。検証とモードの確認のあとで種別マーカーを書いてから、入れ替える（3の手順3・4）。

**構造の版:** 種別マーカーに、データルートの構造の版（固定の子の一覧の版）を記録する。後のリリースで固定の子を加える場合は、構造の版を上げる。構造の版を上げる変更は、固定の子の追加だけに限る（削除・名前の変更・意味の変更はしない。必要になれば別のADRで決める）。

- 記録した版がアプリの版より古い場合は、lockを取り、状態ファイルがなく、起動モードの確認に通ったあとで、増えた子だけを空で作ってから版を更新する（構造のmigration。DBのmigrationと同じくT07の仕組みで行う）。
- 「欠けた子を作り直さない」規則と固定の子の検査は、記録した版に含まれる子のうち、アプリが知っている子にだけ適用する。復元の作業ディレクトリ（マーカーを書く前）では、いまの構造の版の子を対象にする。
- 記録した版がアプリの版より新しい場合（前のリリースへ戻したとき）も、子の追加だけなので開ける。前のリリースは、自分の知っている子だけを確かめ、記録した版を下げない。前のリリースへ戻すrollback（3）も、構造の版では止めない。ただし、前のリリースは知らない子のデータをバックアップに含められないので、記録した版がアプリの版より新しい間は、バックアップの作成を行わない（理由を表示し、新しい版のリリースで作るよう案内する）。
- アーカイブの中の配置とデータルートの配置の対応（制度データや`manifest.json`の置き場所を含む）は、T12で構造の版と合わせて決める。

**単一起動のlock:** 同じデータルートを2つのプロセスが同時に使わないようにする。

- lockファイルの場所は、指定された文字列ではなく、データルートの正規化した実体パスから決める。symlinkやjunction、大文字小文字の違う別名で同じデータルートを指定しても、同じlockになるようにするため。既存のデータルートは実体パスを使う。未作成のデータルートは、親ディレクトリの実体パスに、データルートの名前を正規化してつなげたものを使う。大文字小文字を区別しないファイルシステムでは、OSが返す正規の表記にそろえる（各OSの挙動はT07で確かめる）。
- lockファイルは、その正規のパスの親ディレクトリ、つまりデータルートの外に置く（`<データルート>.lock`。例: `~/Library/Application Support/KurashiLedger.lock`）。データルートの作成・復元での入れ替え・rollbackに影響されず、同じデータルートに対して常に同じlockを使える。空の環境でも、データルートを作る前にlockを取れる。データルートの親ディレクトリは、既にあることを入力の条件とし、アプリは作らない（lockの置き場所を作る手順とlockの取得が循環しないようにするため）。既定のデータルートの親（macOSの`~/Library/Application Support`、Windowsの`%LOCALAPPDATA%`）はOSが用意している。`KURASHI_LEDGER_HOME`で別の場所を指定する場合は、利用者が親を先に作る。親がなければ、理由を表示して終了する。親には、lockファイル、状態ファイル、新規作成・復元の作業ディレクトリと退避ディレクトリを置くので、本人とOSの管理用のアカウント（macOSのroot、WindowsのSYSTEM・Administrators）以外が書き込めないことを確かめ、満たさなければ理由を表示して終了する（ほかのユーザーが、これらを作成・差し替え・削除して、排他制御や復旧を誤らせないようにするため。判定の詳細はT07）。既定の親は、この条件を満たす。lockファイルがデータルートの外にあるので、Windowsでも開いたlockファイルがデータルートの名前変更を妨げない。
- lockファイルと状態ファイル（3の「保守作業の状態ファイル」）は通常のファイルでなければならず、symlinkやjunction等のリンクであってはならない。開く前にリンクでないこと（`lstat`等で確かめる）を確かめ、リンクなら開かずに理由を表示して終了する。ないときは、既存のファイルやリンクがあれば失敗する方法で作る（lockファイルは下の手順、状態ファイルは3の手順）。リンク先のファイルを開いて書き換え、壊さないようにするため。確かめ方（確かめてから開くまでの間の差し替えへの対策を含む）と試験はT07で決める。
- lockは、OSのファイルロックで取る。OSのファイルロックは、プロセスが終われば（強制終了を含む）OSが自動で解放するので、古いlockが残って起動できなくなることがない。PIDの再利用にも影響されない。実装は、このlockファイルを`node:sqlite`で開き、排他lockを保持し続ける方法を第一候補とし、T07で確定する。
- lockファイルには、作成時に、このアプリのlockファイルと分かる識別子と形式の版を記録する（`node:sqlite`なら`application_id`と`user_version`）。既存のlockファイルは、ロックを取る前に、変更せずに識別子を確かめる。合わなければ（利用者の別のファイルや、ほかの用途のSQLiteのDB等）、使わずに理由とパスを表示して終了する。強制終了のあとに残ったこのアプリのlockファイルは、識別子が合うのでそのまま使える。
- lockファイルを新しく作るときは、同じ親ディレクトリの一時名（完成品と区別できる名前）に排他的な作成で作り、識別子と形式の版を書いてディスクへの反映を済ませてから、既存のものを置き換えない方法で正式な名前にする。作る途中で止まっても、正式な名前に初期化されていないlockファイルは残らない。残った一時名のファイルは、起動を妨げない（自動では削除しない）。正式な名前を置くのに失敗した場合（同時に別のプロセスが置いた等）は、置かれたものを上の識別の確認から扱う。
- lockの取得は、1回の原子的な操作で行う。取れなければ、別のプロセスが生きているとみなして終了する。生きているかを確認できない場合も、lockを奪わない。
- PIDや起動時刻を書いたファイルは、利用者への表示のためだけに使い、lockの判定には使わない。
- 復元・rollback等の保守コマンドも同じlockを取り、入れ替えの前後を通して保持し続ける。アプリの起動中は実行できず、保守コマンドの実行中はアプリを起動できない。
- 入れ替え（名前変更）の前に、データルートと作業ディレクトリの中で開いているファイル（DBの接続を含む）をすべて閉じる。Windowsでは、中のファイルが開いているとディレクトリの名前を変えられないため。

- 一時ファイルはOSの一時フォルダではなく、データルートの`tmp/`に置き、失敗時にも削除する。
- 証憑は元ファイルの場所を参照せず、データルート内へ複製する。DBにはハッシュ、元のファイル名、取込日時を記録する。ファイル名に個人情報が入りうるので、保存名はハッシュ等に基づく名前にする。
- 証憑ファイルは書き換えない。取込では、ファイルを`evidence/`へ書き終えてから、それを参照するDBの記録をcommitする。DBから参照されている証憑ファイルは削除しない。訂正は新しい改訂として記録する。

### 2. 暗号化と鍵

**保存中のDBと証憑:** アプリ独自の暗号化は初期範囲に含めない。OSの全ディスク暗号化を、実データを扱う前提条件とする。アプリから有効かどうかを確実には判定できないため、起動手順の確認項目として扱う。前提を満たせない環境では実データを扱わない。

- 前提の対象は、実データのデータルートを置くボリュームである。`KURASHI_LEDGER_HOME`でシステムボリューム以外（外付けドライブ、別のパーティション等）を指定する場合は、そのボリュームも暗号化する（macOS: 暗号化したAPFS、Windows: BitLocker。取り外せるドライブではBitLocker To Go）。システムボリュームの暗号化は、ほかのボリュームを保護しないため。暗号化できないボリュームには、実データのデータルートを置かない。

- macOS: FileVaultを有効にする。Apple siliconやT2のMacは常に暗号化しているが、FileVaultを有効にして初めて、復号にログインパスワードが必要になる。
- Windows: Pro以上はBitLocker、Homeは「デバイスの暗号化」を使う。デバイスの暗号化は、Microsoftアカウント等でサインインしていないと（ローカルアカウントだけでは）、データが暗号化されていても保護されていない状態になる。手順書で注意する。
- ディスク暗号化の回復キーを失うと、PCのデータ全体を失う。アプリのバックアップ（3）とは別に管理する。
- OS全体のバックアップにも注意する。macOSのTime MachineはmacOSに付属しないファイルをバックアップするので、対象から外さない限りデータルートも含まれる。暗号化したバックアップディスクを使うか、データルートを対象から外す。ほかの全体バックアップの道具も同様に扱う。

**アプリのバックアップ:** 外付けドライブやクラウドフォルダなど、PCの外へ持ち出されるので、必ず暗号化する。

**鍵（パスフレーズ）:**

- 既定では、アプリが十分な長さのランダムなパスフレーズを生成して提示する。利用者が自分で決める場合は最低の長さを設け、短いものは受け付けない（長さはT12で決める）。クラウドフォルダに置いたアーカイブは、オフラインで総当たりされうるため。
- パスフレーズはアプリ・DB・設定ファイル・repo・ログに保存しない。パスワードマネージャー等で利用者が管理する。
- **パスフレーズを失うと、そのバックアップは復元できない。** これを手順書と画面に明記する。パスフレーズを変えても既存のバックアップは再暗号化しない（古いパスフレーズが引き続き必要）。

**暗号形式:** 独自の暗号形式は作らない。公開仕様があり、相互運用できる実装を持つ形式として、**age形式**を使う。パスフレーズモードはscryptで鍵を導出し、本体はChaCha20-Poly1305で暗号化する。

- 公式のコマンドラインツール`age`（Go、BSD-3-Clause）でも復号できる。このアプリが動かなくなってもバックアップを取り出せる。
- アプリから使う実装は、公式のTypeScript実装typage（npmの`age-encryption`、BSD-3-Clause）を第一候補にする。2026-10-02時点で0.3系（1.0前）で、監査の有無は確認できていない。T12で、公式`age`との相互復号、scryptの作業係数、ストリーム処理を試験してから確定する。

### 3. バックアップと復元

**中身:**

- DBの一貫したスナップショット（`node:sqlite`の`backup()`または`VACUUM INTO`。使用中のDBファイルをそのままコピーしない。ADR-0005）。
- 証憑（`evidence/`。空でもよい）。
- 制度データ（rules）とそのmanifest。
- manifest（フォーマット版、アプリ版（commit）、スキーマ版、制度データ版、計算エンジン版、データルートの種別（`real`/`synthetic`）、データルートの構造の版（1の「構造の版」）、各ファイルのパスとハッシュ、作成日時）。計算エンジンのコードは、記録したcommitのリリースタグから取得する。
  - manifestは、アーカイブの最上位の固定のパス（`manifest.json`）に置く。自分自身はハッシュの一覧に含めない。manifest自体の改ざんは、age形式の認証付き暗号で、復号の時点で検出する。
- `snapshots/`、`tmp/`、`logs/`、`config/`は含めない。`config/`には、照合済みのタグや保存先のパス等、そのPC固有の記録が入るため。設定は復元後に入れ直す（1の「共通の初期化」で空の`config/`を作る）。

**形式:**

- 中身をtar形式にまとめ、age形式で暗号化する。公式の`age`で復号すれば、macOSとWindows（Windows 10の2018年以降の版）に標準で入っている`tar`で展開できる。
- tarを作るライブラリの選定とライセンスの確認はT12で行う。

**作成:**

- 保存先は利用者が設定するデータルート外のディレクトリ。ブラウザはサーバーにファイルシステムのパスを渡せないので、設定画面のパス入力か設定ファイルで指定し、サーバー側で検査する。repo内とデータルート内は拒否する。暗号化済みなので、外付けドライブもクラウドフォルダも可。
- 作成は利用者の操作（画面またはコマンド）で行う。前回から一定期間が過ぎたら起動時に促す（期間の初期値はT27で決める）。
- **一貫性:** アーカイブは、DBスナップショットの時点を基準にそろえる。アプリの稼働中に取込や訂正が入っても、DBが参照する証憑がアーカイブに欠けないようにする。
  1. DBスナップショットを取る間だけ、アプリは状態を変える要求を受け付けない（単一プロセスなので、プロセス内の書込みロックで止める。画面には作成中であることを示す）。スナップショットが済んだら書込みを再開する。
  2. アーカイブに入れる証憑と制度データは、ディレクトリの一覧からではなく、スナップショットが参照しているものから決める。証憑は書き換えず、DBのcommitより先に書き終えているので（1を参照）、参照されているファイルは必ず存在し、内容も変わらない。
  3. アーカイブへ入れるときに各ファイルのハッシュを計算し、スナップショットに記録されたハッシュと照合する。1件でも合わないか欠けていれば、作成を中止する。
  4. スナップショットより後に取り込まれた証憑は、そのバックアップに含めない（次のバックアップに入る）。
- 作成直後に、まだ手元にあるパスフレーズで復号してハッシュを照合する。成功したものを「検証済み」としてデータルートに記録する。
- 世代管理の初期値は「直近10世代と、各月末の最新を12か月分」。削除するのは、アプリが作成して記録したファイルだけ。削除する前に、そのパスのものが通常のファイル（リンクでない）で、記録したサイズとハッシュに一致することを確かめる。合わなければ（利用者が移動・差し替えた等）、削除せずに一覧で知らせる。最新の検証済みバックアップは自動では消さない。

**migration前の退避:** スキーマを更新する前に、自動で`snapshots/`へ非暗号のスナップショットを作る（DBと同じくディスク暗号化で保護）。直近3世代を残す。migrationの一部としてT07で実装する。

**保守作業の状態ファイル:** 復元とrollbackは、データルートを変える前に、lockファイルと同じ親ディレクトリに状態ファイル（`<データルート>.maintenance`）を作り、作業の種類、対象のデータルート、段階、起動モード（実利用・合成）と、その作業で作る作業ディレクトリと退避ディレクトリの名前を記録する。復旧操作は、推測せずに、記録した名前のディレクトリだけを扱う（保管用に残っている過去の退避ディレクトリと取り違えないため）。

- 状態ファイルの作成と段階の更新は、原子的に、かつディスクに確実に残る形で行い、それが済んでからデータルートを変える。作成は既存のものを置き換えない方法で行い、段階の更新は自分の状態ファイルだけを置き換える。書込みの途中で強制終了や電源断が起きても、古い内容か新しい内容のどちらかが残り、空や書きかけの状態にならないようにするため。具体的な方法（一時ファイルへの書込みとfsync、名前変更、ディレクトリのfsync等）と、各更新点での異常終了の試験は、T07・T12で決める。
- 状態ファイルが読めない、壊れている、内容が分からない場合は、アプリも保守コマンドも起動しない（fail closed）。復旧は、利用者が内容を確かめて行う。

- 状態ファイルがある間は、アプリと、新しい保守作業（別の復元・rollback・バックアップの作成・出力等）は起動しない（起動時の検査）。復元・rollbackのどの段階で異常終了しても、作業ディレクトリが残ったまま通常起動して書き込み、そのあとの再開で新しい書込みを退避して見失う、ということが起きないようにするため。
- 例外として、状態ファイルに記録された作業そのものを片付ける**復旧操作**（やり直し、入れ替えの完了、元に戻す、中止）だけは、同じlockを取って実行できる。復旧操作は、状態ファイルに記録された作業の種類・対象のデータルート・段階が、指定した操作と一致することを確かめてから行う。種類や対象が違えば実行しない。
- 復旧操作は、記録した起動モードで行う。実利用なら`:real`の専用コマンドでだけ行い、承認済みリリースと依存の導入の記録を確かめる（ADR-0007の2）。データルートの固定の子は、あるものだけを、リンクでないこと・データルートの配下にあることで確かめる。欠けた子は段階の判別にだけ使い、作り直さない。
- 状態ファイルを消すのは、作業が完了したとき（完了後に残す`.before-restore-*`や`db.before-rollback-*`は、保管用で起動を妨げない）と、利用者が明示的に中止したときだけ。
- 中止では、作業ディレクトリを削除し、入れ替えの途中なら元に戻してから状態ファイルを消す。
- 検証の段階（入れ替えより前）で止まった作業は、途中から再開しない。作業ディレクトリを捨てて、最初からやり直す。やり直しは、記録と一致することを確かめて状態ファイルを引き継ぎ、作業ディレクトリを捨てたあと、状態ファイルの作成の次の手順から行う。
- 保守作業の中で行う検査（新しい環境での作業ディレクトリの場所の検査、入れ替え後の起動時の検査等）は、その作業自身の状態ファイルと作業ディレクトリを除いて行う。入れ替えの段階で止まった作業だけ、記録した名前のディレクトリの有無から段階を判別して、入れ替えを完了するか元に戻す。

**バックアップからの復元:** アプリを停止した状態で、コマンドで行う。ブラウザからは行わない。実データのデータルートへの復元は実利用モードの専用コマンドでだけ行い、承認済みリリースの条件の確認を起動と同じように行う（1の起動モード）。合成データモードのコマンドは、既定のデータルートや`real`のデータルートを復元先にできない。

1. lockを取る。このデータルートの状態ファイルか、検証中の作業ディレクトリ（`<データルート>.restore-*`）があれば、新しい作業を始めずに復旧操作を案内する。データルートがなく`<データルート>.before-restore-*`がある場合も同じ（7と同じ判定）。データルートがある場合の`.before-restore-*`は、完了した復元の保管用なので妨げない。データルートがまだない新しい環境では、作業ディレクトリの場所を、1の「新規作成の手順」の1・2と同じ方法で検査する。そのうえで、データルートを変える前に状態ファイルを作り、作業ディレクトリ`<データルート>.restore-<日時>`を、データルートと同じ親ディレクトリ（同じボリューム）に空で作る。同じボリュームなら、後の名前変更が1回の操作で済む。
2. 復号したtarは、展開する前に全エントリを検査する。
   - 通常のファイルとディレクトリだけを許可する。symlink、hardlink、デバイス等は拒否する。
   - 絶対パス、`..`を含むパス、Windowsのドライブ指定を拒否する。
   - manifestに載っていないパス（固定のパスの`manifest.json`自身を除く）と、サイズの上限を超えるものを拒否する。
   - エントリ数と、展開後の合計サイズにも上限を設ける。展開前に、合計サイズと作業ディレクトリのボリュームの空き容量（余裕を含む）を比べ、足りなければ中止する。大量の小さなエントリでディスクやinodeを使い切り、同じボリュームにある現在のデータルートまで使えなくするのを防ぐため。
   - 1件でも当たれば、何も展開せずに中止する。ハッシュ検証は展開後にしか行えないので、この検査の代わりにならない。
3. 展開後に、1の「共通の初期化」で、作業ディレクトリに欠けている固定の子（`snapshots/`、`tmp/`、`logs/`、`config/`等）を空で作る。DBはアーカイブのものを使い、初期化では作らない。そのうえで、ハッシュ、`PRAGMA integrity_check`、`application_id`、`user_version`と、固定の子の検査（リンクでないこと。いまの構造の版の子が対象）を行う。
4. 復元先の種別はコマンドのモードで決まる（実利用モードなら`real`）。manifestの種別と合わなければ中止する（実データの復元に合成データのアーカイブを使わない。その逆も同じ）。manifestの構造の版がアプリの版より新しければ中止し、新しい版のリリースで復元するよう案内する（知らない子のデータを落とし、構造の版を下げないため）。合えば、作業ディレクトリに種別マーカー（種別と、いまの構造の版）を書く。
5. 入れ替える。
   - 現在のデータルートがない場合（新しい環境への復元）: この作業自身の作業ディレクトリを除き、同じ親ディレクトリに復元・rollbackの途中の退避物がないことを確認してから、作業ディレクトリをデータルートの名前へ変える（名前変更は1回）。変えたあと、実体パスで起動時の検査（この作業自身の状態ファイルを除く）をもう一度行う。
   - 現在のデータルートがある場合: 現在のデータルートを`<データルート>.before-restore-<日時>`へ名前変更して残し（削除しない）、作業ディレクトリをデータルートの名前へ変える。
   - 2回目の名前変更に失敗したら、退避した名前を元に戻す。
   - 元に戻すことにも失敗したら、そこで止め、両方のパスを表示する。どちらも削除しない。
6. 1〜4で失敗した場合は、作業ディレクトリだけを削除する。現在のデータルートには触れない。
7. どの段階で異常終了しても、状態ファイルが残るので、アプリは起動しない。1〜4で止まった場合は、作業ディレクトリを捨てて最初からやり直すか、中止する。5の2回の名前変更の間で止まった場合（データルートの名前のディレクトリがない）は、復元コマンドが、状態ファイルに記録した名前のディレクトリの有無から段階を判別し、入れ替えを完了するか元に戻す。状態ファイルが失われた場合の追加の防御として、同じ親ディレクトリに`.restore-*`（検証中の作業ディレクトリ）がある場合は、データルートの有無にかかわらずアプリを起動しない。データルートがなく`.before-restore-*`がある場合も、新しく作らずに止める。

**migration前の退避からのrollback:** `snapshots/`にあるのはDBだけなので、データルート全体は入れ替えない。DBファイルだけを入れ替える別の手順にする。

SQLiteのDBの状態は、DBファイルと、存在すればjournal（`<DB名>-journal`。WALなら`-wal`・`-shm`）の組で決まる。migrationの途中で異常終了すると、アプリが止まっていてもjournal（hot journal）が残りうる。DBファイルだけを入れ替えると、残った旧journalが次に開いたときに新しいDBへ適用され、壊れうる。そこで、旧DBとjournalを必ず一式で扱い、新しいDBに旧journalを関連付けない。journalだけを削除することもしない（旧DBを復旧する情報が失われる）。

複数のファイルを1つずつ移すと、途中で異常終了したときにDBとjournalが分かれてしまう。そこで、`db/`にはDBファイルとそのjournal類だけを置き、ほかのファイルを置かない。入れ替えは`db/`ディレクトリの名前変更（同じボリューム内の1回の操作）で行い、DBとjournalを常に同じディレクトリに置いたまま動かす。

1. アプリを停止した状態で、コマンドで行う。必要なら、先にADR-0002の手順で前のリリースタグへ戻す。lockを取り、このデータルートの状態ファイルがないことを確かめてから（あれば復旧操作を案内する）、データルートを変える前に状態ファイルを作る。実データのデータルートでは実利用モードの専用コマンドでだけ行い、承認済みリリースの条件を確認する（1の起動モード）。
2. データルート内に作業ディレクトリ`db.rollback-<日時>/`を作る。スナップショットを正式なDB名で複製し、`PRAGMA integrity_check`、`application_id`、`user_version`を検証する。このディレクトリにjournalはない。
3. `db/`を`db.before-rollback-<日時>/`へ名前変更して残す。DBとjournalはディレクトリごと移るので、対は崩れない。旧DBは、後からそのディレクトリで開けば復旧できる。
4. 作業ディレクトリを`db/`へ名前変更する。開いて`PRAGMA integrity_check`を行い、正常に閉じて、journalが残らないことを確認する。
5. 4で失敗した場合は、`db/`を作業ディレクトリの名前へ戻し、`db.before-rollback-<日時>/`を`db/`へ戻す。戻すことにも失敗したら、そこで止めてパスを表示し、何も削除しない。2で失敗した場合は、作業ディレクトリだけを削除する。
6. どの段階で異常終了しても、状態ファイルが残るので、アプリは起動しない。2で止まった場合は、作業ディレクトリを捨てて最初からやり直すか、中止する。3と4の間で止まった場合（`db/`がない）は、rollbackコマンドが、状態ファイルに記録した名前のディレクトリの有無から段階を判別し、入れ替えを完了するか元に戻す。状態ファイルが失われた場合の追加の防御として、`db.rollback-*`（検証中の作業ディレクトリ）がある場合は、`db/`の有無にかかわらずアプリを起動しない。`db/`がなく`db.before-rollback-*`がある場合も、空のDBを作らずに止める。
7. 証憑、設定、種別マーカーには触れない。スナップショットより後に取り込んだ証憑は`evidence/`に残る。DBから参照されなくなっても削除しない（扱いはT07で決める）。

バックアップからの復元では、アーカイブ内のDBは`backup()`等で作った静止状態のファイルで、journalを伴わない（展開前の検査でmanifestにないファイルは拒否する）。旧データルートはjournalごと名前変更して残すので、こちらでもDBとjournalの対は崩れない。

**CSV/JSON出力:**

- データ交換用で、バックアップの代わりにならない。
- 平文なので、出力先は利用者が都度指定する。repo内とデータルート内は拒否し、暗号化されないことを画面で示す。

### 4. 二台間同期を扱わない

- MacとWindowsの間、または同じOSの複数台の間で、同じDBを同期・共有する機能は**提供しない**。データルートをクラウド同期フォルダやネットワークドライブに置く使い方もサポートせず、1の起動時検査で拒否する。
- 別のPCへ移るときは「バックアップ→移行先で復元」の一方向の移行とする。移行後は移行元を使わない運用を手順書で求める。
- 2台で別々に記録した場合は、それぞれ別の台帳として扱う。統合（マージ）機能は作らない。

## 検討した候補

| 論点 | 候補 | 判断 |
| --- | --- | --- |
| DBの置き場所 | OSのユーザー別アプリデータ領域（採用） / checkout内の`data/` / ブラウザのストレージ（OPFS等） / クラウド同期フォルダ | checkout内は誤ってcommitされうる。ブラウザのストレージはプロファイル削除や容量逼迫で消えうるうえ、外からバックアップしにくい。クラウド同期はSQLiteの破損原因になる |
| 実データと開発の分離 | データルートの種別マーカー＋起動方法による検査（採用） / 運用ルールのみ | 開発・試験・AIが同じPCで動くので、ルールだけでは誤って実データを開きうる |
| 保存中の暗号化 | OSの全ディスク暗号化（採用） / SQLCipher等のDB暗号化 | ADR-0005のドライバでは使えず、ネイティブ依存とライセンスの確認が増える。紛失・盗難にはディスク暗号化で対応でき、ログイン中のマルウェアにはどちらも効かない |
| バックアップの暗号化 | age形式（採用） / Node標準cryptoで独自形式 / 7-Zip・ZIPのAES | 独自形式は検証が難しく、ほかの道具で復号できない。Node標準のAES-GCMは、ストリームで復号すると認証タグの確認前に平文が出てくるため、扱いを誤りやすい。外部コマンドへの依存はWindows・Macでの導入手順を増やす |
| 同期 | 対応しない（採用） / クラウドフォルダに置く / 独自の同期 | 競合解決と履歴保持の設計が大きく、初期範囲外（[実装計画](../implementation-plan.md)） |

## 影響

- 利用者は、OSのディスク暗号化、OS全体のバックアップの設定、パスフレーズの管理が必要。手順書（ADR-0002）に含める。
- 開発・試験のコマンドは、合成データのデータルートを明示しないと動かない。
- ログに金額・勤務先・氏名等を出さない。

## 担当と別タスクで行う検証

- T07: 固定の子（`db/`、`evidence/`、`snapshots/`、`tmp/`、`config/`、`logs/`、種別マーカー）をリンクに差し替えたときに開かずに終了すること、単一起動のlock（データルートの外の`<データルート>.lock`、親ディレクトリがない場合に作らずに終了すること、symlink・junction・大文字小文字の違う別名で同じデータルートを指定した2つのプロセスが同じlockで競合すること、2つ目の起動・保守コマンドが失敗すること、強制終了のあとに次の起動でlockを取れること、表示用のPIDファイルが残っていても判定に影響しないこと、lockファイルや状態ファイルをsymlink・junctionに差し替えたときに開かずに終了し、リンク先を変更しないこと、同じ名前の別のファイル（ほかの用途のSQLiteのDBを含む）があるときに変更せずに終了すること、lockファイルを作る各段階（一時名の作成、識別子の書込み、反映、正式な名前への変更）で強制終了しても、次の起動でlockを取れること、ほかのユーザーが書き込める親ディレクトリ（共有フォルダ、stickyビットだけの`/tmp`の直下等）を拒否すること、新規作成・共通の初期化・構造のmigrationで作るデータルートと固定の子が本人だけの権限になること、データルートや`tmp/`の権限が広いときに開かずに終了すること）、データルートの検査（Git作業ツリー、クラウド同期フォルダ、ネットワークドライブ、種別マーカー）と新規作成の手順、lock、欠けたデータルートやDBを作り直さないこと、migration前の退避と`db/`ディレクトリの入れ替えによるrollback（各段階の異常終了からの再開・巻戻しを含む）。symlink・junctionによる回避、解決できないパス、完全な新規環境での作成の成功、新規作成の各段階で異常終了してもデータルートの名前に中途半端なディレクトリが残らないこと、残った`<データルート>.create-*`（アプリが作ったものでないものを含む）を自動で削除せずに止まり、利用者が削除したあとでやり直せること、禁止先を指すリンクを祖先に含むパスの拒否、作成直後のリンクへの差し替え、復元途中の退避物や状態ファイルがあるときに新規作成しないこと、固定の子を作る共通の初期化（新規作成の側）、構造の版（増えた子だけを作るmigration、前のリリースが新しい版のデータルートを開けて版を下げないこと）、lockを取ったあとの状態ファイルの再確認、復旧操作が欠けた子を作り直さずに段階を判別できること、Windowsの長いパス、日本語パス、OneDriveのフォルダリダイレクトを含めて試験する。rollbackでは、migration途中の強制終了でhot journalが残った状態からスナップショットへ戻して開き直す試験と、途中で失敗したときに旧DBとjournalの対が保たれる試験を行う。rollbackのどの段階で異常終了しても状態ファイルによりアプリが起動せず、やり直し・中止・入れ替えの完了ができることも試験する。状態ファイルを原子的かつ確実に書く方法を決め、書込みの各点での異常終了、壊れた・読めない状態ファイル、状態ファイルが失われて`db.rollback-*`だけが残った場合に起動しないことを試験する。
- T09: 起動モードと承認済みリリースの確認の共通の仕組み。`start:real`に適用し、T07のrollbackの中核の処理をコマンド（`rollback`と`rollback:real`）として公開する。開発branchや変更のある作業ツリー、手元に作っただけのタグ、originが信頼するリポジトリでないcloneから実データを開けないことを試験する。開発時の起動も同じ検査（ADR-0007のG1〜G5）に通し、実データのデータルートを開かないことを試験する。
- T12: アーカイブ（tar＋age）、パスフレーズの生成と最低長、作成直後の検証、世代管理、復元のコマンド、保守コマンドの起動モード（originが信頼するリポジトリでないcloneから実データを扱えないこと、`:real`の付かないコマンドが既定・`real`のデータルートを開かないこと、開発branchや変更のある作業ツリー、手元に作っただけのタグから実データの復元・バックアップ・出力ができないこと）、バックアップ保存先とCSV/JSON出力先のサーバー側の検査（T07のパス解決を使い、実体パスで判定する）。試験には次を含める。
  - 壊れたアーカイブ、未知のフォーマット版、同名の証憑
  - 絶対パス・`..`・symlink・hardlinkを含むエントリ、manifestにないエントリ
  - エントリ数・合計サイズの上限超え、空き容量の不足
  - 入れ替えの途中で異常終了した状態からの再開・巻戻し
  - 状態ファイルの作成・更新の各点での異常終了（書きかけを含む）。壊れた・読めない状態ファイルで起動しないこと。状態ファイルが失われても、`.restore-*`が残っていれば起動しないこと
  - 検証の段階（手順1〜4）で異常終了したとき、状態ファイルによりアプリが起動しないこと。作業ディレクトリを捨てて最初からやり直せること、中止できること、その間に現在のデータルートへの書込みが起きないこと
  - 空の環境と既存の環境への復元で、lockを入れ替えの前後を通して保持し、その間に別のプロセスが起動できないこと。強制終了のあとにlockを取り直せること。Windowsで入れ替えが開いたファイルに妨げられないこと
  - データルートがない新しい環境への復元（Mac→Windows、Windows→Macを含む）
  - 作成中の取込・訂正。参照される証憑が欠けたり変わったりしたときに作成を中止すること
  - `tmp/`や`snapshots/`をリンクに差し替えたとき、スナップショットやアーカイブの作業を始めずに止まること
  - 出力するアーカイブやCSV/JSONのファイル名に、既存のファイルやsymlink・junctionを置いたとき、上書きもリンク先への書込みもせずに止まること
  - 出力の各段階（一時名への書込み、ディスクへの反映、検証、最終名への変更）で中断したとき、最終名に不完全なファイルが残らないこと
  - 世代整理で、記録したファイルが移動・差し替えられていた（別のファイル、リンク、サイズやハッシュの違い）ときに削除しないこと
  - 平文のCSV/JSONの一時ファイルと最終的なファイルが、本人だけが読める権限になること。権限を設定・確認できない場所への出力を拒否すること
  - 復元の作業ディレクトリと、その中に作る固定の子が本人だけの権限になり、アーカイブの中の権限が使われないこと
  - 種別が合わないアーカイブ
  - 入れ替えの各段階での失敗と、元に戻せること
  - 公式`age`と`tar`での手動復元
  - 作ったバックアップが、そのまま自分の検証（manifestを含む展開前の検査とハッシュ）を通ること
  - 記録した構造の版がアプリより新しいデータルートでは、バックアップの作成を行わないこと。manifestの構造の版がアプリより新しいアーカイブの復元を、入れ替えの前に中止すること
  - 復元で、共通の初期化により欠けている固定の子（`config/`を含む）を作ってから検証し、検証とモードの確認のあとで種別マーカーを書くこと。`snapshots/`・`tmp/`・`logs/`・`config/`を含まないバックアップから復元したデータルートが、起動時の検査に通ること
  - 新しい環境への復元が、その作業自身の状態ファイルと作業ディレクトリで止まらないこと。やり直しが状態ファイルを引き継ぐこと
  - 完了した復元の`.before-restore-*`が残っていても、2回目の復元ができること。保管用の退避ディレクトリが複数あっても、復旧操作が状態ファイルに記録した名前のものだけを扱うこと
