# ADR-0006: データ保管先・バックアップ・暗号化・同期の扱い

- 状態: Proposed（このPRがmainに統合された時点でAcceptedとみなす）
- 日付: 2026-10-02
- 関連: T00（Issue #1）、ADR-0002、ADR-0003、ADR-0005。実装はT07・T12・T27、検証はT13・T25。

## 背景

実データ（給与明細、銀行入金、通知書、証憑のPDF・画像）はこのpublic repoのcheckoutに置けない。`.gitignore`は追加の防御にすぎない（[SECURITY.md](../../SECURITY.md)、[architecture.md](../architecture.md)）。さらに、開発用のworktreeとAIも所有者と同じPCで動くため、開発・試験の実行が実データのDBを開かないようにする必要がある（[AGENTS.md](../../AGENTS.md)、[worktree運用](../local-worktrees.md)）。T00では保管先、バックアップ、暗号化と鍵、Mac/Windowsの二台間同期について、扱う範囲と扱わない範囲を決める。

## 決定

### 1. データルート

アプリの全データを1つの「データルート」に置く。

| OS | 実データの既定のデータルート |
| --- | --- |
| macOS | `~/Library/Application Support/KurashiLedger/` |
| Windows | `%LOCALAPPDATA%\KurashiLedger\`（ローミングしない、そのPC専用の領域） |

- パスは決め打ちせず、OSのホームディレクトリや`%LOCALAPPDATA%`から求める。
- この2つは、OneDriveの既知フォルダー移動（デスクトップ、ドキュメント、ピクチャ等）とiCloudの「デスクトップと書類」の同期対象外。macOSでファイルアクセスの許可を求められる場所（書類、デスクトップ、ダウンロード、iCloud Drive等）にも当たらない。
- 環境変数`KURASHI_LEDGER_HOME`（または起動時の引数）で別の場所を指定できる。指定先も同じ規則で検査する。

**実データと合成データの分離:**

- データルートは作成時に種別（`real`または`synthetic`）を記録したマーカーファイルを持つ。
- **起動モード**を明示的に分ける。どちらのモードかを、データルートの指定の有無から推測しない。このモードの区別は、アプリの起動だけでなく、データルートを開くすべてのコマンド（バックアップの作成、復元、rollback、CSV/JSON出力等の保守コマンド）に同じように適用する。
  - **実利用モード:** 専用のコマンド（起動は`npm run start:real`、保守コマンドも`restore:real`のように`:real`の付いた専用のもの）でだけ選べる。既定のデータルート、または`KURASHI_LEDGER_HOME`で指定した`real`のデータルートを開く。次の「承認済みリリース」の条件をすべてGitで確認できなければ、起動しない。開発用のworktreeやAIの作業branchから実行しても、実データを開かないようにするため。
    - HEADが、リリースの名前の規則（`vX.Y.Z`、試験用は`vX.Y.Z-rc.N`）に合う注釈付きタグのcommitと一致し、作業ツリーに変更がない。
    - そのcommitが`origin/main`から到達できる（レビューとマージを経てmainに入っている）。
    - 同じ名前のタグがoriginにあり、指す先が手元のタグと同じ。起動時に`git ls-remote`でoriginと照合する。照合できたタグの名前とobject IDはデータルートに記録し、オフラインのときは記録済みのタグだけを認める。初めてのタグをオフラインで使おうとした場合は起動しない。
    - 作業branchで手元に作っただけのタグ（originにない、または`origin/main`から到達できないcommitを指すもの）は認めない。
    - 署名付きタグの検証は、T25でリリース手順を正式にするときに採否を決める。
  - **合成データモード:** それ以外の起動と保守コマンドはすべてこのモード（`npm start`、`:real`の付かない保守コマンド、開発サーバー、試験、E2E、AIの作業）。`KURASHI_LEDGER_HOME`等で明示した`synthetic`のデータルート（試験ごとの一時ディレクトリを含む）だけを開く。指定がなければ、既定のデータルートへ切り替えずに終了する（fail closed）。既定のデータルートと`real`のデータルートは開かない。
- データルートの新規作成は、そのモードの初回起動で、確認を求めてから行う。手順は下の「新規作成の手順」に従う。既存のデータルートの一部（`db/`や種別マーカー等）が欠けていても、空のものを作り直さない（3の復元・rollbackが途中で止まった状態を壊さないため）。
- 実利用は、開発用のworktreeとは別の利用専用のcloneから行う（ADR-0002）。

**起動時の検査:** 次のどれかに当たれば、DBを開かずに理由を表示して終了する。判定は既知のパスやOSの情報による発見的なものなので、`.gitignore`と同じく追加の防御として扱う。

- データルートがGitの作業ツリー内（上位にリポジトリのメタデータがある）またはアプリのcheckout内にある。
- データルートがクラウド同期フォルダ内（iCloud Drive、OneDrive、Dropbox、Google Drive等）にある。
- データルートがネットワークドライブ上にある（WindowsのUNCパスと割り当てたネットワークドライブ、macOSのネットワークボリューム。判定できる範囲で）。
- 種別のマーカーが起動方法と合わない（上の分離の規則）。
- 復元やrollbackの作業中を示す状態ファイル（3の「保守作業の状態ファイル」）が残っている。

検査は、指定されたパスの字面ではなく、symlinkやWindowsのjunction等（reparse point）を解決した実体のパスと、その祖先すべてに対して行う。字面だけで判定すると、checkoutや同期フォルダを指すリンクを別の名前で指定して回避できてしまうため。既存のデータルートの実体パスを解決できない場合は、開かずに終了する（fail closed）。まだ存在しないデータルートは、次の「新規作成の手順」で扱う。

**新規作成の手順:** 指定（または既定）のデータルートのパスが存在しない場合だけ、新規作成として扱う。

1. パスの祖先のうち、存在する最も近いものを実体パスに解決する。解決できなければ終了する。
2. 解決した祖先と作成予定のパスについて、上の起動時の検査（Git作業ツリー・checkout内、クラウド同期フォルダ、ネットワークドライブ、デスクトップ・書類は確認つき）を行う。
3. 同じ親ディレクトリに、復元・rollbackの途中の退避物（`.before-restore-*`、`.restore-*`）があれば、新規作成として扱わずに止める。復元コマンドでの再開か巻戻しを案内する。
4. 利用者の確認を得て、lockを取ってから、データルートと同じ親ディレクトリに作業ディレクトリ`<データルート>.create-<日時>`を作る。作ったパスを実体パスに解決し直して、2の検査をもう一度行う。作成と検査の間にリンクへ差し替えられた場合も、ここで止まる。
5. 作業ディレクトリの中に、種別マーカーと`db/`等を作り終えてから、作業ディレクトリをデータルートの名前へ1回の名前変更で置く。置いたあと、実体パスでもう一度検査する。DBと証憑への書込みは、そのあとに行う。
6. 途中で失敗・中断した場合、データルートの名前のディレクトリはできていない（中途半端なデータルートは残らない）。残った`<データルート>.create-*`には利用者のデータが入っていないので、次の新規作成のときに削除してからやり直す。中止する場合も削除するだけでよい。

データルートが存在するのに種別マーカーがない、または中身が欠けている場合は、新規作成として扱わずに止める。

**保存先と出力先:** バックアップの保存先とCSV/JSONの出力先も、データルートと同じ方法（実体パスとその祖先）で検査する。アプリはこれらのディレクトリを作らない。存在しなければ拒否するので、利用者がOSで作ってから指定する。

デスクトップ・書類（ドキュメント）配下は、OSの設定次第でクラウドへ同期される。利用者が明示的に確認しない限り使わない。

**構成（案。T07・T12で確定）:** `db/`（SQLiteのDBファイルとそのjournal類だけを置く。3のrollbackを参照）、`evidence/`（証憑の複製）、`snapshots/`（migration前の自動退避）、`tmp/`（スナップショットやアーカイブの作業用）、`config/`、`logs/`、種別のマーカー。単一起動用のlockファイルは、下のとおりデータルートの外に置く。

**単一起動のlock:** 同じデータルートを2つのプロセスが同時に使わないようにする。

- lockファイルの場所は、指定された文字列ではなく、データルートの正規化した実体パスから決める。symlinkやjunction、大文字小文字の違う別名で同じデータルートを指定しても、同じlockになるようにするため。既存のデータルートは実体パスを使う。未作成のデータルートは、存在する最も近い祖先の実体パスに、残りの要素を正規化してつなげたものを使う。大文字小文字を区別しないファイルシステムでは、OSが返す正規の表記にそろえる（各OSの挙動はT07で確かめる）。
- lockファイルは、その正規のパスの親ディレクトリ、つまりデータルートの外に置く（`<データルート>.lock`。例: `~/Library/Application Support/KurashiLedger.lock`）。データルートの作成・復元での入れ替え・rollbackに影響されず、同じデータルートに対して常に同じlockを使える。空の環境でも、データルートを作る前にlockを取れる。親ディレクトリがなければ、新規作成の手順に従って親を作ってからlockを取る。lockファイルがデータルートの外にあるので、Windowsでも開いたlockファイルがデータルートの名前変更を妨げない。
- lockは、OSのファイルロックで取る。OSのファイルロックは、プロセスが終われば（強制終了を含む）OSが自動で解放するので、古いlockが残って起動できなくなることがない。PIDの再利用にも影響されない。実装は、このlockファイルを`node:sqlite`で開き、排他lockを保持し続ける方法を第一候補とし、T07で確定する。
- lockの取得は、1回の原子的な操作で行う。取れなければ、別のプロセスが生きているとみなして終了する。生きているかを確認できない場合も、lockを奪わない。
- PIDや起動時刻を書いたファイルは、利用者への表示のためだけに使い、lockの判定には使わない。
- 復元・rollback等の保守コマンドも同じlockを取り、入れ替えの前後を通して保持し続ける。アプリの起動中は実行できず、保守コマンドの実行中はアプリを起動できない。
- 入れ替え（名前変更）の前に、データルートと作業ディレクトリの中で開いているファイル（DBの接続を含む）をすべて閉じる。Windowsでは、中のファイルが開いているとディレクトリの名前を変えられないため。

- 一時ファイルはOSの一時フォルダではなく、データルートの`tmp/`に置き、失敗時にも削除する。
- 証憑は元ファイルの場所を参照せず、データルート内へ複製する。DBにはハッシュ、元のファイル名、取込日時を記録する。ファイル名に個人情報が入りうるので、保存名はハッシュ等に基づく名前にする。
- 証憑ファイルは書き換えない。取込では、ファイルを`evidence/`へ書き終えてから、それを参照するDBの記録をcommitする。DBから参照されている証憑ファイルは削除しない。訂正は新しい改訂として記録する。

### 2. 暗号化と鍵

**保存中のDBと証憑:** アプリ独自の暗号化は初期範囲に含めない。OSの全ディスク暗号化を、実データを扱う前提条件とする。アプリから有効かどうかを確実には判定できないため、起動手順の確認項目として扱う。前提を満たせない環境では実データを扱わない。

- macOS: FileVaultを有効にする。Apple siliconやT2のMacは常に暗号化しているが、FileVaultを有効にして初めて、復号にログインパスワードが必要になる。
- Windows: Pro以上はBitLocker、Homeは「デバイスの暗号化」を使う。デバイスの暗号化は、Microsoftアカウント等でサインインしていないと（ローカルアカウントだけでは）、データが暗号化されていても保護されていない状態になる。手順書で注意する。
- ディスク暗号化の回復キーを失うと、PCのデータ全体を失う。アプリのバックアップ（3）とは別に管理する。
- OS全体のバックアップにも注意する。macOSのTime MachineはmacOSに付属しないファイルをバックアップするので、対象から外さない限りデータルートも含まれる。暗号化したバックアップディスクを使うか、データルートを対象から外す。ほかの全体バックアップの道具も同様に扱う。

**アプリのバックアップ:** 外付けドライブやクラウドフォルダなど、PCの外へ持ち出されるので、必ず暗号化する。

**鍵（パスフレーズ）:**

- 既定では、アプリが十分な長さのランダムなパスフレーズを生成して提示する。利用者が自分で決める場合は最低の長さを設け、短いものは受け付けない（長さはT12で決める）。クラウドフォルダに置いたアーカイブは、オフラインで総当たりされうるため。
- パスフレーズはアプリ・DB・設定ファイル・repo・ログに保存しない。パスワードマネージャー等で利用者が管理する。
- **パスフレーズを失うと、そのバックアップは復元できない。** これを手順書と画面に明記する。パスフレーズを変えても既存のバックアップは再暗号化しない（古いパスフレーズが引き続き必要）。

**暗号形式:** 独自の暗号形式は作らない。公開仕様があり、相互運用できる実装を持つ形式として、**age形式**を使う。パスフレーズモードはscryptで鍵を導出し、本体はChaCha20-Poly1305で暗号化する。

- 公式のコマンドラインツール`age`（Go、BSD-3-Clause）でも復号できる。このアプリが動かなくなってもバックアップを取り出せる。
- アプリから使う実装は、公式のTypeScript実装typage（npmの`age-encryption`、BSD-3-Clause）を第一候補にする。2026-10-02時点で0.3系（1.0前）で、監査の有無は確認できていない。T12で、公式`age`との相互復号、scryptの作業係数、ストリーム処理を試験してから確定する。

### 3. バックアップと復元

**中身:**

- DBの一貫したスナップショット（`node:sqlite`の`backup()`または`VACUUM INTO`。使用中のDBファイルをそのままコピーしない。ADR-0005）。
- 証憑。
- 制度データ（rules）とそのmanifest。
- manifest（フォーマット版、アプリ版（commit）、スキーマ版、制度データ版、計算エンジン版、データルートの種別（`real`/`synthetic`）、各ファイルのパスとハッシュ、作成日時）。計算エンジンのコードは、記録したcommitのリリースタグから取得する。
  - manifestは、アーカイブの最上位の固定のパス（`manifest.json`）に置く。自分自身はハッシュの一覧に含めない。manifest自体の改ざんは、age形式の認証付き暗号で、復号の時点で検出する。
- `snapshots/`、`tmp/`、`logs/`は含めない。

**形式:**

- 中身をtar形式にまとめ、age形式で暗号化する。公式の`age`で復号すれば、macOSとWindows（Windows 10の2018年以降の版）に標準で入っている`tar`で展開できる。
- tarを作るライブラリの選定とライセンスの確認はT12で行う。

**作成:**

- 保存先は利用者が設定するデータルート外のディレクトリ。ブラウザはサーバーにファイルシステムのパスを渡せないので、設定画面のパス入力か設定ファイルで指定し、サーバー側で検査する。repo内とデータルート内は拒否する。暗号化済みなので、外付けドライブもクラウドフォルダも可。
- 作成は利用者の操作（画面またはコマンド）で行う。前回から一定期間が過ぎたら起動時に促す（期間の初期値はT27で決める）。
- **一貫性:** アーカイブは、DBスナップショットの時点を基準にそろえる。アプリの稼働中に取込や訂正が入っても、DBが参照する証憑がアーカイブに欠けないようにする。
  1. DBスナップショットを取る間だけ、アプリは状態を変える要求を受け付けない（単一プロセスなので、プロセス内の書込みロックで止める。画面には作成中であることを示す）。スナップショットが済んだら書込みを再開する。
  2. アーカイブに入れる証憑と制度データは、ディレクトリの一覧からではなく、スナップショットが参照しているものから決める。証憑は書き換えず、DBのcommitより先に書き終えているので（1を参照）、参照されているファイルは必ず存在し、内容も変わらない。
  3. アーカイブへ入れるときに各ファイルのハッシュを計算し、スナップショットに記録されたハッシュと照合する。1件でも合わないか欠けていれば、作成を中止する。
  4. スナップショットより後に取り込まれた証憑は、そのバックアップに含めない（次のバックアップに入る）。
- 作成直後に、まだ手元にあるパスフレーズで復号してハッシュを照合する。成功したものを「検証済み」としてデータルートに記録する。
- 世代管理の初期値は「直近10世代と、各月末の最新を12か月分」。削除するのは、アプリが作成して記録したファイルだけ。最新の検証済みバックアップは自動では消さない。

**migration前の退避:** スキーマを更新する前に、自動で`snapshots/`へ非暗号のスナップショットを作る（DBと同じくディスク暗号化で保護）。直近3世代を残す。migrationの一部としてT07で実装する。

**保守作業の状態ファイル:** 復元とrollbackは、データルートを変える前に、lockファイルと同じ親ディレクトリに状態ファイル（`<データルート>.maintenance`）を作り、作業の種類と段階を記録する。

- 状態ファイルの作成と段階の更新は、原子的に、かつディスクに確実に残る形で行い、それが済んでからデータルートを変える。書込みの途中で強制終了や電源断が起きても、古い内容か新しい内容のどちらかが残り、空や書きかけの状態にならないようにするため。具体的な方法（一時ファイルへの書込みとfsync、名前変更、ディレクトリのfsync等）と、各更新点での異常終了の試験は、T07・T12で決める。
- 状態ファイルが読めない、壊れている、内容が分からない場合は、アプリも保守コマンドも起動しない（fail closed）。復旧は、利用者が内容を確かめて行う。

- 状態ファイルがある間は、アプリと、新しい保守作業（別の復元・rollback・バックアップの作成・出力等）は起動しない（起動時の検査）。復元・rollbackのどの段階で異常終了しても、作業ディレクトリが残ったまま通常起動して書き込み、そのあとの再開で新しい書込みを退避して見失う、ということが起きないようにするため。
- 例外として、状態ファイルに記録された作業そのものを片付ける**復旧操作**（やり直し、入れ替えの完了、元に戻す、中止）だけは、同じlockを取って実行できる。復旧操作は、状態ファイルに記録された作業の種類・対象のデータルート・段階が、指定した操作と一致することを確かめてから行う。種類や対象が違えば実行しない。
- 状態ファイルを消すのは、作業が完了したとき（完了後に残す`.before-restore-*`や`db.before-rollback-*`は、保管用で起動を妨げない）と、利用者が明示的に中止したときだけ。
- 中止では、作業ディレクトリを削除し、入れ替えの途中なら元に戻してから状態ファイルを消す。
- 検証の段階（入れ替えより前）で止まった作業は、途中から再開しない。作業ディレクトリを捨てて、最初からやり直す。入れ替えの段階で止まった作業だけ、ディレクトリの有無から段階を判別して、入れ替えを完了するか元に戻す。

**バックアップからの復元:** アプリを停止した状態で、コマンドで行う。ブラウザからは行わない。実データのデータルートへの復元は実利用モードの専用コマンドでだけ行い、承認済みリリースの条件の確認を起動と同じように行う（1の起動モード）。合成データモードのコマンドは、既定のデータルートや`real`のデータルートを復元先にできない。

1. lockを取ってから、データルートを変える前に状態ファイルを作る。作業ディレクトリ`<データルート>.restore-<日時>`を、データルートと同じ親ディレクトリ（同じボリューム）に空で作る。同じボリュームなら、後の名前変更が1回の操作で済む。データルートがまだない新しい環境では、作業ディレクトリの場所を、1の「新規作成の手順」の1〜3と同じ方法で検査してから作る。
2. 復号したtarは、展開する前に全エントリを検査する。
   - 通常のファイルとディレクトリだけを許可する。symlink、hardlink、デバイス等は拒否する。
   - 絶対パス、`..`を含むパス、Windowsのドライブ指定を拒否する。
   - manifestに載っていないパス（固定のパスの`manifest.json`自身を除く）と、サイズの上限を超えるものを拒否する。
   - エントリ数と、展開後の合計サイズにも上限を設ける。展開前に、合計サイズと作業ディレクトリのボリュームの空き容量（余裕を含む）を比べ、足りなければ中止する。大量の小さなエントリでディスクやinodeを使い切り、同じボリュームにある現在のデータルートまで使えなくするのを防ぐため。
   - 1件でも当たれば、何も展開せずに中止する。ハッシュ検証は展開後にしか行えないので、この検査の代わりにならない。
3. 展開後に、ハッシュ、`PRAGMA integrity_check`、`application_id`、`user_version`を検証する。
4. manifestの種別から、データルートの種別マーカーを作り直す。復元先の種別はコマンドのモードで決まり（実利用モードなら`real`）、manifestと合わなければ中止する（実データの復元に合成データのアーカイブを使わない。その逆も同じ）。
5. 入れ替える。
   - 現在のデータルートがない場合（新しい環境への復元）: 同じ親ディレクトリに復元・rollbackの途中の退避物がないことを確認してから、作業ディレクトリをデータルートの名前へ変える（名前変更は1回）。変えたあと、実体パスで起動時の検査をもう一度行う。
   - 現在のデータルートがある場合: 現在のデータルートを`<データルート>.before-restore-<日時>`へ名前変更して残し（削除しない）、作業ディレクトリをデータルートの名前へ変える。
   - 2回目の名前変更に失敗したら、退避した名前を元に戻す。
   - 元に戻すことにも失敗したら、そこで止め、両方のパスを表示する。どちらも削除しない。
6. 1〜4で失敗した場合は、作業ディレクトリだけを削除する。現在のデータルートには触れない。
7. どの段階で異常終了しても、状態ファイルが残るので、アプリは起動しない。1〜4で止まった場合は、作業ディレクトリを捨てて最初からやり直すか、中止する。5の2回の名前変更の間で止まった場合（データルートの名前のディレクトリがない）は、復元コマンドがディレクトリの有無から段階を判別し、入れ替えを完了するか元に戻す。状態ファイルが失われた場合の追加の防御として、同じ親ディレクトリに`.restore-*`（検証中の作業ディレクトリ）がある場合は、データルートの有無にかかわらずアプリを起動しない。データルートがなく`.before-restore-*`がある場合も、新しく作らずに止める。

**migration前の退避からのrollback:** `snapshots/`にあるのはDBだけなので、データルート全体は入れ替えない。DBファイルだけを入れ替える別の手順にする。

SQLiteのDBの状態は、DBファイルと、存在すればjournal（`<DB名>-journal`。WALなら`-wal`・`-shm`）の組で決まる。migrationの途中で異常終了すると、アプリが止まっていてもjournal（hot journal）が残りうる。DBファイルだけを入れ替えると、残った旧journalが次に開いたときに新しいDBへ適用され、壊れうる。そこで、旧DBとjournalを必ず一式で扱い、新しいDBに旧journalを関連付けない。journalだけを削除することもしない（旧DBを復旧する情報が失われる）。

複数のファイルを1つずつ移すと、途中で異常終了したときにDBとjournalが分かれてしまう。そこで、`db/`にはDBファイルとそのjournal類だけを置き、ほかのファイルを置かない。入れ替えは`db/`ディレクトリの名前変更（同じボリューム内の1回の操作）で行い、DBとjournalを常に同じディレクトリに置いたまま動かす。

1. アプリを停止した状態で、コマンドで行う。必要なら、先にADR-0002の手順で前のリリースタグへ戻す。lockを取ってから、データルートを変える前に状態ファイルを作る。実データのデータルートでは実利用モードの専用コマンドでだけ行い、承認済みリリースの条件を確認する（1の起動モード）。
2. データルート内に作業ディレクトリ`db.rollback-<日時>/`を作る。スナップショットを正式なDB名で複製し、`PRAGMA integrity_check`、`application_id`、`user_version`を検証する。このディレクトリにjournalはない。
3. `db/`を`db.before-rollback-<日時>/`へ名前変更して残す。DBとjournalはディレクトリごと移るので、対は崩れない。旧DBは、後からそのディレクトリで開けば復旧できる。
4. 作業ディレクトリを`db/`へ名前変更する。開いて`PRAGMA integrity_check`を行い、正常に閉じて、journalが残らないことを確認する。
5. 4で失敗した場合は、`db/`を作業ディレクトリの名前へ戻し、`db.before-rollback-<日時>/`を`db/`へ戻す。戻すことにも失敗したら、そこで止めてパスを表示し、何も削除しない。2で失敗した場合は、作業ディレクトリだけを削除する。
6. どの段階で異常終了しても、状態ファイルが残るので、アプリは起動しない。2で止まった場合は、作業ディレクトリを捨てて最初からやり直すか、中止する。3と4の間で止まった場合（`db/`がない）は、rollbackコマンドがディレクトリの有無から段階を判別し、入れ替えを完了するか元に戻す。状態ファイルが失われた場合の追加の防御として、`db.rollback-*`（検証中の作業ディレクトリ）がある場合は、`db/`の有無にかかわらずアプリを起動しない。`db/`がなく`db.before-rollback-*`がある場合も、空のDBを作らずに止める。
7. 証憑、設定、種別マーカーには触れない。スナップショットより後に取り込んだ証憑は`evidence/`に残る。DBから参照されなくなっても削除しない（扱いはT07で決める）。

バックアップからの復元では、アーカイブ内のDBは`backup()`等で作った静止状態のファイルで、journalを伴わない（展開前の検査でmanifestにないファイルは拒否する）。旧データルートはjournalごと名前変更して残すので、こちらでもDBとjournalの対は崩れない。

**CSV/JSON出力:**

- データ交換用で、バックアップの代わりにならない。
- 平文なので、出力先は利用者が都度指定する。repo内は拒否し、暗号化されないことを画面で示す。

### 4. 二台間同期を扱わない

- MacとWindowsの間、または同じOSの複数台の間で、同じDBを同期・共有する機能は**提供しない**。データルートをクラウド同期フォルダやネットワークドライブに置く使い方もサポートせず、1の起動時検査で拒否する。
- 別のPCへ移るときは「バックアップ→移行先で復元」の一方向の移行とする。移行後は移行元を使わない運用を手順書で求める。
- 2台で別々に記録した場合は、それぞれ別の台帳として扱う。統合（マージ）機能は作らない。

## 検討した候補

| 論点 | 候補 | 判断 |
| --- | --- | --- |
| DBの置き場所 | OSのユーザー別アプリデータ領域（採用） / checkout内の`data/` / ブラウザのストレージ（OPFS等） / クラウド同期フォルダ | checkout内は誤ってcommitされうる。ブラウザのストレージはプロファイル削除や容量逼迫で消えうるうえ、外からバックアップしにくい。クラウド同期はSQLiteの破損原因になる |
| 実データと開発の分離 | データルートの種別マーカー＋起動方法による検査（採用） / 運用ルールのみ | 開発・試験・AIが同じPCで動くので、ルールだけでは誤って実データを開きうる |
| 保存中の暗号化 | OSの全ディスク暗号化（採用） / SQLCipher等のDB暗号化 | ADR-0005のドライバでは使えず、ネイティブ依存とライセンスの確認が増える。紛失・盗難にはディスク暗号化で対応でき、ログイン中のマルウェアにはどちらも効かない |
| バックアップの暗号化 | age形式（採用） / Node標準cryptoで独自形式 / 7-Zip・ZIPのAES | 独自形式は検証が難しく、ほかの道具で復号できない。Node標準のAES-GCMは、ストリームで復号すると認証タグの確認前に平文が出てくるため、扱いを誤りやすい。外部コマンドへの依存はWindows・Macでの導入手順を増やす |
| 同期 | 対応しない（採用） / クラウドフォルダに置く / 独自の同期 | 競合解決と履歴保持の設計が大きく、初期範囲外（[実装計画](../implementation-plan.md)） |

## 影響

- 利用者は、OSのディスク暗号化、OS全体のバックアップの設定、パスフレーズの管理が必要。手順書（ADR-0002）に含める。
- 開発・試験のコマンドは、合成データのデータルートを明示しないと動かない。
- ログに金額・勤務先・氏名等を出さない。

## 担当と別タスクで行う検証

- T07: 単一起動のlock（データルートの外の`<データルート>.lock`、symlink・junction・大文字小文字の違う別名で同じデータルートを指定した2つのプロセスが同じlockで競合すること、2つ目の起動・保守コマンドが失敗すること、強制終了のあとに次の起動でlockを取れること、表示用のPIDファイルが残っていても判定に影響しないこと）、データルートの検査（Git作業ツリー、クラウド同期フォルダ、ネットワークドライブ、種別マーカー）と新規作成の手順、rollbackコマンドの起動モード（開発branchや変更のある作業ツリー、手元に作っただけのタグから実データをrollbackできないこと）、lock、欠けたデータルートやDBを作り直さないこと、migration前の退避と`db/`ディレクトリの入れ替えによるrollback（各段階の異常終了からの再開・巻戻しを含む）。symlink・junctionによる回避、解決できないパス、完全な新規環境での作成の成功、新規作成の各段階で異常終了してもデータルートの名前に中途半端なディレクトリが残らず、残った作業ディレクトリを削除してやり直せること、禁止先を指すリンクを祖先に含むパスの拒否、作成直後のリンクへの差し替え、復元途中の退避物があるときに初期化しないこと、Windowsの長いパス、日本語パス、OneDriveのフォルダリダイレクトを含めて試験する。rollbackでは、migration途中の強制終了でhot journalが残った状態からスナップショットへ戻して開き直す試験と、途中で失敗したときに旧DBとjournalの対が保たれる試験を行う。rollbackのどの段階で異常終了しても状態ファイルによりアプリが起動せず、やり直し・中止・入れ替えの完了ができることも試験する。状態ファイルを原子的かつ確実に書く方法を決め、書込みの各点での異常終了、壊れた・読めない状態ファイル、状態ファイルが失われて`db.rollback-*`だけが残った場合に起動しないことを試験する。
- T12: アーカイブ（tar＋age）、パスフレーズの生成と最低長、作成直後の検証、世代管理、復元のコマンド、保守コマンドの起動モード（`:real`の付かないコマンドが既定・`real`のデータルートを開かないこと、開発branchや変更のある作業ツリー、手元に作っただけのタグから実データの復元・バックアップ・出力ができないこと）、バックアップ保存先とCSV/JSON出力先のサーバー側の検査（T07のパス解決を使い、実体パスで判定する）。試験には次を含める。
  - 壊れたアーカイブ、未知のフォーマット版、同名の証憑
  - 絶対パス・`..`・symlink・hardlinkを含むエントリ、manifestにないエントリ
  - エントリ数・合計サイズの上限超え、空き容量の不足
  - 入れ替えの途中で異常終了した状態からの再開・巻戻し
  - 状態ファイルの作成・更新の各点での異常終了（書きかけを含む）。壊れた・読めない状態ファイルで起動しないこと。状態ファイルが失われても、`.restore-*`が残っていれば起動しないこと
  - 検証の段階（手順1〜4）で異常終了したとき、状態ファイルによりアプリが起動しないこと。作業ディレクトリを捨てて最初からやり直せること、中止できること、その間に現在のデータルートへの書込みが起きないこと
  - 空の環境と既存の環境への復元で、lockを入れ替えの前後を通して保持し、その間に別のプロセスが起動できないこと。強制終了のあとにlockを取り直せること。Windowsで入れ替えが開いたファイルに妨げられないこと
  - データルートがない新しい環境への復元（Mac→Windows、Windows→Macを含む）
  - 作成中の取込・訂正。参照される証憑が欠けたり変わったりしたときに作成を中止すること
  - 種別が合わないアーカイブ
  - 入れ替えの各段階での失敗と、元に戻せること
  - 公式`age`と`tar`での手動復元
  - 作ったバックアップが、そのまま自分の検証（manifestを含む展開前の検査とハッシュ）を通ること
- T27: バックアップの設定・作成・検証済み一覧の画面、起動時の催促（期間の初期値を含む）、CSV/JSON出力の操作。2026-10-02の所有者決定を受けて台帳に追加した（T12の範囲はinfrastructureと復元手順で、UIを含まないため）。
- T13・T25: 新規環境と別OS（Mac→Windows、Windows→Mac）への復元。パスフレーズを失った場合の限界の説明。
