# 公開範囲と公開前の点検

T02（[Issue #9](https://github.com/doc-gif/kurashi-ledger/issues/9)）の成果物。このリポジトリはpublic。ここに書く規則と検査は、実データを公開しないための追加の防御で、保証ではない。主な境界は「実データのデータルートをリポジトリの外に置き、checkoutの中では起動しない」こと（[ADR-0006](adr/0006-data-location-backup-encryption.md)）。英語の要約は[SECURITY.md](../SECURITY.md)。

## 公開してよいもの・しないもの

| 区分 | 例 | 置き場所 |
| --- | --- | --- |
| 公開する | ソースコード、設定、一般化した要件・設計、出典付きの制度の資料、合成データ、デザイン資産 | このリポジトリ |
| 公開しない | 実際の給与明細・銀行の記録・通知書・源泉徴収票、勤務先・氏名・住所・口座、収入の実額、資格情報・鍵・トークン、実データのスクリーンショット、DB、CSV/JSONの出力、バックアップ（`*.age`を含む）、会話の私的な内容、private repoの具体的な資料やコード | リポジトリの外（実データはデータルート、バックアップは利用者が選んだ保存先） |

- 合成データは、実データの名前や金額を置き換えて作らない。勤務先・日付・正確な金額の組合せだけでも個人を特定できる（[テスト方針](testing.md)）。
- Issue、PR、コメント、CIのログ、artifactにも同じ規則を適用する。

## 合成データとデザイン資産の置き場所

`.gitignore`は、実データになりうる種類のファイル（PDF、画像、CSV、Excel、zip、ログ、鍵、DB、`*.age`等）をどの階層でも除外する。次の場所の、次の種類だけを例外にする。

| 場所 | 許す種類 | 用途 |
| --- | --- | --- |
| `tests/fixtures/` | `.csv`、`.pdf`、`.png`、`.jpg`、`.jpeg` | 合成データのfixture（T03の期待結果、T12の合成の証憑等） |
| `design/` | `.png`、`.jpg`、`.jpeg` | デザインの書き出し・スクリーンショット（T04） |

- `/data/`、`/private/`、`/local-data/`、`/evidence/`、`/exports/`、`/backups/`は、リポジトリ直下だけを除外する。`src/domain/evidence/`のようなソースの置き場所は除外しない。
- 拡張子と`.env`の規則は、`.gitignore`と同じく、パスのどの階層の名前にも当てる（`statements.pdf/readme.md`や`.env/config`も除外する）。
- 実データになりうる名前（上のディレクトリ、拡張子、`.env`）は、大文字小文字を区別しない（`photo.PNG`、`DATA/`等も除外する）。LinuxのGitでも同じになるよう、`.gitignore`では`*.[pP][dD][fF]`のように書く。例外の場所（`tests/fixtures/`、`design/`）は小文字の名前だけ。MacやWindowsのGitは場所の名前の大文字小文字も区別しないので、`Design/`のような名前は`.gitignore`では除外されないことがあるが、公開検査では止まる。
- 例外の場所でも、鍵（`.pem`、`.key`）、`.env`、DB（`.sqlite`、`.db`）、`*.age`、Excel、zip、ログは除外したまま。
- 名前による例外（合成データの場所の拡張子と、`.env.example`）は、1つの規則に従う。例外は**通常のファイルの最後の名前**にだけ当たり、途中のディレクトリやディレクトリの項目（submoduleを含む）には当たらない。合成データの場所の拡張子の例外は、さらに例外の場所（リポジトリ直下の`tests/fixtures/`・`design/`）の下に限る。`tests/fixtures/evidence.pdf/`や`docs/.env.example/`のような、例外の名前に見えるディレクトリは、どこにあっても除外し、その中のファイルも除外する。`.gitignore`では、例外の行のあとに、同じ名前のディレクトリだけを除外し直す行（末尾の`/`）を置く。
- 守る名前はすべてASCIIなので、Unicodeの正規化（NFC・NFD）の違いは生じない。見た目の似た別の文字を使った名前は別の名前として扱い、例外を受けない（`.env.`で始まる名前は除外される）。
- 公開検査（`npm run check:public`）は、同じ規則を`git add -f`で加えたファイルにも適用する。submodule（gitlink）はディレクトリとして扱い、リポジトリ直下の`data`等の名前そのものも止める。
- シンボリックリンク（indexのmode 120000）は、場所・拡張子・リンク先によらず公開しない。例外の場所の中のリンクも止める。リンクをたどる処理がcheckoutの中の非公開のファイルを読む経路になり、Windowsでは設定によって通常のファイルとして取り出されるため。`.gitignore`ではリンクと通常のファイルを区別できないので、公開検査だけが止める。実行可能なファイル（mode 100755）は通常のファイルとして扱う。種類の分からない項目は止める。`.gitignore`と公開検査の規則が食い違わないことは、`scripts/public-policy.test.ts`の見本で確かめる。

### 例外を変える手順

場所や種類を加えるときは、1つのPRで次をそろえ、PRに理由を書く。

1. `.gitignore`の例外の行（`!/tests/fixtures/**/*.[cC][sS][vV]`のような行と、同じ名前のディレクトリを除外し直す`/tests/fixtures/**/*.[cC][sS][vV]/`の行の両方）。
2. `scripts/lib/public-policy.ts`の`SYNTHETIC_LOCATIONS`（`.gitignore`の拡張子は大文字小文字を区別しない書き方にする）。
3. `scripts/public-policy.test.ts`の見本（許す例と、許さない例の両方）。
4. この資料の表。

## 公開前の点検（commitの前）

1. `git status`で、意図しないファイルがないことを確かめる。元checkoutの未追跡の試作や、ほかの作業のファイルを混ぜない。
2. stageするファイルを名前で指定する（`git add .`や`git add -A`を使わない）。
3. `git diff --cached --stat`と`git diff --cached`で、公開する差分をすべて読む。
4. `npm run check:public -- --staged`を実行する（WindowsのPowerShellでは`npm.cmd run check:public -- --staged`）。当たった項目は、中身を確かめて直す。検査を通すためだけに規則や見本を変えない。
5. 例外の場所（`tests/fixtures/`、`design/`）にファイルを加えるときは、次も確かめる。
   - 中身がすべて合成で、実データを置き換えたものでないこと。
   - 画像・PDFのメタデータ（撮影日時・位置情報・作成者・ソフトウェア・元のファイルのパス）に、個人の情報がないこと。必要なら書き出し直して除く。
   - スクリーンショットに、通知、ほかのウィンドウ、ファイルのパス、アカウント名、実データが写っていないこと。
   - ファイル名に、勤務先・氏名・実際の年月と金額などを入れないこと。
6. PRでは、テンプレートの「公開差分に実データ・秘密情報が含まれないことの確認」に、行った点検を書く。

Gitのhookは自動では入れない。hookの設定（`core.hooksPath`）はworktreeの間で共有され、ほかの担当の作業に影響するため。各自が手順の4を実行する。CIでの実行はT05で加える。

### 公開検査が見るもの・見ないもの

- 見るもの: 上の置き場所の規則、indexの項目の種類（シンボリックリンクを止める）、秘密鍵・ageの秘密鍵・主なサービスのトークンやAPIキーらしい文字列、個人の名前を含みうる絶対パス（`/Users/<名前>`、`C:\Users\<名前>`、`/home/<名前>`）、メールアドレス（例示用のドメインを除く）。
- 見ないもの: 金額、勤務先、氏名、住所、口座番号などの個人の事実（パターンでは見分けられない）、バイナリ（画像・PDF）の中身、submodule（gitlink）の参照先の中身（置き場所の規則だけを当てる）、形式の決まっていない秘密情報。検査に通ったことは、公開してよいことの証明にならない。
- 結果に、見つけた文字列そのものは表示しない。環境変数`CI=true`のとき（または`--redact-paths`）は、ファイル名も表示しない。

## 誤って公開したとき

1. 広げない: 同じ内容のpush・PR・コメントを止める。Issueやチャットに漏れた内容を貼り直さない。
2. 資格情報（トークン、鍵、パスワード）: すぐに無効化・再発行する。最新のファイルから消すだけでは足りない。Gitの履歴、fork、clone、キャッシュに残る。
3. 個人情報: 所有者に、漏れたものの種類と場所（ファイル名・commit・PR番号）だけを、非公開の手段で伝える。漏れた内容そのものは書かない。
4. 履歴の書換え（force push）、PRやIssueの削除、GitHubへのキャッシュ削除の依頼は、所有者が判断する。AIは自分で行わない。
5. 原因（点検の手順のどこで漏れたか）を、実データを含めずに記録し、必要なら検査の規則や手順を直すPRを出す。
