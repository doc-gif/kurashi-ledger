# 修正前に過去の指摘との整合を確認する

目的は、指摘数を隠すことではなく、同じ原因の手直しと修正による回帰を減らすこと。製品実装の停止、担当割当、マージ権限は変更しない。所有者が2026-10-02に依頼したレビュー運用の改善として整備する。

## 変更前の手順

1. 最新main・担当Issue・open PRを取得し、変更予定のファイルと対象base SHAを決める。取得失敗なら未確認とする。
2. `tools/review_guard/guard.py prepare`で、該当する不変条件、その関連条件、過去の指摘、確認シナリオを取り出す。対象パスからの選択は補助なので、間接影響があれば予定パス・対象条件を追加する。
3. **コードを直す前に** `.review/plans/<task-id>.json`へ方針を書く。各条件を維持する理由、検証方法、独立した期待結果、既存仕様との衝突を埋める。正常系だけでなく初回・更新・旧版復帰・空環境への復元・既存環境への復元・途中終了・同時実行を通して検討する。対象OSで成立する根拠を示す。
4. 衝突があれば局所修正へ進まず、同じ承認範囲内で操作全体の方針を見直す。条件自体の変更は`change-proposed`として設計判断へ戻す。レビュー指摘は候補であり、採用不要なら理由を残す。異なるレビューを同時に満たせるかも確認する。
5. 整理できた計画を先にcommitしてから実装する。実装後は実際の差分パスで`check`する。base・変更範囲・前提が変われば計画も再確認する。初回導入PRだけは既存の計画基盤がないため、この順序の例外とし、独立レビューを受ける。

`check`の成功は**記入・参照・対象範囲が揃ったことだけ**を示す。方法の妥当性、実行結果、計画を本当に先に考えたか、所有者の承認を証明しない。`not-applicable`にも理由と各シナリオへの説明が必要。AIが文章を埋めただけで実装・マージの許可にしない。

## 正本と信頼境界

| 情報 | 正本 |
| --- | --- |
| 守る仕様・権限 | 最新mainの規約とADR、所有者の明示指示 |
| 過去の原因と教訓 | `.review/findings.json`。現在の解消状態は保持しない |
| 今回の方針 | `.review/plans/<task-id>.json`とそのcommit |
| 最新の解消状態 | 対象head/base付きのGitHubレビュー・引継ぎ・検証結果 |

不変条件は結果の制約であり、過去の修正方法を永久に固定するルールではない。設計が変わる場合は新しい決定と旧判断の置換理由を残す。学習したAIメモリは正本にしない。履歴に載る指摘も、根拠と現在の適用範囲を確認する。

CLIは確認観点の抽出・構造検査・原因キーの照合だけを行う。自由文をコマンドとして実行せず、ネットワーク、GitHub投稿、マージ、アプリDBへのアクセスを行わない。判断・投稿権限は持たない。

CIは導入用テンプレートを用意した段階で、まだ稼働していない（現在の認証にworkflow scopeがない）。ローカルの確認とAIの手順による運用から始める。CIを有効にすると、base側の検査コードと条件でPRの計画を検査する。PR内の条件緩和は、そのPRを通す根拠にしない。提案された条件の構造も検査するが、変更の採用には内容レビューが必要。初回導入時にbaseに検査器がない場合は`bootstrap`として明示し、計画ゲートを検証したと報告しない。

## 同じ指摘を繰り返さない

- 指摘IDはPR内の番号だけでなく`PR2-R007`のようにPR番号を含める。Copilot・Greptile・Codexの同じ原因は同じIDへ対応付け、出典リンクを追記する。
- 同一条件・同一原因を別IDで台帳へ追加すると検査が失敗する。`triage`は原因キーが一致する候補を`update-existing`へ振り分ける。表現違いの意味の照合はレビュワーが行う。
- 同じhead/base・同じ証拠には再投稿しない。新しい差分・再発・別の失敗条件なら、根拠を添えて既存IDを更新する。解消済みという履歴だけで新しい回帰を抑制しない。
- 初回レビューで関連資料と操作全体を一巡し、必要な指摘をまとめて返す。再レビューは修正点とその影響範囲を中心に行う。新たな重大欠陥は報告するが、無関係な改善・文体の好みを追加の完了条件にしない。
- 同じ原因で2回の修正後も解消しない場合は、まず実装を止めて設計の整合確認へ戻す。守る条件・矛盾点・一貫する修正方針を短くまとめる。仕様拡大、費用、権限、両立しない要求など所有者判断が必要な場合だけ、推奨案と2〜3の選択肢・利点・欠点を提示する。
- 文書PRでは、実装で確かめる事項に担当タスクと受入試験があれば、その検証自体を先取りして要求しない。ただし明らかに成立しない操作や矛盾は設計段階で直す。

受入は「必要な欠陥が解消し、残るリスクが明示されたこと」。AIの指摘ゼロや全員一致は品質保証ではない。未解決の重大欠陥を隠すためにseverityを下げたり、checkをskipしたりしない。

## GreptileとほかのAI

`.greptile/files.json`で同じ条件・履歴・手順を参照する。設定は補助レビュー用で、自動起動とauto-approveを無効にしている。設定ファイルを置くだけではGitHub Appの導入や課金を開始しない。利用する場合は、アカウント・料金・対象repoのアクセスを所有者が確認し、まず手動で1 PRを試す。CodexはGreptileの結果も原因単位で統合する。

Greptileの通常設定はPRのsource branchから読み込まれるため、独立承認の代わりにしない。Codex/Claude/Copilotの入口も本手順へリンクし、別々の長い規則を複製しない。[Greptile公式設定](https://www.greptile.com/docs/code-review/greptile-config-reference)、[source branchからの読込](https://www.greptile.com/docs/code-review/greptile-json-reference)（確認: 2026-10-02）。

## 別リポジトリへの移行

`tools/review_guard/`はPython標準ライブラリだけの汎用検査器、`.review/`はkurashi-ledger固有の条件・履歴・計画、`.github/`と`.greptile/`は接続設定とする。税・給与・保険の意味やGitHubのrepo名を検査コードへ埋め込まない。

移行時は検査器とテストだけを別repoへ移し、こちらは条件・履歴・計画を保持する。JSONの`schema_version`とCLI入出力を維持し、検査器はレビュー済みの固定commitで参照する。共有repoのmainを毎回そのまま実行しない。まずコピーまたは固定版のCLIで接続し、複数repoの利用実績が出るまで常駐サービス・DB・汎用DSLを追加しない。公開ライセンスは所有者の未決事項であり、別repo化を再利用許諾とみなさない。

## 効果の確認

次の3 PRで、同一原因の修正往復回数、再発した原因数、計画段階で発見できた矛盾、重複投稿数、所有者への判断依頼数を記録する。単純な指摘総数は成功指標にしない。負担だけが増える項目は、根拠を残して確認条件を見直す。
