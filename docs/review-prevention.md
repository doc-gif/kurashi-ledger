# 修正前に過去の指摘との整合を確認する

目的は、指摘数を隠すことではなく、同じ原因の手直しと修正による回帰を減らすこと。製品実装の再開と各実装者の条件付き自己PRマージは、所有者の決定と[マージ条件の正本](github-agent-operations.md#merge-conditions)に従う。ツールの構造合格だけで権限を与えない。担当済みPRでは作成者と内容レビュワーを分け、実装者に応じてClaude/Codexが役割を交代する。この運用ツールは新しい製品タスクを割り当てない。所有者が2026-10-02に依頼したレビュー運用の改善として整備する。

## 変更前の手順

1. 最新main・担当Issue・open PRを取得し、変更予定のファイルと対象base SHAを決める。取得失敗なら未確認とする。
2. `tools/review_guard/guard.py prepare`で、該当する不変条件、その関連条件、過去の指摘、確認シナリオを取り出す。対象パスからの選択は補助なので、間接影響があれば予定パス・対象条件を追加する。
3. **各修正に取り掛かる前に**、最新の指摘全体（Claude・Codex・Copilot・人）と過去の同じ原因の指摘を照合し、設計そのものが受入条件と両立するか見直す。個々の指摘への局所対応を先に始めない。`.review/plans/<task-id>.json`の方針と回帰を検出する確認条件を照合する。新規作業や方針の変更は計画へ記録する。各条件を維持する理由、変更の影響範囲、検証方法、独立した期待結果、既存仕様との衝突を埋める。過去に直した条件が逆戻りしないかも確認する。正常系だけでなく初回・更新・旧版復帰・空環境への復元・既存環境への復元・途中終了・同時実行を通して検討する。対象OSで成立する根拠を示す。
4. 衝突があれば局所修正へ進まず、同じ承認範囲内で操作全体の方針を見直す。条件自体の変更は`change-proposed`と決定参照を記録して設計判断を確認する。構造検査は参照の記入だけを確かめ、承認の有効性は別担当が確認する。レビュー指摘は候補であり、採用不要なら理由を残す。異なるレビューを同時に満たせるかも確認する。
5. 整理できた計画を先にcommitしてから実装する。実装後は実際の差分パスで`check`する。指摘修正では毎回計画を確認し、base・範囲・前提・方針・検証方法が変わった場合だけ同じ計画を更新して先にcommitする。変化がなければ再確認結果を引継ぎへ記載する。base更新時は取り込み後、既存の評価を保ちつつ影響分だけ修正する。書式と複数PRの命名は[CLI手順](../tools/review_guard/README.md)を参照する。初回導入PRだけは既存の計画基盤がないため、この順序の例外とし、独立レビューを受ける。

`check`の成功は**記入・参照・対象範囲が揃ったことだけ**を示す。方法の妥当性、実行結果、計画を本当に先に考えたか、所有者の承認を証明しない。`not-applicable`にも理由と各シナリオへの説明が必要。AIが文章を埋めただけで実装・マージの許可にしない。

変更された計画ファイル1つは、自己記入を避けるため、未計画パス判定と不変条件のパス選択から除外する。計画だけを変更するPRは、`planned_paths`が空なら選択条件も空となり、名前・task_id・base・書式・衝突の検査を満たせば`metadata-complete`になりうる。これは計画の意味が正しいという判定ではなく、独立した内容レビューが必要。他の`.review/**`（条件・原因台帳・固有試験など）の変更は除外せず、通常どおり条件を選択する。全PRが計画を含むだけでレビュー運用条件を一律に課す設計にはしない。

## 正本と信頼境界

| 情報 | 正本 |
| --- | --- |
| 守る仕様・権限 | 最新mainの規約とADR、所有者の明示指示 |
| 過去の原因と教訓 | `.review/findings.json`。現在の解消状態は保持しない |
| 今回の方針 | `.review/plans/<task-id>.json`とそのcommit |
| 最新の解消状態 | 対象head/base付きのGitHubレビュー・引継ぎ・検証結果 |

不変条件は結果の制約であり、過去の修正方法を永久に固定するルールではない。設計が変わる場合は新しい決定と旧判断の置換理由を残す。学習したAIメモリは正本にしない。履歴に載る指摘も、根拠と現在の適用範囲を確認する。

汎用CLI（`guard.py`・`ci.py`・`changed_paths.py`）は確認観点の抽出・構造検査・原因キーの照合だけを行う。Gitアダプタのみ、信頼したbaseから読み取りのgitコマンドを呼ぶ。自由文をコマンドとして実行せず、ネットワーク、GitHub投稿、マージ、アプリDBへのアクセスを行わない。判断・投稿権限は持たない。T23で加えたPRの巡回の判定は、判定の中核（`patrol.py`。ネットワーク・投稿・実行なし）と、GitHubを読む部分（`github_source.py`。`gh api`のGETだけ。投稿は`--post`を明示したときだけで、既定はdry-run）に分けた。どちらもPRのコードを実行せず、マージしない（[CLI手順](../tools/review_guard/README.md)の「PRの巡回の判定」）。

T05で、テンプレートの計画の検査とツールの試験を、CI（`.github/workflows/ci.yml`の`review plan`・`review tools`）に配置した。base側の検査器と条件を実行するので、そのPRの計画記入にbaseの条件が適用される。ただし`pull_request`のworkflow自体もPRから変更できるので、**この配置だけでは検査の迂回を防げない**。workflow・検査器・条件・台帳の変更に独立レビューを必須にする保護と、迂回試験を別途用意するまでは、強制ゲートとは扱わない。必須のstatus checkを`Quality gate`だけにすることと、「Require branches to be up to date before merging」を有効にすることは、2026-10-03の所有者決定（所有者本人の確認: PR #18のCodexの記録5965890988）で、T05のマージのあとに実装側が設定する。workflow・検査器・条件・原因台帳の変更に独立レビューを必須にする保護と、その迂回試験は、T23で問題と確かめる観点を下の「独立レビューを必須にする保護」にまとめた（具体の設定と手順はIssue #41の確定案を待つ。repoの設定はまだしていない）。必須のstatus checkにしても、この迂回の限界は残る。

候補catalogは構造検査に加え、baseとの条件・シナリオ・paths・関連条件の追加／削除／変更を報告する。意味的な「緩和」の自動判定はしない。台帳変更も表示する。そのPR自身にbaseの記入条件を適用しても、変更をマージすれば次回のbaseは変わるため、差分の採否は別担当が必ずレビューする。初回導入でbaseに検査器がないCIは失敗終了する。ツールを先にmainへ導入してからCIを別PRで配置する。

Gitアダプタはbaseがheadに取り込まれているか確認して三点diffを取る。遅れたbranchは明示的に停止し、他PRのファイルを計画へ加えさせない。CLIの構造検査だけでは実際のGit祖先関係を証明しない。

## 独立レビューを必須にする保護（T23。保留: Issue #41の確定案を待つ）

**状態: 保留。repoの設定は変えていない。** repoの設定は所有者が判断する（[タスク台帳](implementation-tasks.md)のT23）。2026-10-03に所有者は、承認者の身元として、別のユーザーアカウントではなく、CodexとClaudeそれぞれのGitHub Appを選んだ（[Issue #41](https://github.com/doc-gif/kurashi-ledger/issues/41)）。rulesetの具体と迂回試験の手順は、Issue #41で確定する案に対して作る。この節には、特定の設定に依存しない問題と確かめる観点だけを置き、実行用の設定案や手順は置かない。

### 問題

- `pull_request`のworkflowはPR自身が変えられるので、CI（`review plan`等）の合格は、workflow・検査器・条件・原因台帳を変えるPRの迂回を防がない。
- 所有者とAIが同じGitHubアカウントを使う間は、GitHubの承認（Approve）は作者自身にできず、COMMENTのレビュー記録はGitHub上の独立承認にならない。
- AIが使う資格情報に管理者の権限があると、AIもrulesetを外せる・迂回できる。管理者を迂回の一覧に入れると、同じアカウントのAIも迂回できる。

### 迂回試験で確かめる観点（確定案に対して手順にする）

合成の変更だけを使い、マージしない。

1. 保護対象（`.review/patrol.json`の`policy_paths`）を変えるPRは、CIが合格しても、作者と別の身元の承認なしにはマージできない。
2. 作者の身元は自分のPRを承認できない。
3. 管理者の迂回（`--admin`等）で通せない。
4. AIの資格情報でrulesetを変更・削除できない。
5. 承認のあとのpushで承認が無効になる。
6. 保護対象を変えないPRの運用は変わらない。
7. 試験の間に迂回が記録されていない（rulesetの「Rule insights」）。

どれかが成り立たなければ、保護を強制ゲートとして扱わない。

### 設定するまでの扱い

- 保護対象を変えるPRは、巡回の判定（[CLI手順](../tools/review_guard/README.md)の「PRの巡回の判定」）が`policy_files`に一覧にする。レビュー担当は、CIの合格ではなく、その変更そのもの（迂回・条件の緩和がないか）を内容レビューで確かめる。
- 判定の`accepted`・CIの合格・COMMENTの記録を、GitHub上の独立承認や強制ゲートと称さない。

## 同じ指摘を繰り返さない

- 台帳の指摘IDは`PR2-R007`のようにPR番号を含める。既存のPR内表記`R-007`は同じIDの省略形として読み、履歴の採番をやり直さない。新規の共有記録ではPR付きIDを使う。検査器は`PR<正整数>-R<3桁以上の正の番号>`（ASCII数字、PR番号の先頭ゼロなし）のみ受理する。Claude・Codex・Copilotの同じ原因は同じIDへ対応付け、出典リンクを追記する。
- 同一条件・同一原因を別IDで台帳へ追加すると検査が失敗する。原因キーは台帳・候補とも前後空白のない文字列にし、空白のある入力は拒否する。`triage`は原因キーが一致する候補を`update-existing`へ振り分ける。 同じ入力バッチで同一条件・同一原因の候補が重複した場合は、登録済みかどうかにかかわらずバッチ全体を拒否し、部分的な照合結果も出力しない。証拠を1候補へまとめてから再入力する。表現違いの意味の照合はレビュワーが行う。
- 同じhead/base・同じ証拠には再投稿しない。新しい差分・再発・別の失敗条件なら、根拠を添えて既存IDを更新する。解消済みという履歴だけで新しい回帰を抑制しない。
- 初回レビューで関連資料と操作全体を一巡し、必要な指摘をまとめて返す。再レビューは修正点とその影響範囲を中心に行う。新たな重大欠陥は報告するが、無関係な改善・文体の好みを追加の完了条件にしない。
- 同じ原因で2回の修正後も解消しない場合は、まず実装を止めて設計の整合確認へ戻す。守る条件・矛盾点・一貫する修正方針を短くまとめる。設計を見直した後も同じ原因で解決しない場合はneeds-ownerで止める。利用枠不足、完了報告の出し方が不明、仕様拡大、費用、権限、両立しない要求（解消済みの欠陥を再発させる要求を含む）も修正を止めてneeds-ownerとし、推奨案と2〜3の選択肢・利点・欠点を提示する。Copilotは[現行マージ条件](github-agent-operations.md#merge-conditions)で任意とした。Copilotの無応答・利用枠不足だけで停止したり、同じ所有者判断を再度求めたりしない。設計確認を理由に試行回数をリセットせず、外部AI同士の無制限な往復や承認の自己生成を避ける。
- 文書PRでは、実装で確かめる事項に担当タスクと受入試験があれば、その検証自体を先取りして要求しない。ただし明らかに成立しない操作や矛盾は設計段階で直す。

受入は「必要な欠陥が解消し、残るリスクが明示されたこと」。AIの指摘ゼロや全員一致は品質保証ではない。未解決の重大欠陥を隠すためにseverityを下げたり、checkをskipしたりしない。

## Claude・Codex・Copilotの役割

Greptileは採用しない。原因の台帳と事前確認はリポジトリ内で管理し、新しいレビューサービスを契約せずに運用する。

- **変更する担当:** ClaudeまたはCodexが計画→変更→検証を行い、作業中はDraft、レビュー依頼時はOpenのPRと対象SHA付き引継ぎでいったん止め、別担当のレビューを待つ。指摘対応後は新しい引継ぎを出す。別担当の最新head/baseのaccepted後に、[マージ条件の正本](github-agent-operations.md#merge-conditions)を確認して自分のPRだけをマージする。
- **内容を確認する担当:** 差分を作っていない別の担当が、計画・過去の原因・操作全体を確認する。Claudeが実装したPRはCodex、Codexが実装したPRはClaude等へ回す。同じGitHubアカウントのCOMMENTは役割の記録であり、GitHub上の独立承認ではない。
- **Copilot:** 既存設定による補助レビュー。指摘は原因単位で人／担当AIが検証・集約する。Copilotの完了や同意を内容レビューの代わりにしない。
- **所有者:** 承認範囲を超える仕様変更・権限・費用などを判断する。通常の指摘対応で同じ許可を取り直さない。

入口はAGENTS/CLAUDE/Copilotから本手順を参照する。CLIは計画と原因の整理を手伝い、意味の正しさは別担当が確かめる。担当間のコメントも着手許可を新しく発行しない。外部AIの起動や別チャットへの送信は、この仕組みでは行わない。

この運用ツールはT23/T24で再利用する先行成果物であり、そのタスクの受入完了ではない。定期実行の登録・状態確認・停止・API障害への対応は後続タスクの範囲として残す。Actionsテンプレートの配置はT05の共有資源・最小権限・SHA固定に合わせる。

本PRがmainに入る前は既存mainの規約で作業し、このPRの草案を着手許可にしない。導入後は新しい変更の前に計画を作る。すでに作業中のPRは実際の差分から移行用の計画を作って未確認の条件を確認し直す。「実装前に計画済み」と遡って記録しない。後からマージするPRの担当が最新mainを取り込み、停止／再開の最新判断を上書きせず整合を検査する。

## 別リポジトリへの移行

`tools/review_guard/`はPython標準ライブラリだけの汎用検査器、`.review/`はkurashi-ledger固有の条件・履歴・計画、`.github/`とActionsテンプレートはGitHubとの接続設定とする。税・給与・保険の意味やGitHubのrepo名を検査コードへ埋め込まない。

移行時は`tools/review_guard/`の検査器と汎用テストを別repoへ移し、こちらは`.review/`の条件・履歴・計画と固有ルーティング試験（`.review/tests/`）を保持する。汎用テストは一時的な合成fixtureを使い、このrepoのJSONやIDを読まない。JSONの`schema_version`とCLI入出力を維持し、検査器はレビュー済みの固定commitで参照する。共有repoのmainを毎回そのまま実行しない。まずコピーまたは固定版のCLIで接続し、複数repoの利用実績が出るまで常駐サービス・DB・汎用DSLを追加しない。公開ライセンスは所有者の未決事項であり、別repo化を再利用許諾とみなさない。

次の3 PRで、同一原因の修正往復回数、再発した原因数、計画段階で発見できた矛盾、重複投稿数、所有者への判断依頼数を記録する。単純な指摘総数は成功指標にしない。負担だけが増える項目は、根拠を残して確認条件を見直す。
